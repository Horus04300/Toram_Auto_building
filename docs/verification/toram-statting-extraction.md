# 장비 강화(옵션부여) 데이터와 계산 근거

2026-10-20. 게임의 `SmithGrant` 처리와 `GrantData`를 보존된 실행 코드에서 분석했다. 이번 작업은 데이터·계산 규칙 조사이며 앱의 수동 장비 옵션과 추천기는 변경하지 않았다.

## 추출 결과

- [전체 JSON](../../data/sources/toram-statting/catalog.json): 일반 옵션 67종, 속성 6종, 네이티브 ID/10개 필드/6개 언어/앱 스탯 연결.
- [전체 CSV](../../data/sources/toram-statting/catalog.csv): 옵션별 비용·카테고리·구간·상한 필드 비교용.
- [마스터 근거](../../data/sources/toram-statting/native-schema/README.md), [잠재력 근거](../../data/sources/toram-statting/native-potential/README.md), [상한·패널티 근거](../../data/sources/toram-statting/native-penalty/README.md).

일반 아이템의 옵션 전체와 **플레이어가 부여할 수 있는 옵션 목록**은 다르다. 옵부 목록은 별도 번들의 이름 검색이 아니라 `GrantData` 정적 초기화 코드가 만드는 두 Dictionary에 있었다. `EnhanceCost`는 BonusType ID를, `EnhanceElementCost`는 속성 ID를 키로 쓴다. 기존 아이템 ID/언어 자료와 같은 BonusType을 통해 직접 연결했다.

일반 67종 중 65종은 기존 앱의 스탯 ID와 연결됐다. 운석경감(125), 사인경감(127)은 기존 매핑에 없어 `null`로 남겼다. 속성 6종은 `bonusId=65`와 별도 `elementId`로 보존했다. 이 추출표를 앱의 수동 옵션에 자동 적용하지는 않았다.

## 각 필드의 역할

각 행은 `EnhanceProperties2` 40바이트 구조체다. 필드 순서와 오프셋은 마스터 근거에 보존했다.

| 필드 | 역할 |
| --- | --- |
| UsePotential | 기본 구간에서 내부 수치 1당 잠재력 비용 |
| Coefficient | 별도 계수. 생성자의 필드명·값은 확인했으며 실제 소재 소비와의 연결은 미검증 |
| MaterialCategory | 금속/천/짐승/목재/약품/마소의 네이티브 ID |
| AbilityCategory | 동일 카테고리 패널티를 계산하는 ID |
| Rate | 레벨 210 이후 상한 증가의 float32 계수 |
| BaseMax | 기본 구간과 레벨 210 전 상한의 기준 |
| UpperMax / LowerMax | 양수/음수 방향의 별도 제한 필드 |
| OverRate | 경계 밖 구간의 정수 나눗셈·일부 옵션 상세 값 정규화에 사용 |
| DoubleUse | 장비 종류별 비용 배수: 0=그대로, 1=비무기에서 두 배, 2=무기에서 두 배 |

`DoubleUse`는 참/거짓 값이 아니다. `Rate`와 `OverRate`도 서로 다르다. 수치는 화면 문자열 자체가 아닌 내부 옵션 값으로 계산한다. 최대 HP/MP는 기존 표시 규칙의 10배 변환도 필요하다. 상세 화면은 HP/명중/회피/DEF/MDEF/ASPD/CSPD에 추가 정규화 경로를 사용하므로 CSV의 `UpperMax`를 곧바로 화면 최대값으로 읽으면 안 된다.

| 옵션 | 기본 비용 | 카테고리 | BaseMax | OverRate | DoubleUse |
| --- | ---: | ---: | ---: | ---: | ---: |
| ATK+ / ATK% | 3 / 10 | 3 | 20 / 10 | 1 / 1 | 1 / 1 |
| 크리티컬률+ / % | 1 / 1 | 8 | 20 / 20 | 1 / 1 | 0 / 0 |
| 크리티컬대미지+ / % | 3 / 10 | 8 | 20 / 10 | 1 / 1 | 0 / 0 |
| 명중+ / % | 10 / 20 | 5 | 10 / 5 | 2 / 1 | 1 / 1 |
| ASPD+ / % | 1 / 1 | 7 | 20 / 20 | 16 / 1 | 0 / 0 |
| 어그로% | 6 | 10 | 15 | 1 | 0 |

이 표의 비용은 장비 배수·카테고리·구간 초과를 적용하기 전 값이다.

## 부여자 레벨과 스킬에 따른 상한

게임은 캐릭터 상태의 `get_Lv`와 스킬 365=장비 강화, 366=정확한 강화, 367=장인의 강화기술을 읽는다. 음수 스킬 레벨은 0으로 보정한다. 스킬 계수는 `(10+3×s365+3×s366+3×s367)/100`이고, 셋 다 Lv10이면 1이다. 아래 float 곱셈은 실제로 float32이며 `trunc`는 0 방향 절삭이다.

```text
Lv < 210:
  max(1, min(trunc(스킬계수×BaseMax), trunc(Lv/10), BaseMax))

Lv ≥ 210:
  n = max(0, trunc(Lv/10)-20)
  증가 = trunc(float32(Rate×n))×OverRate
  방향별 제한 = (UpperMax 또는 LowerMax - BaseMax)×OverRate + BaseMax
  값 = min(trunc(float32((BaseMax+증가)×스킬계수)), 방향별 제한)
  특정 상세값 타입이면 BaseMax 초과 부분을 OverRate로 나눠 정규화
  max(1, 값)
```

예를 들어 세 스킬 Lv10·부여자 Lv300에서 크리티컬률+ 상한 30, 크리티컬대미지+ 23, 크리티컬대미지% 11, ATK% 15다. 어그로%는 양수 상한 20, 음수 크기 상한 15로 방향별로 다르다. HP·ASPD 등은 상세값 정규화 뒤 화면/내부 값 변환까지 따라야 한다. `max(1,…)`이 나온다고 해당 음수 옵션을 UI/서버가 모두 허용한다는 뜻은 아니다.

사용 가능한 옵션 줄은 `3+floor(float32((s366+2)×0.3))+floor(float32((s367+4)×0.2))`다. 두 스킬 Lv0이면 3줄, Lv10이면 8줄이다. 무조건 정확히 8줄이어야 하는 규칙은 아니다.

추가로 확인한 성공률의 **스킬 보너스 부분**은 `max(s365,0)+(s366>0 ? 10+s366 : 0)+(s367>0 ? 20+s367 : 0)`이다. 셋 다 Lv10이면 +60이다. 낮은 레벨에서는 기존 Smith 원문의 단순 1배/2배/3배 설명과 다르다. 전체 성공률·서버 실행 결과는 이 함수만으로 확정하지 않았다.

## 카테고리 패널티

게임은 **변경 후의 최종 옵션 배열**에서 카테고리별 개수 `n`을 센다. `n≥2`인 카테고리에만 `0.05×n²`를 더해 전체 배율을 만든다.

```text
배율 = 1 + Σ(0.05 × n²), 단 n ≥ 2
소모 잠재력 = trunc_float32(단계별 옵션 비용의 합 × 배율)
```

크리티컬대미지+와 %는 같은 카테고리 8이므로 +20%, 크리티컬률+까지 넣으면 +45%다. 명중+와 %는 별도 카테고리 5여서 +20%p가 더해져 **총 +65%, 배율 1.65**다. 이는 사용자가 설명한 규칙과 일치한다.

카테고리는 1=STR/INT/VIT/AGI/DEX, 2=HP/MP·자연회복, 3=ATK/MATK·안정률·관통, 4=방어·내성·공격 유형 경감, 5=명중, 6=회피, 7=ASPD/CSPD, 8=크리티컬, 9=속성 대미지·속성 내성, 10=이상내성·Guard/Avoid·어그로, 11=속성이다. 이 이름들은 멤버를 요약한 설명이며 게임에 같은 이름의 enum이 있다고 주장하지 않는다.

이미 있던 옵션도 최종 배열에 남으면 개수에 포함된다. 부호나 이번 변경량이 0인지를 기준으로 제외하지 않는다. `Type=0` 빈 슬롯과 호출자가 명시한 제외 Type은 건너뛴다. 직접 함수에 0값의 유효 Type을 넣으면 세지만 게임 UI가 그런 슬롯을 만드는지는 별도 검증 대상이다.

## 소비·반환·절삭 순서

1. 기존 값과 목표 값에서 변경량을 만든다.
2. 장비 종류에 따라 `UsePotential`을 두 배로 만든다.
3. `±BaseMax` 경계를 통과하는 구간을 나눠 계산한다. 양의 초과 구간은 `2×비용×trunc(구간량/OverRate)`이고, 음의 초과 구간 반환에는 0.5배가 들어간다. 기존 음수 값을 복구하는 구간도 별도 분기다.
4. 감소분에는 `float32(TEC/1000+0.05)`를 적용한 뒤 **옵션마다 정수 절삭**한다. TEC255는 약30.5%다.
5. 비용을 합산한 뒤 최종 옵션 배열의 패널티 배율을 **한 번** 적용하고 다시 정수 절삭한다.

정수 나눗셈과 float→int 변환은 **0 방향 절삭**이다. 음수에서는 수학적 바닥 함수와 다르다. float 연산은 각 연산마다 float32로 반올림된다. 함수 내부의 signed short 누적도 근거에 보존했지만 오버플로를 유효한 게임 조작으로 해석하지 않는다.

예를 들어 크리티컬대미지+의 기본 비용 3, 경계 20, TEC255에서 `0→-10`은 -9pt다. `0→-5→-10`으로 나누면 -4-4=-8pt다(카테고리 전). 따라서 **최종 옵션만 더하는 비용표로 실제 다단계 옵부를 재현할 수 없다.**

속성은 일반 증감·TEC 경로를 건너뛴다. 기본 비용은 100이고, 원본 아이템 마스터와 같은 속성이면 장비 배수 처리 후 정수 10분의 1로 줄인다. 이 분기만으로 기존 속성의 임의 교체를 UI/서버가 허용한다고 결론 내릴 수 없다.

## 증거와 재현

저장된 런타임 스냅샷의 선택 함수만 Ghidra로 분석했다. 실행 중인 게임을 새로 읽거나 함수를 실행하지 않았다. 이번에 확인한 설치 DLL과 metadata SHA256은 저장된 분석 버전과 일치했다. 전체 입력 해시는 [provenance.json](../../data/sources/toram-statting/provenance.json)과 각 증거 index에 있다. REA retained Evidence ID는 없다.

```powershell
python tools/extraction/extract-toram-statting.py
python tools/extraction/extract-toram-statting.py --check
python data/sources/toram-statting/native-potential/self-check.py
python data/sources/toram-statting/native-penalty/self-check.py
```

첫 명령은 보존된 초기화 코드에서 JSON/CSV를 재생성하고 나머지는 입력 해시·파싱·경계 사례·산출물 동일성을 검증한다. 새 게임 버전의 코드가 바뀌면 재분석·검토가 필요하며 이 도구가 임의로 새 버전을 허용하지 않는다. 소재 총량, 서버의 최종 성공/실패·슬롯 보존 결과, 모든 UI 입력 허용 조합은 이번 정적 검증의 완료 범위가 아니다.

이번 검증: 추출기 `--check`(73행·6언어·원본/함수 해시·재생성 동일성), potential self-check(3,721 전이 범위와 대표 경계), penalty self-check(12함수 해시·20/45/65%·0/음수/제외·합산 절삭·Lv209/210/300·스킬 슬롯/보너스), `npm run ai:audit`, `git diff --check` 모두 PASS. 앱 실행 코드를 바꾸지 않아 앱 전체 회귀·브라우저 동작 검사는 반복하지 않았다.
