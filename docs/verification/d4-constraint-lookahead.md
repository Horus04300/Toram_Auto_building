# 큰 박스의 제약 경계 추가 분할

2026-09-26. `d4-post-ampr-profile.md`의 다음 후보인 큰 박스 제약 상한 강화를 구현했다.

## 적용 방식과 안전성

- 보통 분할에서 형제 박스가 2개 이상 제약으로 제거되고, 작업자 로컬 제약 탈락/평가 비율이 기존 `utility_pressure` 기준을 만족할 때만 추가 검사를 고려한다. 포화된 MP·CRIT 값이 목표와 같다는 이유만으로 모든 박스를 검사하지 않는다.
- 기존 대미지 근접 lookahead를 적용하지 않은 큰 박스(64개 초과 조합)를 한 단계 더 분할한다. 각 부분공간은 기존 안전 envelope와 동일한 목표 평가기로 판정한다. 형제 탈락 비율은 비용 배분 조건일 뿐 삭제 증거가 아니다.
- 추가 분할에서 안전하게 제거된 부분공간이 있으면 살아남은 자식과 각각의 안전 상한을 반환한다. 전부 살아남으면 원래 박스 하나를 유지한다. 불완전 탐색으로 후보를 없애거나 대기 큐를 무조건 네 배로 늘리지 않는다.
- 기존 대미지 lookahead와 제약 lookahead를 같은 자식에 중복 적용하지 않는다. 제약 검사의 추가 재귀에는 기존 깊이 한도를 전달해 더 깊은 lookahead를 막는다.
- 취소·deadline·오류는 기존 미완료 반환을 사용하며, 호출자가 원래 부모를 재등록한다. 동점 삭제 기준·build ID 순서·계산식은 유지한다.
- 제약 탈락이 적은 경로는 기존 결과 목록에 바로 넣는다. 임시 자식 4개는 고정 배열로 보관해 별도 힙 할당을 하지 않는다.
- Native/checkpoint v8, 계산 v2·split v3·utility policy 2 유지. v4~v7 checkpoint 거부 회귀를 포함한다.

## 검증

- 새 Rust 회귀는 음수 HP 옵션을 가진 큰 박스에서 추가 검사 전후의 전체 공간을 비교한다. 공간이 실제 감소하고, 제거된 모든 조합이 infeasible이며, 중복 coverage가 없고, 보존된 자식 상한이 실제 feasible 점수 이상임을 검사한다. 사전 취소 시 미완료 반환도 검사한다.
- 첫 회귀 입력은 HP 여유가 너무 커 추가 검사가 발동하지 않았다. 옵션 페널티를 강화해 실제 형제 탈락을 발생시킨 뒤 성공했다. 구현을 통과시키기 위해 삭제 안전성 assertion을 완화하지 않았다.
- `cargo test --manifest-path src-tauri/Cargo.toml`: 49+49+15+62=175개 통과. 바이너리별 중복 모듈 검사 포함. 기존 deadline/cancel/checkpoint/resume·직렬/병렬·동점 검사 포함.
- `npm run test:r0`: 71/71 프로세스 성공. JS oracle/상한·원시 parity·utility 105개 직렬/공유 세션 대조 포함. 실제 Native 저장 E2E는 CDP 미설정 SKIP.
- `npm run verify:r9`, `cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings` 통과. 제품 수식·스킬 데이터 변경이 없어 S1을 이번 작업에서 재실행하지 않았다.

## 계측

기존 source/control 바이너리를 `src-tauri/target/constraint-lookahead/before.rs`, `before.exe`에 보존했다. 수정 후 `profile-d4-slow-inputs.mjs build`의 control을 사용한다. 최초 1회 실험은 루브닐 단축, 듀얼 지연을 관측해 임시 Vec 할당을 제거하고 저탈락 경로를 유지하도록 보완했다. 이후 최종 구현으로 전→후/후→전 각 2회씩 측정한다.

```powershell
node tools/profile-d4-slow-inputs.mjs build
$env:D4_EVALUATION_EXPERIMENT='constraint-lookahead'
$env:D4_COMPARE_REPEATS='2'
node tools/benchmark-d4-partial-utility.mjs
```

벤치마크는 루브닐·듀얼·utility-tight의 동일 준비 입력, 16작업자, 새 프로세스 12회를 순차 실행한다. 빌드·회귀 테스트와 겹치지 않는다. 두 바이너리는 같은 초당 snapshot 계측을 포함하며 JS 후보 준비·UI/IPC는 제외한다. 바이너리/입력 해시·평가·메모리·진행 상태·최종 ID는 `d4-constraint-lookahead-measurements.json`에 보존한다. 2회 반복은 P95 인증이 아니다.

## 최종 결과와 채택

| 입력 | 변경 전 2회 | 변경 후 2회 | 판단 |
| --- | --- | --- | --- |
| 루브닐 | 10.277 / 10.223초 | 9.007 / 8.876초 | 평균 약 12.8% 단축 |
| 듀얼 | 19.488 / 20.895초 | 19.651 / 19.308초 | 범위가 겹치며 이 입력의 개선율은 확정하지 않음 |
| 유틸리티 충돌 | 5.813 / 5.949초 | 5.910 / 5.889초 | 평균상 사실상 동일 |

루브닐은 전체 평가가 약 6050만→6082만으로 조금 늘지만, 세션 작업 묶음은 20,603→15,892~15,893회로 약 22.9% 감소했다. 최대 대기 후보는 약 294만→289만이다. 추가 안전 검사를 큐에 넣기 전에 수행하면서 큐/작업 전달 왕복을 줄이는 이득을 관측했다. 최댓값 숫자 하나만 조이는 변화가 아니라 불가능한 부분공간을 먼저 제거하는 방식이다.

관측 peak working set은 루브닐 약 134.4→132.5 MiB, 듀얼 약 164 MiB 유지, 충돌 약 125→127~146 MiB였다. 충돌 입력은 최대 대기 후보도 291만→294만으로 소폭 늘었다. 메모리 감소를 전 입력에서 보장하는 변경은 아니며, 이 입력에서는 추가 분할의 공간 비용이 남는다.

12회 모두 exact이며 입력별 최적 점수·조합 ID·최종 upper가 일치했다. 수정 후 진행 snapshot의 상한이 최종 exact 점수를 포함하는 검사도 통과했다. 선택적 제약 경계 분할을 제품 경로에 채택하며 모든 입력의 속도 향상을 주장하지 않는다.
