# 듀얼소드 입력의 임의 유틸리티 보정 제거 비교

2026-10-02. 현재 구현 상태는 `../handoff/current-development-handoff.md`가 기준이다. 이 작업은 입력과 측정·설명을 보완했으며 계산식이나 탐색 코드는 변경하지 않았다.

**2026-10-03 정정: 이 입력은 사용자 듀얼소드 빌드를 재현하지 못한 부적절한 샘플이다. 아래 시간 감소를 사용자 요청의 성능 개선 근거에서 제외한다.** 실제 장비 옵션·스킬·버프·요리 합산을 준비하지 않은 채 가산만 제거한 검사는 요청한 feasible 빌드 성능 검증을 충족하지 못했다. 실제 입력을 요청한 뒤 검증해야 하며 해당 작업은 미완료다. 아래 입력·측정은 잘못된 실험의 감사 기록으로만 보존한다.

## 기존 입력의 출처와 설명 정정

앞선 상한·분기 비교의 ‘듀얼·유틸리티 여유’ 입력은 기존 `tools/benchmarks/benchmark-crysta-native-scaling.mjs`의 회귀 설정을 재사용한 것이다. 듀얼 무기/능력치 설정에 `amprF=200`, `critF=200`, `maxHpF=20000`, `maxMpF=3000`, `aspdF=3000`이 들어 있었다. 이 다섯 수치는 실제 장비·스킬·요리의 합산 출처가 연결된 값이 아니다.

`baseContext`는 후보 크리스타 옵션을 적용하기 전의 공통 계산 입력이다. `amprF`와 `critF`는 각각 AMPR와 크리티컬에 숫자를 더하는 옵션 좌표다. 200은 듀얼소드 고유 수치나 최종 계산 결과가 아니다. 기존 입력을 크리스타 없이 계산하면 듀얼 적용 전 AMPR는 244(최종 AMPR 488), 평타 CRIT은 225다. 최적화 제약 판정은 별도의 기존 포화 정책을 사용한다.

이 입력을 유지한 전후 비교는 조건에 여유가 있는 경우의 동작과 비용을 관찰하는 자료로 사용할 수 있다. 다만 이를 실제 듀얼소드 빌드의 대표 결과로 해석할 수 없다. ‘새 검사의 비용을 확인하려고 처음부터 200을 넣었다’는 이전 설명은 최초 설정 이유를 확인한 설명이 아니며, 확인된 사실은 기존 회귀 입력을 재사용했다는 것이다.

## 이번 입력

`tools/fixtures/crysta-dual-unadjusted.json`에서 위 다섯 가산 좌표만 0으로 바꿨다. 나머지 레벨·능력치·무기·중량옷·보스·금지·크리스타 데이터·요구조건은 동일하다. 원래 입력을 보정 전 값으로 복원해 전체 객체가 일치하는지 집계 스크립트에서 검사했다. AMPR·CRIT만 지우고 HP·MP·ASPD 가산을 남기는 비교는 하지 않았다.

요구조건은 HP 10,000, MP 2,000, **듀얼 적용 전 AMPR 100**, 저항 후 평타 CRIT 100, ASPD 1,000이다. 요구조건을 낮추거나 해제하지 않았다. 크리스타 없이 계산한 값은 HP 2,520, MP 425, 듀얼 적용 전 AMPR 14(최종 28), CRIT 25, ASPD 868이다. 이 시작값의 부족만으로 전체 조합이 불가능하다고 판정하지 않고 전체 Native 탐색 결과를 확인했다.

이 입력은 기존 테스트에서 임의 유틸리티 가산을 제거한 입력이며 저장된 실제 플레이어 빌드는 아니다. 무기 공격력과 능력치 등 나머지 테스트 설정은 유지했다.

## 10회씩의 전후 결과

Windows / AMD Ryzen 7 9800X3D / 논리 16스레드 / Node v24.17.0. 기존 보관 실행파일 세 개를 같은 현재 JS client로 실행했다. 각 표본마다 새 Node·Native 프로세스를 시작하고, 세 버전의 여섯 실행 순서를 순환하여 10회씩 총 30회를 순차 측정했다. 빌드·테스트와 겹치지 않았다. 파일 SHA-256과 Rust/JS 소스 해시를 상세 기록에 보존하고 현재 v11 실행파일의 소스 일치를 확인했다.

`timing.totalMs`는 raw 입력 컴파일부터 JS 후보 준비, Native 실행과 결과 복원까지 포함한다. UI/WebView는 제외하고 stdio transport를 사용한다. 해가 없으므로 최종 bestBuild의 JS 재평가는 발생하지 않는다. 모든 실행은 30초 slice 하나에서 끝났다.

| 구현 | 평균 / 중앙값 | 범위 | 평균 평가 횟수 | 평균 방문 노드 |
| --- | --- | --- | --- | --- |
| 상한 개선 전 v9 | 1.700 / 1.696초 | 1.637~1.760초 | 4,987,830 | 1,244,759 |
| 결합 상한 적용 v10 | 1.394 / 1.386초 | 1.361~1.433초 | 538,787 | 251,988 |
| 분기 처리까지 적용 v11 | 1.365 / 1.358초 | 1.333~1.425초 | 204,691 | 144,636 |

- v9→v10: 평균 **18.0% 감소**, 평가 약 **89.2% 감소**. 10쌍 모두 빨랐고 전체 시간 범위도 겹치지 않았다.
- v10→v11: 평균 **2.1% 감소(약 29ms)**, 평가 약 **62.0% 감소**. 10쌍 중 8쌍에서 빨랐고 시간 범위는 겹친다. 마지막 분기 변경만의 전체 시간 이득은 작다.
- v9→v11: 평균 **19.7% 감소**, 중앙값 **19.9% 감소**, 평가 약 **95.9% 감소**. 10쌍 모두 빨랐다. 평가 카운터 감소율이 전체 실행시간 감소율을 뜻하지는 않는다. 추가 결합 검사 횟수도 기존 evaluations에는 포함되지 않는다.

### 결과의 의미와 제한

30회 모두 incumbent 없이 남은 작업이 소진됐으며 `readyWorkItems=0`, `continuationId=null`, `bestBuild=null`, `score=null`, `upperBound=null`이었다. v10/v11은 `invalid`를 반환한다. v9은 frontier가 소진되어도 해가 없으면 `no-incumbent-yet`를 반환했던 기존 표시 문제를 포함한다. 이 상태 차이는 이전 상한 작업에서 수정한 것이며 이번에 새로 바뀐 것이 아니다.

따라서 확인한 것은 **이 무보정 입력의 불가능성을 판정하는 시간이 줄었다**는 것이다. 요구조건을 만족하는 듀얼소드 조합의 최적해를 찾는 시간이 줄었다는 근거로 사용할 수 없다. 또한 불가능 입력의 10회 결과를 실제 필수 입력의 exact 10초/P95 Gate로 세지 않는다.

현재 결과로 상한 개선의 반복 가능한 효과는 확인됐고, 분기 변경만의 추가 효과는 작았다. 실제 장비·스킬 합산 출처가 있는 feasible 듀얼소드 입력의 성능은 별도로 검증해야 한다. 이번 검사에 맞추기 위해 출처 없는 가산을 다시 넣지는 않았다.

Native peak working set도 50ms마다 표본 수집했지만 Native 실행 구간이 짧아 표본 누락에 민감하다. 이 측정으로 메모리 개선율을 주장하지 않는다.

## 검증과 재현

- `node src-tauri/target/dual-unadjusted/prepare.mjs`: 변경 좌표·보정 전/후 계산·요구조건 보존 검사.
- `& ./src-tauri/target/dual-unadjusted/compare.ps1`: 3버전×10회, 총 30회 fresh 프로세스 실행 완료.
- `node src-tauri/target/dual-unadjusted/summarize.mjs`: 30회 소진 상태·입력 보존·실행파일/소스 해시 검사 통과 및 상세 기록 생성.
- `npm run ai:audit`, `git diff --check`: 문서·fixture 변경 검증.

원본/수정 raw 입력, 개별 시간·카운터·메모리·상태·환경·해시는 `crysta-dual-unadjusted-measurements.json`에 저장했다. 로컬 재현 스크립트는 Git 제외 디렉터리 `src-tauri/target/dual-unadjusted/`에 있고 비교 실행파일은 이전 상한/분기 실험 디렉터리에 있다. 새 checkout에는 이 로컬 실행파일이 자동 제공되지 않는다. 현재 코드만의 재현은 아래 표준 도구를 사용할 수 있다. 표준 도구는 feasible exact 비교만 승인하므로 이 입력의 `invalid`를 기록한 뒤 종료 코드 1을 반환한다.

```powershell
npm run bench:optimization:build
npm run bench:optimization -- --input tools/fixtures/crysta-dual-unadjusted.json --repeats 1 --output src-tauri/target/computation-benchmark/dual-unadjusted.json
```

프로덕션 코드를 바꾸지 않아 기존 전체 계산/탐색 회귀를 다시 실행하지 않았다. 이번에 실행한 검사와 이전 코드 변경의 회귀 통과 기록을 구분한다.
