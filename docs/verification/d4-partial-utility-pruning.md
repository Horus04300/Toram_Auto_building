# 진행 상한 수정과 부분 조합 유틸리티 검사

2026-09-24. `d4-post-utility-profile.md`에서 발견한 진행 상한 반환 문제를 수정하고 첫 성능 후보를 구현했다.

## 정확성 계약

- 세션이 반환하는 전체 상한은 `max(남은 공간의 안전 상한, 현재 feasible 최고 점수)`다. heap의 상한이 최고 점수보다 낮아진 뒤에도 bounded snapshot에 잘못된 전체 상한을 표시하지 않는다. heap을 조기에 비우거나 동점 ID 탐색을 생략하지 않는다.
- 제품 공유 세션의 작은 박스 열거는 선택한 부분합과 나머지 그룹의 기존 envelope 합으로 유틸리티 상한을 검사한다. 최소 하나의 목표를 충족할 수 없을 때 해당 하위 조합을 생략한다. 후보 삭제·분할 트리·대미지 상한 수식은 변경하지 않는다.
- 추가 검사 적용은 작업자 로컬 `pruned_by_constraint > evaluations / 4`로 선택한다. 이 비율에는 완성 조합과 박스의 제약 탈락이 포함되며 통계적 확률이 아니다. 검사 비용을 쓸지 고르는 규칙일 뿐 제거 증거로 사용하지 않는다.
- 부분 조합 검사에는 남은 완성 조합이 4개 이상이어야 한다. 이미 실패한 제약에서는 평가를 멈추고, 통과한 상한도 대미지를 계산하기 전에 멈춘다. 추가 검사를 끈 경로는 남은 조합 수 계산도 생략한다.
- 기존 취소·deadline 검사와 중단한 부모 박스 재등록 경로를 유지한다. 추가 검사 통계는 실제 추가 평가 및 제거한 부분공간을 센다. `enumeratedCompletions`는 생략된 조합을 포함하지 않는다.
- 직렬 완전 열거는 독립 대조 경로로 유지한다. 원자 카운터를 쓰는 별도 standalone scheduler는 추가 검사 활성화를 기본으로 하지 않는다. 제품의 `LocalSearchCounters` 공유 세션에서 적용한다.
- Native 엔진/checkpoint v7. 이전 v4/v5/v6 checkpoint는 거부한다. 계산 v2, split v3, utility policy 2 유지.

## 검증

- snapshot 회귀: 남은 heap 상한이 incumbent보다 낮아진 bounded 상태와 checkpoint 복원 모두 `upperBound == score` 확인.
- 부분 조합 회귀: 음수 HP와 높은 ATKP가 함께 붙은 256개 조합에서 검사 적용/미적용의 최적 점수·ID 일치, 실제 열거 감소 확인.
- `cargo test --manifest-path src-tauri/Cargo.toml`: 47+47+14+60=168개 통과(바이너리별 중복 모듈 검사 포함).
- `npm run test:r0`: 71/71 프로세스 성공. 실제 Native 저장 E2E는 CDP 미설정 SKIP. 마지막 조기 실패 평가/비활성 경로 단순화 후 Rust 전체와 utility 105사례를 다시 실행했다.
- `tools/test-d4-utility-caps.mjs`를 확장해 105개 입력의 JS 완전 탐색·직렬 Native·4작업자 공유 세션의 상태·점수·최적 ID를 비교한다. 트리 상한·단조성 및 13개 경계 검사도 통과했다.
- `npm run verify:r9`, release 브리지 빌드, clippy `--all-targets -- -D warnings` 통과. 이번 변경은 스킬 수식·원문 연결 변경이 아니며 S1은 재실행하지 않았다. 설치본 UI/저장 E2E는 미실행이다.

## 계측 방법

변경 전 계측용 control 바이너리를 `target/partial-utility/before.exe`에 보존하고, 수정 후 `profile-d4-slow-inputs.mjs build`의 control을 after로 사용했다. `node tools/benchmark-d4-partial-utility.mjs`가 세 입력에서 전→후/후→전 순으로 각 2회씩 순차 실행한다. 빌드·테스트와 계측을 겹치지 않았다.

두 바이너리는 동일한 초당 진행 snapshot을 포함한다. 후보 준비와 앱 UI/IPC는 측정하지 않는다. 원자료 `d4-partial-utility-measurements.json`에 바이너리·입력 SHA-256, 최종 조합, 시간·메모리·평가·열거 수·진행 snapshot을 기록한다. 수정 후 snapshot마다 최종 exact 점수 이상을 포함하는지도 검사한다. 2회 반복의 작은 시간 차이는 확정적 개선율이나 모든 입력의 P95 보장으로 해석하지 않는다.

## 최종 측정

| 입력 | 변경 전 시간 | 변경 후 시간 | 완성 조합 열거 전 → 후 |
| --- | --- | --- | --- |
| 루브닐 | 9.275 / 9.566초 | 9.293 / 9.329초 | 3,994,073 → 3,183,289~3,183,609 |
| 듀얼 | 18.083 / 17.402초 | 17.736 / 17.345초 | 50,924,398 → 동일 |
| 유틸리티 충돌 | 5.124 / 5.316초 | 5.139 / 4.950초 | 35,345,610 → 32,660,541~32,693,230 |

12회 모두 exact, 입력별 점수·최적 ID·최종 upper 일치. 변경 후 모든 진행 snapshot의 upper가 최종 최적점을 포함했다. 루브닐 약 20.3%, 충돌 약 7.5~7.6%의 완성 조합 평가를 줄였다. 추가 상한 검사를 포함한 전체 평가도 각각 약 6115만→6050만, 6532만→6329만~6331만으로 감소했다. 듀얼 평가 수는 기존과 같다. 실행 시간은 평균상 소폭 감소하지만 반복 변동이 있어 뚜렷한 속도 개선율로 확정하지 않는다. 큐 자체 비용은 이 변경으로 제거되지 않는다.

선택적 검사를 제품 공유 세션에 채택했다. 적용 이득이 있는 입력의 평가량 감소와 최적 결과 보존을 확인했으며, 낮은 제약 탈락 입력에서는 기존 경로를 유지한다. 검증 도구 문법 검사, fmt, AI 문서 감사 및 diff 검사도 통과했다.
