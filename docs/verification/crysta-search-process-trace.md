# 크리스타 B&B 실행 과정 로그 분석

- 실행일: 2026-10-11, 개선 전 Native v16 조사 기록. 이후 변경은 [초기해 개선 기록](crysta-pair-seed.md)을 따른다.
- 입력: `tools/fixtures/crysta-saved-sword-shield-revenir-unlocked.json`의 저장 검방 샘플. 모든 크리스타 잠금 해제 상태이며 기존 스탯·스킬·요구조건을 유지했다. 현재 사용자가 앱에서 편집 중인 입력을 읽은 것은 아니다.
- 목적: 시간 측정 없이 후보 준비 → 초기해 → 상자 분기 → 상한/제약 검사 → 실제 완성 조합 평가의 실행량과 진행을 확인한다.
- 확정 결과 근거: `crysta-search-process-trace-results.json`. 전체 작업 묶음 로그 생성 경로는 `src-tauri/target/search-trace/events-1.jsonl`, `events-8.jsonl`; 전체 결과 생성 경로는 같은 폴더의 `report-1.json`, `report-8.json`이다. 이 생성 경로는 재실행 시 덮어쓰므로 현재 파일을 당시 결과로 인용하지 않는다.
- 제품 알고리즘·상한·분기 정책·계산식은 수정하지 않았다. `trace-crysta-search.mjs`가 현재 Rust 소스를 별도 crate에 복사해 이벤트 카운터와 표본 로그를 삽입한다. 소스 hash와 유일한 삽입 anchor를 검사한다.

## 실행 경로와 범위

기존 headless 환경에서 제품 compiler와 Native client의 실제 prepare/native payload 생성 경로를 사용했다. 복사본의 `NativeSearchSession::new`와 `advance_parallel_slice_with_control`을 호출한다. Tauri 화면/IPC/service의 30초 continuation은 이 실행에 포함하지 않는다.

1 worker에서는 작업 묶음당 최대 32개 frontier 상자를 꺼내 10,000묶음까지 실행했다. 8 workers에서는 최대 256개씩 1,250묶음을 실행했다. deadline은 전달하지 않았고 **작업량으로 중단**했다. 재귀 lookahead 때문에 방문 수는 꺼낸 상자 수보다 크다. 두 전체 입력 실행은 모두 `bounded`이며 전체 최적성을 증명한 실행이 아니다.

요구조건은 HP 10,000 / MP 2,000 / 듀얼 전 AMPR 100 / 평타 CRIT 100 / ASPD 1,000이다. raw 부위별 패키지 수는 4,000 / 3,319 / 3,914 / 3,740, Pareto 준비 후에는 1,701 / 1,330 / 1,648 / 1,572였다. 준비 후 곱은 5,860,918,788,480조합이다. 이 곱을 탐색 진행률의 분모로 쓰지 않는다.

| 1,000 | 32,915 | 93,256 | 0 | 1,821,006 | 2,422,534.68 |
| 5,000 | 200,161 | 425,395 | 0 | 1,821,006 | 2,218,243.98 |

초기해 단계에서 이미 feasible 조합을 얻었다(1,526회 후보 평가 중 573회 feasible). 그 뒤 285,462개 노드를 방문해야 첫 소형 상자에 도달했다. 초기해가 5,000묶음까지 그대로인 동안 queue는 425,395개로 늘었다. 탐색은 진행되지만, 높은 상한을 가진 넓은 상자들을 분기하고 보관하는 작업에 집중되어 실제 조합 확인이 늦어진다.

## 주요 문제와 코드 연결

### 1. 상한을 통과하는 상자가 많이 쌓인다

`solver.rs:1289`의 `group_envelope`는 부위 내 좌표별 최댓값을 모으고, `solver.rs:1534`의 `box_stats`는 부위 envelope를 더한 뒤 결합 공격 상한을 적용한다. 서로 다른 패키지가 각 좌표의 최대 공급자일 수 있다. 기존 결합 상한이 있어도 모든 옵션·요구조건의 상관을 실제 조합처럼 유지하는 표현은 아니다.

실행에서 자식 생성 이벤트 2,067,828회 중 1,237,893회(59.86%)가 제약·점수 상한 검사를 통과했다. 점수 상한 탈락은 653,343회, 개별 Utility 탈락 176,585회, 자식 joint 사전 탈락 7회였다. 최종 gap은 15.34%, 최종 frontier 선두 상자의 부위별 크기는 53 × 42 × 13 × 12였다. 넓은 공간이 최선 점수를 넘는 상한을 유지한다.

`WorkItem`의 최대 상한 우선 정렬(`solver.rs:1182`)과 64조합 이하에서만 열거하는 정책(`solver.rs:2902`)이 이 느슨함과 함께 작동해 실제 완성 조합에 도달하기 전 frontier를 크게 만든다. 상한이 큰 순서라는 사실만으로 해를 빨리 개선하거나 증명을 빨리 끝내지는 못한다.

### 2. 실제 열거에서도 제약 탈락이 늦게 드러난다

두 번째 소형 상자 표본(`smallBoxOutcome`, occurrence 2)은 크기 7 × 2 × 2 × 2, 상한 2,183,585.40이었다. 실제 56조합을 평가하자 52조합이 요구조건에 탈락했고 나머지 4조합도 기존 해 1,830,685.80보다 낮았다. 기존 해를 개선하는 조합은 없었다. 상자가 검사를 통과한 것과 실제 feasible 고득점 조합이 존재하는 것은 다른 사건이다.

전체 열거 406회 중 376회(92.61%)가 제약 탈락, 25회는 기존 해보다 낮고 5회는 incumbent를 개선했다. `leafRejected` 표본에는 HP 9,523, MP 1,875, AMPR 89, 평타 CRIT 90 등이 남았다. 표본만으로 각 제약의 전체 탈락 비중을 추정하지 않는다.

현재 joint 검사는 AMPR/CRIT 관계를 다루며, 이 실행의 joint 탈락은 방문 상자 639회 + 자식 7회였다. 총 제약 탈락 177,231회 중 대부분은 일반 Utility 상한/실제 조합 검사에서 발생했다. 이 입력에서는 joint 가지치기가 전체 상자 증가를 충분히 억제하지 못했다.

### 3. 반복 작업의 대부분은 완성 조합보다 자식 상한 평가다

총 평가 2,069,755회 중 자식 상한 평가가 2,067,821회(99.91%)다. `solver.rs:2877`의 `expand_parallel_node_inner`에서 stats 합산·Utility 검사·대미지 상한 계산을 반복하는 과정이 지배적이다. 이는 **호출 수 기준**이며 함수별 CPU 비용/시간 비중을 뜻하지 않는다.

일반 lookahead 196,278회, Utility lookahead 1,401회로 전체 방문의 38.19%가 추가 재귀였다(`solver.rs:2816`). 부분 Utility 검사 카운터는 0이었다. 이는 해당 실행에서 그 휴리스틱 조건이 켜지지 않았다는 뜻이다. lookahead를 끄거나 64 한도를 바꾸는 것이 개선된다는 증거는 이번 로그에 없으므로 정책을 수정하지 않았다.

8 workers에서도 방문 515,473회, 미해결 상자 718,479개, 열거 406회, 제약 탈락 376회, 최선 점수 1,851,405.06으로 같은 양상을 확인했다. 병렬 bounded 탐색 순서는 달라질 수 있으므로 카운터 결정성이나 시간 성능을 주장하지 않는다.

## 검증 및 재현

```powershell
node tools/benchmarks/trace-crysta-search.mjs build
node tools/benchmarks/trace-crysta-search.mjs run
node tools/benchmarks/trace-crysta-search.mjs run --threads 8 --max-batches 1250
```

- Build/run PASS. 매번 입력은 현재 JS/compiler/client 경로에서 준비하며 저장된 결과를 재사용하지 않는다.
- 1 worker control/trace: 상태·점수·build ID·상한 및 방문/평가/가지치기/열거 카운터 모두 일치 PASS.
- 두 전체 실행: 이벤트 합계/평가 합계와 solver 카운터 일치, feasible 여부와 최종 점수의 JS 재평가 PASS.
- 준비된 입력에서 부위별 3패키지(현재 feasible 해의 패키지 + 앞의 다른 2패키지)로 만든 81조합 검증: 초기 ID를 feasible 조합으로 지정, 같은 binary를 1 worker/100묶음 한도로 실행. control/trace 모든 결과 일치, `exact`, upper=score, 이벤트 합계 PASS. 전체 입력 최적성의 증거로 사용하지 않는다.
- 이벤트 상세는 발생 순번 1, 2, 4, 8, …에서 표본 저장하며 모든 발생은 카운터에 포함한다. 이벤트 수는 고유 조합 수가 아니다. compact parent를 유지하는 Utility lookahead의 재검사도 카운터에 포함된다.
- 이번 분석은 소요 시간, peak memory, 실제 앱 화면, Worker fallback, 다른 빌드의 성능을 검증하지 않았다.

후속 실험의 우선 대상은 **상관관계를 잃어 살아남는 상자와 넓은 frontier 증가**다. 안전한 상한 강화/상자 표현을 먼저 검토하고, feasible 조합 도달을 앞당기는 탐색 순서는 별도 비교한다. 후보 삭제·상한·분기 변경은 `docs/architecture/crysta-optimization-contract.md`의 oracle/property/coverage 및 성능 Gate를 통과한 뒤에만 제품에 적용한다.

## 추가 질문: 실제 불필요한 평가의 비율

2026-10-11 같은 1 worker/10,000묶음 입력을 재실행했다. 복사본에서 상한 평가의 tree-node tuple과 초기해/완성 조합 평가의 package ID tuple을 각각 HashSet으로 기록했다. 고정 context/requirements에서 동일 tuple의 재평가는 동일한 값 계산을 반복한다. 이는 평가값 재사용으로 생략 가능한 호출 수이며 캐시의 메모리·조회 비용을 제외한 CPU 절감률은 아니다. 추가 HashSet도 계측용이며 제품 코드에 넣지 않았다.

| 구분 | 횟수 | 전체 평가 2,069,755회 대비 |
| --- | ---: | ---: |
| 동일 상자 상한 재평가 | 312 | 0.015075% |
| 동일 완성 조합 재평가(초기해 포함) | 8 | 0.000387% |
| 반복 평가 합계 | **320** | **0.015461%** |
| 가지치기 없이 결과를 버린 Utility lookahead의 자식 상한 평가 | 852 | 0.041164% |

Utility lookahead 1,401회 중 213회는 검사한 4개 자식이 모두 살아남아 자식을 버리고 compact parent를 그대로 유지했다(`solver.rs:3026` 부근). 이 추가 평가 852회는 해당 검사에서 공간 제거·incumbent 개선에 활용되지 않았다. 하지만 검사를 해야 그 사실을 알 수 있으며 이후 동일 자식 재평가와 중복될 수 있다. 따라서 반복 평가 비율과 더해 총 낭비율로 보고하지 않는다.

**측정된 반복 평가 비율은 0.0155%다.** 전체 상한 평가 99.91%를 불필요한 연산으로 분류할 근거는 없다. 서로 다른 상자의 안전 상한을 증명하기 위한 작업이 대부분이며, 더 강한 상한으로 실제 줄일 수 있는 양은 아직 검증하지 않았다. 이 값은 정해진 작업량으로 중단한 이번 입력 구간의 호출 수 기준이고 전체 exact 실행/다른 입력의 비율이 아니다.

추가 계측 후 기존 결과·상한·모든 solver 카운터가 이전 로그 및 control과 동일했고 최종 JS 평가도 PASS였다. 수치·표본은 결과 JSON의 `redundantEvaluationAudit`에 보존했다. 재실행 명령은 위의 build/run과 같다.
