# 현재 아이템 데이터 형식 평가

2026-10-18. 결론은 **현재 425개 크리스타에는 기존 형태가 충분히 작고, 전체 게임 아이템·다국어·갱신 이력에는 ID 기반으로 분리한 가공본이 적합하다**는 것이다. 이를 실제 변환기와 개발판 적용 명령에 연결했다. 계약은 [item-data-format.md](../architecture/item-data-format.md), 실행은 [toram-item-pipeline.md](toram-item-pipeline.md)를 따른다.

## 현재 형식의 장점과 한계

`web/src/data/crysta-data.js`는 425개·52,167바이트(gzip 11,163)다. `stats` 사전은 희소한 스탯을 표현하기에 간단하고, UI의 `getCrystaByName`도 처음에 이름 맵을 만들어 이후 조회하므로 매번 전 배열을 검색하지 않는다. 이 규모의 파일을 작게 만들려고 바이너리/DB/숫자 스탯 벡터를 도입할 근거는 없다.

확장할 때의 문제는 용량보다 계약이다. 이름이 객체 키·저장값·계보 링크라 번역/이름 변경과 충돌에 취약하다. 실제 전체 데이터에는 같은 한국어 이름을 공유하는 ID 그룹이 36개다. 현재 425개에는 정규화된 이름 중복이 없지만 이 조건을 전체 데이터로 일반화할 수 없다. `condStats`의 main/sub는 AND인데 네이티브에는 둘 중 하나인 OR 조건도 있어 그대로 옮기면 계산이 달라진다.

검토용 전체 JSON은 44,568,723바이트다. minify만 하면 26,366,453바이트가 되지만 여전히 6언어·raw record·근거·관계를 매번 함께 파싱한다. 추출본을 런타임 카탈로그로 직접 읽는 방식은 채택하지 않았다.

## 측정

아래 표와 보존 계측 JSON은 소모품 버프 연결 전 최초 가공본의 측정이다. Node v24.17.0, 같은 프로세스에서 준비된 문자열을 11회 파싱/평가한 중앙값이다. 압축 크기는 각 요청 파일을 따로 gzip한 합계다. 원본과 가공본은 모두 11,723개를 보존하지만 가공본은 앱용 필드만 포함하며 상세 원문은 원본 스냅샷에 남긴다. 기존 425개와 전체 카탈로그의 속도를 같은 작업량으로 비교하지 않는다.

| 대상 | 요청 파일 | 비압축 크기 | gzip 크기 | 파싱/평가 중앙값 |
| --- | ---: | ---: | ---: | ---: |
| 기존 425개 classic JS | 1 | 52,167 B | 11,163 B | 약 0.70 ms |
| 전체 연결 JSON | 1 | 44,568,723 B | 3,186,724 B | 약 68.7 ms |
| 동일 전체 JSON minify | 1 | 26,366,453 B | 2,590,437 B | 약 56.9 ms |
| 가공본 전체 종류·6언어 합계 | 106 | 10,654,969 B | 1,217,136 B | 약 26.6 ms |
| 한국어 크리스타 ID 최초 조회 | 4 | 426,682 B | 54,612 B | 약 1.16 ms |
| 같은 종류의 한국어 설명 추가 조회 | 1 | 34,757 B | 2,457 B | 약 0.09 ms |
| 한국어 크리스타 이름 목록만 | 2 | 39,463 B | 12,668 B | 약 0.06 ms |

전체 연결 JSON을 읽는 경우에 비해 첫 ID 조회 파일 크기는 99.04% 감소한다. 같은 항목 재조회는 추가 요청 0회다. 이것은 파일 구성/Node 파싱 측정이며 실제 네트워크·브라우저 시작 시간·앱 전체 속도 개선률을 뜻하지 않는다. [보존한 계측 JSON](item-data-format-measurements.json)이 이번 값이며 `node tools/benchmarks/benchmark-item-data-format.mjs`로 재현한 새 계측은 `build/tmp/toram-item-format-assessment.json`에 쓴다.

## 채택한 구조

- 이름 대신 게임 ID로 객체를 찾는다. 이름·설명을 종류/언어별로 분리하고 누락 번역도 null로 보존한다.
- 계산에 쓰는 sparse `stats` 형태와 프로젝트 canonical 키는 유지한다. 소비 시 `{key,value}` 옵션 목록으로 바꾼다. 새 계산 엔진이나 벡터 포맷은 만들지 않는다.
- 설명·미연결 효과 문구·원본 기본 필드와 계산 데이터를 분리한다. raw hex·offset·네이티브 의사코드는 원본 조사 자료에 유지한다.
- 내용 hash 파일명을 manifest가 참조한다. 파일을 모두 검증한 후 manifest를 교체하고 빌드에는 참조한 파일만 포함한다.
- 개발판 API는 필요한 종류와 언어만 읽고 같은 요청을 공유한다. 시작 시 전체 카탈로그를 읽지 않는다.

소모품 연결 뒤 비어 있지 않은 옵션 18,439개는 **프로젝트 키 매핑 15,650개 + 미연결 1,964개 + 장비 조건 마커 589개 + 시간 마커 236개**로 설명된다. `fullyMappedEquipment=6,281`, `fullyMappedConsumableBuffs=206`은 옵션 키 매핑 범위이지 실제 게임 산식 전체 검증 수가 아니다. 회복·특수 효과·아바타 전용·아직 매핑되지 않은 옵션을 일반 숫자 스탯으로 추측해 넣지 않았다.

## 적용·검증 범위

추출 단계에 `project/` 생성 단계를 추가했고 `npm run items:sync`로 결과를 `web/public/game-data/items/`에 적용한다. root/하위 경로에 맞는 `ToramApp.items` API와 웹/앱 준비 단계도 연결했다. 네이티브 재검토 대상이나 변환 실패에서 이전 개발판 manifest 유지, 중복 sync 차단을 확인했다.

기존 425개 계산 자료·이름 기반 저장 스키마·계보·잠금·금지 처리는 그대로다. 새 가공본을 추천기 후보 전체로 바꾸려면 게임 ID 마이그레이션과 강화 계보 검증을 먼저 끝내야 한다. 미연결 효과가 활성인 아이템은 `resolveItemOptions`가 오류를 반환하므로, 부분 값만 적용한 결과를 완전한 계산이라고 보여주지 않는다.

후속 연결에서는 주무기·보조·몸/추가/특수 장비와 단순 버프 소모품의 선택·계산·저장에 가공본을 사용한다. 보조의 일반 옵션 적용 여부는 확인된 native 종류 분기를 따른다. 선택한 몇 개의 ID·버전·조건/수치만 저장해 전체 카탈로그를 빌드마다 복제하지 않는다. 기존 커스텀 옵션과 수동 외부 보정은 보존하며 제작 장비는 수동 입력만 사용할 수 있다. 원본 선택은 선택 사항이고, 선택 시에는 수동 보정과 합산한다. 저장 빌드는 선택 정의를 고정해 이후 업데이트가 기존 계산을 바꾸지 않는다. 상세 계약은 [장비·소모품 적용 경계](../architecture/item-data-format.md)를 따른다.

실행 결과: `npm run items:test`, Python 파이프라인 self-test 14개, `verify:architecture`, `ai:audit`, `git diff --check`, source/web/desktop entry 검사 PASS. 실제 Edge의 개발 루트·배포 하위 경로 모두 ID 9911의 HP 1000·돌진경감 10을 4개 요청으로 읽고 재조회 추가 요청 0회를 확인했다. 기존 계산·JSON 저장/복원·Worker exact/cancel 회귀도 PASS다. 검토되지 않은 설치본으로 sync했을 때 needs-review/개발판 manifest hash 불변을 확인했고, 실제 공개 CDN을 쓰는 `npm run items:sync` 재실행은 unchanged/developmentApplied=true였다. 공개 릴리스나 실제 미래 게임 버전 검증을 수행한 결과는 아니다.
