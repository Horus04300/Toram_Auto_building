# 스킬트리 검증 기준

이 문서는 스킬트리별 데이터화 작업의 완료 기준과 검증 절차를 정의한다. 개별 스킬의 오류를 수정하기 전에 이 기준을 적용하며, 원문에 없는 내용을 추정하여 계산식으로 등록하지 않는다.

## 1. 검증 단위와 원문 기준

- 검증 단위는 스킬트리 하나다.
- 기준 원문은 `docs/sources/skills/<TreeId>.txt`이며, 수집 URL·수집 시각·SHA-256은 같은 폴더의 `manifest.json`에서 확인한다.
- 데이터 정의에는 `sourceRef.file`과 `sourceRef.anchor`를 기록한다. `anchor`는 원문의 효과·조건·상한을 식별할 수 있는 실제 문구여야 한다.
- 원문이 모호하거나 수치가 누락되었으면 `unknown` 또는 `notModeled`로 남긴다. 임의의 수치·상한·조건을 넣지 않는다.

## 2. 스킬별 판정 단계

각 스킬은 아래 상태를 독립적으로 기록한다. 기존 `dataStatus`의 `unreviewed`, `partial`, `verified`는 이 판정의 요약값으로만 사용한다.

| 단계 | 의미 | 완료 조건 |
| --- | --- | --- |
| S0 미확인 | 원문과 대조하지 않음 | 카탈로그 기본 등록만 존재 |
| S1 출처 연결 | 원문상 해당 스킬 위치를 찾음 | `sourceRef`와 실제 anchor 대조 통과 |
| S2 구조 확인 | 스킬의 성격과 상태를 확인 | 패시브·공격·버프·유틸리티와 대상·무기 제한이 원문과 일치 |
| S3 규칙 기록 | 계산 가능한 모든 규칙을 데이터로 기록 | 비용·수식·조건·스택·상태 전이가 원문에 근거해 기록 |
| S4 계산 연결 | 엔진이 그 규칙을 실제 계산에 사용 | 효과 phase, 참조 스탯, 공격식 또는 상태 변화가 엔진 지원 범위에 연결 |
| S5 사례 검증 | 대표 입력으로 결과를 검증 | 최소 정상·경계·조건변경 사례가 기대값과 일치 |

`verified`는 S1~S5를 모두 만족할 때만 부여한다. 원문은 확인했지만 엔진이 아직 지원하지 않는 경우는 `partial`이며, 미지원 이유를 남긴다.

## 3. 필수 검증 항목

### 3.1 공통 식별·제한

1. 스킬 ID, 이름, 스킬트리, 습득 레벨/계열을 카탈로그와 원문에 대조한다.
2. 패시브/공격/버프/유틸리티 및 콤보 시동 가능 여부를 확인한다.
3. 무기·서브 장비·대상 상태·거리·파티/본인 범위·선행 버프 조건을 기록한다.
4. MP/HP 소비, 쿨다운, 지속시간, 재사용 불가 조건을 분리해 기록한다.

### 3.2 패시브

1. 적용 시점: 순수 스탯, 장비 반영 후 스탯, 전투 시점, 공격/명중 후 중 어디인지 정한다.
2. 고정 수치, %, 최종 배율을 구분한다.
3. 무기 보정과 다른 패시브·버프와의 합/곱/상한 규칙을 기록한다.
4. 계산기에 적용되지 않는 효과는 효과명과 미지원 사유를 남긴다.

### 3.3 공격 스킬

1. 타격마다 피해 유형, 타수, 계수, 상수, 속성, 거리/발도/크리티컬 규칙을 분리한다.
2. 기본 스탯·총 스탯·최종 전투 스탯 중 어떤 값을 참조하는지 명시한다.
3. 조건부 강화, 후속타, 추격타, 확정 크리티컬, 방어력/내성/관통 예외를 각각 기록한다.
4. 시전 후 얻는 버프와 공격 자체의 피해 계산을 혼동하지 않는다.

### 3.4 버프·상태·스택

1. 활성화 방식: 단순 ON/OFF, 지속시간형, 재시전 갱신형, ON/OFF 양방향형, 전투 자원형으로 구분한다.
2. 초기 스택, 증감 계기, 최대치, 소모 계기, 종료·초기화 조건을 모두 기록한다.
3. 효과별 스택 상한이 서로 다르면 각각 기록한다. UI 최대치와 효과 최대치를 하나의 숫자로 합치지 않는다.
4. 스택 최대치가 없거나 HP/시간 등으로 종료되면 임의의 UI 상한을 두지 않는다.
5. 버프 ON/OFF 상태에 따라 효과가 달라지는 경우에는 각 상태의 효과를 분리한다. 현재 UI가 표현하지 못하면 `partial`로 남긴다.

### 3.5 콤보·자원 상호작용

1. 기본 MP 비용과 콤보 태그 적용 뒤 비용을 분리한다.
2. 충전·강타·연속공격 등 콤보 태그로 달라지는 피해, 자원, 후속 스킬 규칙을 기록한다.
3. 스킬이 스택·MP·HP를 생성/소비하여 다음 스킬에 영향을 주면 `stateTransitions`로 표현하거나 엔진 미지원으로 표시한다.

## 4. 데이터와 UI의 경계

- 데이터 정의는 게임 규칙의 원본이다. UI는 이를 표시·입력하는 수단일 뿐이다.
- UI가 표현할 수 없다는 이유로 원문 규칙을 단순화하거나 다른 규칙으로 바꾸지 않는다.
- UI가 아직 없는 상태 모델은 `stackModel` 또는 `stateModel`에 규칙과 한계를 기록하고, 계산 반영 여부를 `partial`로 표시한다.
- 스킬별 입력값은 공격 선택·콤보·버프 탭 중 어느 탭이 소유하는지 명시한다. 같은 상태를 여러 탭에서 별도로 저장하지 않는다.

## 5. 스킬트리 완료 판정

스킬트리를 완료하려면 아래를 전부 만족해야 한다.

1. 트리의 모든 스킬이 S1 이상이며, 출처 anchor 대조 자동 검증을 통과한다.
2. 모든 패시브·버프·공격 스킬의 S2 분류가 완료된다.
3. 계산 대상 효과는 S3 이상이고, 미지원 효과는 이유와 후속 작업 위치가 남아 있다.
4. 현재 엔진에서 계산 가능한 규칙은 S4 이상이다.
5. 트리 대표 사례에 정상·최대 레벨·경계값·무기/상태 조건변경 사례가 각각 포함되어 S5를 통과한다.
6. `verified`와 `partial`의 목록 및 남은 항목이 트리 검증 기록에 남아 있다.

## 6. 작업 순서

1. 원문을 읽고 스킬 목록·분류·출처 anchor만 먼저 확정한다.
2. 패시브 → 단순 버프 → 단순 공격 → 조건부 공격 → 스택/상태 → 콤보 의존 규칙 순서로 데이터화한다.
3. 각 단계마다 원문 대조 도구와 구문 검사를 실행한다.
4. 마지막에 대표 사례를 작성하고 계산 결과를 검증한다.
5. 한 스킬트리에서 발견한 공통 엔진 부족분은 별도 엔진 작업으로 분리하며, 다른 트리 데이터를 추정으로 채우지 않는다.

## 7. 현재 자동 검증 범위

`node tools/audit-stack-source-links.mjs`는 원문 캐시 해시, 모든 상세 정의의 `sourceRef`/원문 anchor, 정해진 스택 상한, 그리고 카탈로그 전체의 S1 출처 연결 범위를 검사·표시한다. 기본 실행은 미완료 목록을 보고하되 작업 중인 부분 정의를 막지 않는다. `--tree <TreeId>`로 한 스킬트리만 점검하고, `--require-s1`을 함께 주면 해당 범위에 S0 또는 sourceRef 누락이 하나라도 있을 때 실패한다. S2~S5 자동 점검은 이후 확장한다.
