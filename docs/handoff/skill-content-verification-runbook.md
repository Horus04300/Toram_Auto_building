# 스킬 내용 검증 실행 런북

> 함께 읽을 문서: `docs/handoff/skill-content-coverage-handoff.md`  
> 이 문서는 다음 작업자가 스킬 누락 검증을 **어떤 순서와 절차로 진행할지** 정한다.

## 0. 작업 원칙

1. 한 번에 **스킬트리 하나만** 다룬다. 다음 트리로 넘어가기 전에 데이터 반영, 감사, 검증 기록을 끝낸다.
2. 스킬트리 전체 작업은 두 종류의 완료를 구별한다.
   - **S1 완결:** 모든 카탈로그 스킬에 원문 출처가 연결됨.
   - **계산 완결(S2~S5):** 유형·조건·수식·엔진·사례까지 끝남.
3. “원문에 있다”와 “계산기에 적용된다”는 별개다. 전투 상태 엔진이 없으면 원문 규칙을 데이터/메타데이터로 보존하고 `partial`로 남긴다.
4. 원문을 읽지 않은 수치·상한·조건을 다른 스킬에서 유추해 넣지 않는다.
5. S1 완결 전에는 “해당 트리 검증 완료”라고 표현하지 않는다.

## 1. 권장 검증 순서

원래의 검증 흐름은 아래 순서였다.

1. Blade
2. Shot
3. Magic
4. Martial
5. Halberd
6. Mononofu
7. DualSword
8. Crusher

다만 실제 S1 완결 여부를 새 감사 도구로 다시 확인한 결과, 위 트리들은 모두 일부만 출처 연결된 상태다. 따라서 다음 순서로 **재개**한다.

1. **Martial** — 화경(`Martial:18`) 누락이 사용자에게 직접 발견되었고, 파괴자와의 무기 ATK% 합산 상한이라는 공통 설계 문제가 있다.
2. **Blade** — 현재 9/24 S1, 미완료 15개가 명확히 확인됐다. 이미 일부 공격/버프 데이터가 있어 재검증 시 상호작용 오류를 찾기 좋다.
3. **Shot** — 크로스 파이어/퀵 로더의 상태 전이와 공격 스킬이 연계된다.
4. **Magic** — 차징·맥시마이저·체인 캐스트·버스트의 MP/영창 상호작용을 별도 상태 모델로 설계해야 한다.
5. **Halberd** — 토네이도 랜스, 신의 창솜씨, 신속의 수도의 피격·스택 상호작용을 함께 대조한다.
6. **Mononofu** — 천류난성·화룡점정·불요불굴처럼 장기 스택/공격 상태가 많다.
7. **DualSword** — 세이버 오라↔아크 세이버 전환 및 스택 소모를 검증한다.
8. **Crusher** — 갓 핸드·골리아·호흡법의 피해 감소 성공/충전/쿨다운 상태를 묶는다.

이 순서는 “바로 계산 가능한 단순 패시브/버프 → 상태·콤보 의존 규칙”의 흐름을 유지하면서, 이미 발견된 누락을 먼저 해소한다. 다른 트리도 같은 절차로 추가한다.

## 2. 트리 하나를 처리하는 표준 절차

### 단계 A — 시작 전 현황 고정

```powershell
node tools/audit-stack-source-links.mjs --tree Martial
```

- 출력의 `S1 출처 연결 범위`를 검증 기록 첫머리에 적는다.
- `S1 미완료` 목록을 복사해 해당 트리의 작업 목록으로 삼는다.
- 이전 상세 정의와 `docs/verification/<TreeId>.md`를 읽어 이미 반영한 항목과 보류 이유를 확인한다.

### 단계 B — 원문과 카탈로그를 함께 읽기

다음 세 가지를 대조한다.

- `docs/sources/skills/<TreeId>.txt`: 수치와 원문 문구의 기준
- `assets/js/data/skill-tree-data.js`: 스킬 ID·한국어 이름·습득 순서
- `assets/js/data/skill-combat-catalog.js`: 계산 카탈로그 ID

원문 캐시는 수집된 본문이라 줄바꿈이 적거나 길 수 있다. 스킬 이름/`패시브`/`버프`/`마나 소모` 등으로 검색해 전후 문맥을 확인한다.

### 단계 C — 우선 S1/S2 뼈대 완결

한 트리의 모든 카탈로그 스킬에 대해 아래를 먼저 만든다.

- `id`, `treeId`, `skillId`, `nameKo`
- `sourceRef.file`, `sourceRef.anchor`
- `kind`: `passive`, `buff`, `attack`, `utility` 등
- 무기/서브장비/대상 조건이 있으면 `requirements.when`
- 아직 계산식이 복잡하면 `dataStatus: 'partial'` 및 `notes`/검증 문서에 보류 사유

이 단계에서는 정확한 공격식을 아직 구현하지 못해도 된다. 하지만 `sourceRef.anchor`는 반드시 원문에 실제로 있는 식별 문구여야 한다. 단순한 “스킬명”보다 `화경 버프 / 권갑 전용`처럼 종류와 조건이 포함된 문구가 좋다.

모든 스킬을 S1로 연결한 뒤 반드시 실행한다.

```powershell
node tools/audit-stack-source-links.mjs --tree <TreeId> --require-s1
```

이 명령이 통과해야 **그 트리의 원문 출처 연결(S1) 완결**이다. 통과 전에는 다음 트리로 넘어가지 않는다.

### 단계 D — S3 데이터화 순서

S1/S2가 끝난 뒤에는 아래 순서로 상세 구현한다.

1. 패시브: 고정 스탯, %, 적용 시점, 무기/서브 조건
2. 단순 버프: 비용, 지속시간, ON/OFF, 정적 효과
3. 단순 공격: 비용, 타수, 계수, 상수, 피해 유형, 거리/발도/치명 조건
4. 조건부 공격: 대상 상태, 거리, 기본/총 스탯, 후속타
5. 스택·상태: 초기/최대/증감/소모/종료/갱신
6. 콤보·자원: 기본 MP와 콤보 태그 후 MP, 다음 스킬 1회 효과, 충전/강타 등

이 순서를 지키는 이유는 뒤 단계가 앞 단계의 장비·스탯·공격·상태 모델을 참조하기 때문이다.

### 단계 E — 엔진 연결 및 사례 검증

- 새 데이터 파일은 `index.html`의 스크립트 로드 목록에 추가한다.
- 새 데이터 파일은 `tools/audit-stack-source-links.mjs`의 로드 목록에도 추가한다. 그렇지 않으면 감사가 해당 정의를 보지 못한다.
- 최소 사례 3종을 Node VM으로 검증한다.
  1. 정상값: 대표 무기/레벨/스택
  2. 경계값: 최대 레벨·최대 스택·지속시간 경계 등
  3. 조건 변경: 다른 무기, 서브장비 장착, 버프 OFF, 대상 상태 없음 등
- 구문 검사와 감사도 실행한다.

```powershell
node --check assets/js/data/skills/<tree>.js
node tools/audit-stack-source-links.mjs --tree <TreeId>
git diff --check
```

S4/S5로 올릴 수 없는 규칙은 실패로 숨기지 말고, 현재 엔진이 왜 지원하지 못하는지 기록한다.

### 단계 F — 검증 기록 갱신

`docs/verification/<TreeId>.md`에 반드시 남긴다.

- 검증일, 원문 SHA-256, 카탈로그 총 수
- S0~S5 개수
- 상세 대조 표: ID, 원문상 반영 결과, 남은 항목
- S0/S1 미완료 목록
- 이번에 발견·수정한 오류
- 실제 실행한 사례와 기대값
- 다음 단계

기존 기록의 “반영 완료” 문구가 트리 전체 완료처럼 읽히지 않는지 확인한다.

## 3. 화경(Martial:18) 처리 체크리스트

다음 작업자는 Martial의 첫 작업으로 화경을 등록한다.

### 원문상 핵심 규칙

- 권갑 전용, MP 100, 행동 속도 영향 없음
- 모션 중 받은 피해를 0으로 함
- 피해 감소 성공 시 화경 버프 + 차크라 버프 획득
- 차크라의 즉시 MP 회복은 발생하지 않음
- 차크라 버프는 자신에게만 적용, 다단히트로 맞으면 즉시 종료
- 화경/차크라 중 낮은 레벨을 따라 차크라 버프가 발동
- 화경 지속시간: Lv.1 30초, Lv.5 45초, Lv.10 90초만 원문 명시
- 화경 효과: 안정률 +10%; 메인 권갑이면 무기 ATK `+5 × 레벨%`
- 화경과 크러셔 파괴자의 무기 ATK 증가는 합산 최대 50%

### 구현 방침

- `sourceRef`: `docs/sources/skills/Martial.txt`, anchor `화경 버프 / 권갑 전용`
- 피해 감소 성공은 `stateTransitions` 이벤트로 기록한다. 지금 엔진에 실제 피해 차단 이벤트가 없으므로 자동 적용됐다고 주장하지 않는다.
- 화경 버프와 차크라 버프를 별도 `stateId`로 표현한다.
- 파괴자(`Crusher:8`)와 화경의 WATKP 상한은 두 버프를 함께 해석하는 공통 상태/효과 상한 설계가 필요하다. 한 스킬 데이터에 임의로 50% clamp를 넣지 않는다.
- 원문이 레벨 1/5/10만 명시한 지속시간의 중간 레벨은 추정하지 말고 `unknown`/`notModeled`로 남긴다. 필요하면 UI는 해당 세 레벨만 정확함을 표시한다.

## 4. 현재 데이터 구조에서 특히 조심할 점

### 스킬 조건

- 메인/서브 장비 값은 한국어 문자열이다.
- 예: 듀얼소드는 `mainWeapon === '한손검'` 및 `subWeapon === '한손검(듀얼소드)'` 모두 필요하다.
- 양손쥐기처럼 보조 없음이 필요한 규칙은 `subWeapon === '없음'`을 조건으로 둔다.
- 패시브 엔진은 이제 스킬의 `requirements.when`을 검사한다. 조건을 `effects.when`에만 숨기지 말고, 스킬 전체 적용 조건이면 `requirements`에도 기록한다.

### 스탯 키

현재 계산기에서 자주 쓰는 키:

- 무기 ATK%: `WATKP`
- ATK%: `ATKP`
- MATK%: `MATKP`
- 고정 ATK/MATK: `ATK`, `MATK`
- CRIT, CDMG, ASPD, MOTIONSPEED, STABILITY, UNSHEATHE, PHYS_PIERCE, MAG_PIERCE

새 키가 실제 결과 계산기에 합산되는지 `assets/js/calculator.js`의 `applyStat()`도 확인한다. 엔진이 효과를 반환하더라도 계산기 본체가 그 키를 해석하지 않을 수 있다. 이 경우 S4가 아니라 `partial`이다.

### 액티브 버프 UI

- 구현: `assets/js/active-buff-ui.js`
- 습득 레벨이 1 이상인 `kind: 'buff'`가 대상이다.
- 기본 상태는 OFF.
- 유한 스택은 `stackControl`이 있으면 카드 하단 `(-) (n/m) (+)`으로 표시된다.
- UI가 스택을 보이는 것과 전투 중 자동 증감은 별개다.
- OFF 상태에서도 스택을 보존해야 하는 예외(아수라 오라)는 `persistWhenDisabled`, `showWhenDisabled`, `applyWhenDisabled`를 사용한다.

### 공격/콤보 엔진의 한계

아직 완결되지 않은 대표 영역:

- 시간 경과, 피격, 피해 감소 성공, 통상 공격, 대상 사망 등 실시간 전투 이벤트
- 다음 스킬 1회 효과/소비
- 콤보 태그와 상태 전이의 실제 순서
- 대상 상태이상 저항 시간
- 복수 버프의 공통 상한/합산 규칙

이 항목들은 데이터에 기록하고 검증 문서에 미지원 이유를 명시한다. UI 수동 토글/스택 입력만으로 자동 전이가 구현됐다고 간주하지 않는다.

## 5. 작업 단위와 대화 관리

- 정확도를 우선하면 **대화/컨텍스트 하나당 스킬트리 하나**가 적절하다.
- 원문이 길고 상태 규칙이 많은 Martial, Mononofu, DualSword은 한 트리 안에서도 “S1/S2 전체 연결”과 “S3~S5 상세 구현”을 별도 대화로 나눠도 된다.
- 긴 원문을 보고 즉시 많은 수식을 한 번에 넣지 않는다. 먼저 출처 연결 목록을 만든 뒤, 3~5개 스킬 묶음으로 구현·테스트한다.
- 각 묶음 종료 시에는 원문 anchor 감사와 조건 변경 테스트를 실행한다.

## 6. 다음 AI에게 권장하는 첫 메시지/첫 명령

첫 작업은 Martial의 S1 누락을 정리하는 것이다.

```powershell
Set-Location 'C:\Users\조연우\Documents\GitHub\Toram_Auto_building\Toram_Auto_building'
node tools/audit-stack-source-links.mjs --tree Martial
Get-Content docs/sources/skills/Martial.txt -Raw
Get-Content docs/verification/Martial.md -Raw
```

그 다음 화경부터 등록하되, 바로 모든 수식을 구현하려 하지 말고 우선 `Martial:0`~`Martial:21`의 S1/S2 목록을 완결한다. 완료 전 최종 확인 명령은 다음과 같다.

```powershell
node tools/audit-stack-source-links.mjs --tree Martial --require-s1
```

이 명령이 통과한 뒤에야 마셜의 “원문 출처 연결 완료”라고 보고할 수 있다.
