# D4 전역 크리스타 최적화 — 탐색 공간 사전 축소 전략 분석

## 1. 문제 재정의

현재 D4의 원래 목표는 무기·몸장비·추가장비·특수장비의 총 8개 크리스타 슬롯을 독립적으로 추천하지 않고, 하나의 전역 조합 문제로 계산하여 **실제 최적 조합임이 증명된 exact 결과를 10초 안에 반환하는 것**이다. 기존 구조는 후보 컴파일 → Pareto → 실제 조합 하한 → 안전한 상한 → Branch-and-Bound의 흐름을 사용한다.

최종 강화 크리스타만 기준으로 단순 계산한 원시 탐색 공간은 다음과 같다.

- 무기: 90개 → `C(90,2) = 4,005`
- 몸장비: 81개 → `C(81,2) = 3,240`
- 추가장비: 88개 → `C(88,2) = 3,828`
- 특수장비: 86개 → `C(86,2) = 3,655`

따라서 전체 경우의 수는 약 **181조 5,517억 개​**이다.

하지만 실제 사람이 빌드를 구성할 때는 80~90개의 크리스타를 전부 비교하지 않는다. 현재 공격 계열과 관계없는 크리스타, 명백한 하위호환, 필요한 Utility에 기여하지 않는 후보, 조건이 맞지 않는 후보 등을 먼저 제외한 뒤 실제 경쟁력이 있는 소수 후보만 비교한다.

따라서 D4의 문제를 다음과 같이 다시 정의할 필요가 있다.

> **181조 개의 조합을 빠르게 탐색하는 것이 아니라, 181조라는 탐색 공간 자체가 생성되지 않도록 입력 후보를 증명 가능한 방식으로 축소한다.**

현재 문서의 Utility dependency 및 residual dominance 분석은 이러한 사전 제거에 사용할 기반을 이미 일부 갖추고 있지만 실제 후보 삭제에는 적극적으로 연결되지 않았다.

# 2. 기존 방식의 핵심 한계

현재 B&B 자체는 exact 최적화를 위한 알고리즘으로 잘못된 선택은 아니다. 문제는 **너무 많은 후보를 유지한 상태에서 후단의 B&B와 Bound가 문제를 해결하도록 맡기고 있다는 것**이다.

현재 구조는 대략 다음과 같다.

```text
많은 후보 유지
    ↓
Pareto
    ↓
Pair / Envelope
    ↓
Branch-and-Bound
    ↓
가지치기
```

문서에서도 현재 상한은 서로 다른 후보의 ATK%, CRIT, 거리 위력 등의 최댓값을 하나의 가상 후보처럼 결합하기 때문에 실제 후보 간 상관관계를 잃고, 그 결과 Upper Bound가 과대평가되어 gap이 크게 남는다고 분석한다.

Pair를 이용해 상관관계를 보존하려는 시도 역시 전체 Pair 물질화는 시간·메모리 비용이 지나치게 컸고, root-only envelope은 분기 이후 상관관계가 다시 사라졌다.

따라서 앞으로는 다음 구조가 더 적절하다.

```text
Raw Candidate
    ↓
Problem Reduction
    ↓
실제로 경쟁 가능한 후보
    ↓
Pareto / State Compression
    ↓
Branch-and-Bound
    ↓
Exact 인증
```

즉 **더 좋은 탐색기 이전에 더 작은 문제를 만들어야 한다.**

# 3. 사전 후보 제거 전략

## 3.1 Scenario Dependency Pruning

가장 먼저 현재 Build와 Scenario에서 실제로 사용되는 스탯을 결정한다.

예를 들어 물리 근거리 공격이라면 다음과 같이 판단할 수 있다.

```text
현재 Scenario
│
├─ DPS Dependency
│   ├─ ATK
│   ├─ 물리 관통
│   ├─ 근거리 위력
│   ├─ CRIT
│   ├─ CDMG
│   └─ 해당 스킬 특수 계수
│
├─ Utility Dependency
│   ├─ MAXHP
│   ├─ MAXMP
│   ├─ AMPR
│   ├─ ASPD
│   └─ 평타 CRIT
│
└─ Structural Dependency
    ├─ 강화 계보
    ├─ 중복 제한
    └─ 조건부 효과
```

현재 Scenario에서 후보의 모든 효과가 DPS·Utility·조건·구조 어디에도 영향을 미치지 않는다면 **provably irrelevant candidate**로 제거할 수 있다.

예:

```text
물리 근거리 Scenario

후보 A
MATK +10%
마법관통 +5%
마법위력 +3%

→ DPS 기여 없음
→ Utility 기여 없음
→ 구조적 의미 없음

SAFE DROP
```

다만 크리스타 이름이나 “마법계열” 같은 분류만으로 삭제해서는 안 된다.

```text
MATK +10%
CRIT +14
```

처럼 물리 공격에는 MATK가 무관하더라도 CRIT 때문에 후보가 필요할 수 있기 때문이다.

따라서 판단 기준은 **계열 이름이 아니라 evaluator dependency**여야 한다.

---

## 3.2 Scenario Projection

서로 다른 공격 계열 옵션이 한 크리스타에 동시에 존재하는 경우는 단순 제거해서는 안 된다.

예:

```text
ATK +10%
MATK +10%
```

물리 빌드에서는 다음과 같이 투영한다.

```text
원본
[ATK +10, MATK +10]

물리 Scenario Projection
[ATK +10]
```

또는:

```text
근거리 위력 +8%
원거리 위력 +8%
```

근거리 Scenario에서는

```text
[근거리 위력 +8]
```

로 평가한다.

즉 **무관한 옵션 축을 후보 전체와 함께 제거하는 것이 아니라, 현재 Scenario에서 의미 없는 좌표만 제거한 표현으로 후보를 비교한다.**

이후 투영된 후보가 다른 후보에게 완전히 지배된다면 삭제할 수 있다.

---

## 3.3 Structural Feasibility Propagation

개별적으로 합법적인 후보라도 최종 완성 조합에는 절대로 포함될 수 없는 경우가 존재할 수 있다.

예:

```text
후보 X 선택
   ↓
계보 제한 적용
   ↓
다른 슬롯 후보 감소
   ↓
중복 제한 적용
   ↓
특정 슬롯 후보 0개
```

이 경우 X는 단독으로는 유효하지만 전역적으로는 완성 가능한 빌드를 만들 수 없다.

따라서 compiler 단계에서 다음을 검사할 수 있다.

> **후보 X가 최소 하나 이상의 완성 가능한 조합에 포함될 수 있는가?**

불가능하면 탐색 전에 제거한다.

이는 CSP의 constraint propagation / arc consistency와 유사한 접근이다.

---

## 3.4 Strict Dominance

현재 Scenario에서 두 후보 A와 B가 동일한 구조적 조건을 갖고 있고,

```text
A ≥ B
```

가 모든 유효 DPS 및 Utility 좌표에서 성립하며 하나 이상에서 엄격하게 크다면 B는 최적해가 될 수 없다.

예:

```text
A
ATK +12
CRIT +14

B
ATK +10
CRIT +14
```

다른 조건이 동일하다면 B는 제거 가능하다.

반면

```text
A
ATK +12
CRIT +10

B
ATK +10
CRIT +14
```

는 단순 비교할 수 없다.

B가 추가로 제공하는 CRIT 4가 필요한 상황이 존재할 수 있기 때문이다.

여기서 **Utility의 기회비용** 개념이 필요해진다.

# 4. Utility Opportunity Cost

## 4.1 문제

기존 방식에서는 Utility에 조금이라도 기여하는 후보를 쉽게 제거할 수 없다.

예를 들어 물리 빌드에서:

```text
A
MATK +10
CRIT +14

B
ATK +10
CRIT +10
```

A는 공격 계열상 명백하게 불리하지만 CRIT +14 때문에 살아남을 수 있다.

그러나 실제 판단은 단순히

> A가 CRIT를 가지고 있는가?

가 아니라

> **추가 CRIT 4를 얻기 위해 ATK +10을 포기할 가치가 있는가?**

가 되어야 한다.

이를 **Utility Opportunity Cost**로 볼 수 있다.

---

## 4.2 Utility와 DPS의 가치 구조 차이

DPS 계열과 Utility 계열은 동일한 방식으로 비교할 수 없다.

예:

```text
CRIT +14 vs CRIT +10
```

과

```text
ATK +12% vs ATK +10%
```

의 차이는 의미가 다르다.

예를 들어 필요한 CRIT가 100이고 현재 CRIT가 96이라면:

```text
CRIT +10 → 106
CRIT +14 → 110
```

둘 다 constraint를 만족한다.

따라서 추가 +4 CRIT의 가치가 사실상 매우 작을 수 있다.

반면:

```text
ATK +10%
ATK +12%
```

은 목표값을 넘으면 효용이 사라지는 hard constraint가 아니라 DPS에 계속 영향을 준다.

따라서 +2% 차이가 계속 최종 결과에 반영된다.

즉 Utility는 대부분 다음과 같은 **잔여 요구량(residual requirement)** 관점으로 평가해야 한다.

```text
Utility Effective Value
= min(후보 Utility,
      현재 남은 Utility 요구량)
```

단, MAXMP→AMPR 등 Utility 원값이 다른 계산에 다시 사용되는 경우에는 단순 cap 처리를 해서는 안 된다. 문서 역시 MAXMP·AMPR·CRIT 등의 raw value 보존 필요성을 명시한다.

---

## 4.3 Utility Supply Frontier

각 Utility를 얻기 위해 어떤 DPS 손실을 감수해야 하는지를 미리 계산할 수 있다.

예를 들어 CRIT에 대해:

```text
CRIT Supply Frontier

CRIT +10
→ DPS 손실 0.5%

CRIT +14
→ DPS 손실 0.7%

CRIT +20
→ DPS 손실 4.8%

CRIT +25
→ DPS 손실 9.2%
```

처럼 표현할 수 있다.

그러면 물리 빌드에서:

```text
MATK +10
CRIT +14
```

라는 후보가 있더라도 동일하거나 비슷한 CRIT를 훨씬 낮은 DPS 비용으로 얻을 수 있는 물리계열 후보가 있다면 해당 후보를 유지할 이유가 줄어든다.

따라서 후보 비교는 다음 형태가 된다.

```text
Candidate
│
├─ 현재 Scenario DPS 기여
├─ Utility 공급량
├─ 동일 Utility의 대체 공급원
└─ Utility 확보에 따른 DPS Opportunity Cost
```

---

# 5. Utility를 먼저 채우는 방식

사용자 제안의 핵심은 다음과 같다.

> **Utility를 충족시키는 후보들을 먼저 고려하고, 필요한 Utility가 충족된 이후에는 Utility 때문에 살아남았던 타 공격계열 후보를 제거한다.**

이는 매우 유망하지만 Utility 조합을 하나로 확정해서는 안 된다.

예:

```text
목표 Utility = 100

A
Utility 100
DPS 0

B
Utility 60
DPS 80

C
Utility 40
DPS 80
```

Utility만 먼저 최적화하여 A를 선택하면:

```text
A = Utility 100 / DPS 0
```

이 되지만 실제 최적은:

```text
B + C
Utility 100
DPS 160
```

일 수 있다.

따라서 **Utility를 먼저 채운다는 것은 하나의 Utility 조합을 선택한다는 뜻이 아니다.**

다음과 같은 Frontier를 유지해야 한다.

```text
Utility 충족량
×
DPS 기여
×
슬롯 비용
×
구조적 조건
```

그 위에서 지배되는 Utility 공급 방식만 제거한다.

---

# 6. Residual Utility Pruning

Utility 목표가 충족되고 나면 후보의 가치가 변한다.

예:

```text
현재 CRIT 부족량 = 14

후보 A
MATK +10
CRIT +14

후보 B
ATK +10
CRIT +10
```

초기에는 A가 CRIT 때문에 필요할 수 있다.

그러나 다른 슬롯에서 CRIT가 이미 확보되어:

```text
Residual CRIT = 0
```

이 되면 A는:

```text
MATK +10
```

만 남는다.

물리 Scenario에서 MATK가 아무 효과도 없다면 A는 그 branch에서 제거할 수 있다.

즉 후보의 유효성은 고정되어 있지 않고:

```text
Candidate relevance
=
f(Scenario, Residual Utility State)
```

로 보는 것이 적절하다.

이 방식은 특히 다음과 같은 후보 제거에 강하다.

```text
물리 공격
+ 마법 공격 옵션
+ 필요한 Utility

마법 공격
+ 물리 공격 옵션
+ 필요한 Utility

근거리 공격
+ 원거리 옵션
+ 필요한 Utility

원거리 공격
+ 근거리 옵션
+ 필요한 Utility
```

Utility가 이미 다른 곳에서 충족되면 해당 후보가 가지고 있던 **유일한 생존 이유가 사라진다.**

---

# 7. Residual Feasibility Pruning

반대 방향도 가능하다.

후보 X를 선택했을 때 남은 슬롯을 모두 최고의 Utility 후보로 채워도 hard constraint를 만족할 수 없다면 X는 제거할 수 있다.

예:

```text
CRIT 목표 = 100

X 선택 후 현재 CRIT = 20

남은 슬롯 최대 가능 CRIT
= 20 + 25 + 30
= 75

20 + 75 = 95 < 100
```

따라서:

```text
X를 포함하는 완성 조합
→ 전부 infeasible
```

이고 X 자체를 사전 제거할 수 있다.

이것은 수많은 완성 조합을 실제 생성하지 않고도 **하나의 후보 수준에서 전역 불가능성을 증명하는 방법**이다.

---

# 8. Impossible Condition Elimination

현재 Scenario에서 절대로 발동하지 않는 조건부 효과를 사전에 제거할 수 있다.

예:

```text
원거리 공격 시 +10%
```

인데 현재 공격이 확정적으로 근거리라면 해당 효과는 0으로 투영한다.

또는 특정 스킬·무기·상태 조건이 현재 Scenario에서는 절대로 성립할 수 없다면 해당 조건부 효과 역시 제거한다.

그 결과:

```text
원래 후보
원거리 위력 +10
CRIT +5

↓

근거리 Scenario
CRIT +5
```

가 된다.

이렇게 축소된 후보가 다른 `CRIT +10` 후보 등에 지배된다면 전체 후보를 삭제할 수 있다.

---

# 9. Semantic Equivalence

현재 Scenario에서 서로 다른 크리스타가 evaluator 관점에서는 완전히 동일해질 수 있다.

예:

```text
A
ATK +10
MATK +10

B
ATK +10
원거리 +5
```

현재 Scenario가 물리 근거리이고 MATK와 원거리가 모두 무관하다면:

```text
Projection(A) = ATK +10
Projection(B) = ATK +10
```

이 된다.

다만 계보·중복·충돌·동점 ID 규칙이 서로 다를 수 있으므로 단순 병합은 위험하다.

따라서:

```text
Evaluator equivalence
+
Structural equivalence
+
Tie-break equivalence
```

까지 증명되는 경우에만 병합한다.

그렇지 않은 경우에도 동일 성능 그룹으로 묶어서 후속 계산 비용을 줄이는 방법은 검토할 수 있다.

---

# 10. Candidate-Level Upper Bound

기존 B&B의 가지치기를 후보 수준까지 끌어올릴 수 있다.

좋은 실제 조합을 heuristic으로 먼저 찾아:

```text
현재 최고 실제 점수
LB = 1,000
```

을 확보했다고 하자.

후보 X를 반드시 사용한다고 가정한 상태에서 나머지 모든 슬롯에 이상적인 상한을 적용해도:

```text
UB(X) = 950
```

이라면:

```text
UB(X) < LB
```

이므로 X를 포함하는 어떤 조합도 최적해가 될 수 없다.

따라서 X 자체를 삭제할 수 있다.

```text
후보 X
│
└─ X를 포함하는 최고 이론 조합
       UB = 950
          ↓
현재 실제 최고 조합
       LB = 1000

950 < 1000
→ X 전체 제거
```

이 방식은 기존 문서의:

> 실제 완성 조합으로 하한을 만들고 안전한 상한으로 가지치기한다.

라는 B&B 원리를 후보 단계까지 앞당긴 것이다.

# 12. 기대 효과

후보 수 감소는 조합 수에 비선형적으로 영향을 준다.

무기의 경우:

```text
90 candidates
C(90,2)
= 4,005
```

가령 전처리 후:

```text
20 candidates
C(20,2)
= 190
```

이면 단일 부위만 약 21배 감소한다.

만약 네 부위가 모두 대략 20개 수준까지 감소한다고 단순 가정하면:

```text
190⁴
≈ 1,303,210,000
```

즉 약 **13억 경우**이다.

기존:

```text
181,551,770,868,000
```

과 비교하면 raw 조합 공간 자체가 약 **14만 배** 작아진다.

물론 실제로 네 부위가 모두 20개까지 줄어든다는 보장은 없으며, 이 숫자는 효과 크기를 설명하기 위한 예시이다.

중요한 점은 이후에도:

```text
구조 제약
Utility feasibility
Dominance
Candidate UB
Pareto
Branch-and-Bound
```

가 추가 적용된다는 것이다.

따라서 실제 평가해야 하는 조합 수는 13억보다 훨씬 작아질 가능성이 있다.

# 13. Exact 보장을 위한 안전 원칙

후보 축소가 강력할수록 잘못 삭제했을 때 exact가 깨지는 위험도 커진다.

따라서 후보 제거 규칙은 반드시 다음 두 종류로 구분해야 한다.

## Proven Drop

수학적·논리적으로 최적해에 포함될 수 없음이 증명된 경우.

```text
[PROVEN DROP]

- Scenario에 완전히 무관
- 완성 조합 생성 불가능
- 다른 후보에게 엄격하게 지배됨
- Utility constraint 충족 불가능
- Candidate UB < incumbent LB
```

이 경우 실제 삭제 가능.

## Heuristic Reject

경험적으로 가치가 매우 낮지만 최적해 가능성을 완전히 배제할 수 없는 경우.

```text
[HEURISTIC]

- 실제 유저들이 거의 사용하지 않음
- 일반적으로 효율이 나쁨
- 메타에서 사용 빈도가 낮음
- 평균 DPS가 낮음
```

이것들은 exact 경로에서 삭제 근거로 사용하면 안 된다.

필요하다면 heuristic 탐색 순서를 정하거나 초기 LB를 빠르게 만드는 용도로만 사용할 수 있다.

# 14. 분석상 가장 중요한 새로운 관점

기존 질문은:

> **181조 개를 어떻게 10초 안에 탐색할 것인가?**

였다.

새로운 질문은:

> **왜 optimizer가 처음부터 181조 개를 가능한 후보 공간으로 인정해야 하는가?**

이다.

사람이 실제 빌드를 구성할 때 이미 하는 판단:

```text
이건 마법용이라 제외
이건 원거리라 제외
이건 같은 CRIT인데 공격력이 낮음
이건 Utility가 이미 충분하니 필요 없음
이건 다른 후보로 Utility를 더 싸게 확보 가능
이걸 끼우면 나머지 슬롯으로 조건을 못 맞춤
```

을 정확성 증명이 가능한 알고리즘으로 옮기면 된다.

따라서 향후 D4의 주요 연구 방향은 **Search Optimization보다 Problem Reduction을 우선하는 것**이 적절하다.

> **최적화해야 할 대상은 181조 개의 탐색 속도가 아니라, 181조라는 탐색 공간이 만들어지는 과정 자체다.**

이 과정을 충분히 수행한 뒤 살아남은 실제 경쟁 후보에 대해서만 기존 Pareto와 Branch-and-Bound를 사용하면, 현재의 exact 철학을 유지하면서도 훨씬 작은 문제를 풀 수 있을 가능성이 있다.
