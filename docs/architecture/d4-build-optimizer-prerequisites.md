# D4 빌드 최적화 구현 선행조건

- 문서 역할: 기능 확장 전의 데이터·정확성 선행조건. 단계별 구현 기록은 작성 당시 정보이며 현재 완료 판정은 `docs/handoff/current-development-handoff.md`를 따른다.
- 기준일: 2026-08-24
- 상위 설계: `docs/architecture/d4-build-optimizer-design.md`

## 1. 목적

이 문서는 D4 전역 빌드 최적화 구현을 시작하거나 기능 범위를 확장하기 전에 반드시 충족해야 하는 조건을 정의한다. 알고리즘 자체의 설명보다 **무엇이 준비되어야 다음 단계로 넘어갈 수 있는지**와 **완료를 어떻게 증명할지**를 기준으로 한다.

D4는 다음 다섯 단계로 나누며, 뒤 단계는 앞 단계의 완료를 전제로 한다.

```text
정확한 평가 기반
  → 크리스타 전역 최적화
    → Utility·고정 장비 선택
      → 완성 커스텀 장비 옵션
        → 잠재력 제약 8옵션 자동 설계
```

## 2. 현재 상태 요약

현행 코드에서 확인된 상태는 다음과 같다.

- 크리스타 후보: 425개
- StatRegistry 감사 범위: 크리스타·스킬 원문 표기 111종, 미등록 키 0개
- 평가기: DOM·localStorage 비의존 BuildEvaluator와 공통 계산 커널 사용
- 크리스타 조건 키: `main`, `sub`, `armor`이며 후보 컴파일 때 사전 해결
- 현재 최적화: 네 장비 8슬롯을 하나의 문제로 계산하는 anytime 전역 탐색
- 고정 장비 카탈로그 후보 선택 모델: 없음
- 유저 제작 장비 옵션 상한·잠재력 비용 레지스트리와 8옵션 frontier: 없음
- 전역 안전 상한·최적성 gap·전수조사 oracle: 구현 완료

아래 53개는 D4 착수 전 기존 `applyStat`이 직접 소비하지 않던 초기 조사 목록이다. 현재는 전부 StatRegistry에서 계산·Utility·보존 전용 중 하나로 분류되며 조용히 소실되지 않는다. 현재 범위 밖 키는 향후 탱커·기타 빌드를 위해 `preservedStats`에 남긴다.

초기 조사 당시 직접 처리되지 않던 키:

```text
ANTICIPATE, AOE_RES, AREA_RES, AROUND_RES, AVOID_RATE, AVOID_RECHARGE,
```

## 3. 공통 필수 선행조건

아래 P01~P09는 크리스타만 대상으로 하는 최초 D4 구현에도 전부 필요하다.

### P01. 전체 StatRegistry

모든 스탯 키를 하나의 레지스트리에 등록한다.

키마다 다음 정보를 가져야 한다.

- 정규 ID와 허용 별칭
- 단위와 고정소수점 배율
- 적용 단계
- 합산 방식: 고정값, %, 최종 배율, Boolean, 조건부
- 반올림 위치
- 최솟값·최댓값 또는 게임 상한
- 계산 결과 경로
- 최적화 역할: 목적함수, hard constraint, Utility, 조건 입력, 표시 전용, 범위 밖
- 현재 지원 상태와 원문 근거

완료 기준:

- 크리스타·장비·스킬 데이터에 등장하는 모든 키가 등록된다.
- 알 수 없는 키가 입력되면 계산을 중단하고 키 이름을 진단한다.
- 등록 키가 조용히 0으로 사라지는 경로가 없다.
- 모든 키가 `calculated`, `utility`, `displayOnly`, `notModeled` 중 하나로 감사된다.

현재 상태: **1차 D4 범위 완료**. `assets/js/stat-registry.js`가 크리스타 87종 키와 스킬 `stat` 효과를 합친 111종 원문 표기를 정규화한다. 대미지·MAXHP·MAXMP·AMPR·ASPD 관련 키는 계산 대상으로 연결하고 나머지는 `preservedStats`에 보존한다. `node tools/audit-d4-stat-registry.mjs` 기준 미등록 키는 0개이며, 알 수 없는 사용자 키는 `UNKNOWN_STAT` 진단으로 최적화를 차단한다.

1차 D4에서는 대미지, MAXHP, MAXMP, AMPR, ASPD를 계산·제약 축으로 사용한다. 드롭률·EXP·부활 시간·아이템 쿨타임·어그로·가드·회피·배리어·반사·상태이상/속성/물리/마법/탄환 내성·자연회복·추격/추가타·명중 계열은 최적화 점수와 지배 판정에서 제외한다. 단, 향후 탱커·기타 빌드 최적화를 위해 원시 데이터와 StatRegistry 항목은 삭제하지 않고 `notModeled` 또는 보존 전용으로 유지한다.

### P02. 순수 BuildEvaluator

현재 계산식을 다음 형태의 순수 함수로 분리한다.

```text
evaluate(BuildSnapshot, ScenarioSnapshot) → OutcomeVector
```

필수 조건:

- DOM, localStorage, 전역 UI 상태를 읽지 않는다.
- 입력 객체를 변경하지 않는다.
- 같은 입력은 항상 같은 결과를 반환한다.
- 현재 계산기의 바닥 함수·상한·합산 순서를 그대로 유지한다.
- 현재 세팅과 최적화 후보가 같은 평가 함수를 사용한다.
- Worker로 복사할 수 있는 직렬화 가능 입력과 출력을 사용한다.

완료 기준:

- 평가기 내부 DOM 접근 0건
- 현행 회귀 fixture에서 기존 계산 결과와 일치
- 옵션 적용 순서를 바꾸어도 동일해야 하는 스탯은 동일 결과
- 부동소수점 비교 허용 범위와 정수 반올림 위치가 테스트에 명시됨

현재 상태: **1차 D4 범위 완료**. `assets/js/build-evaluator.js`의 `evaluate(BuildSnapshot, ScenarioSnapshot)`는 DOM·localStorage를 읽지 않고 동결된 복사본을 평가한다. 현재 결과와 기존 부위별 최적화도 같은 평가기와 `ToramCalculationKernel`을 사용한다. 액티브 변환은 UI 캡처 시 직렬화 가능한 스냅샷으로 고정하며, 기존 직접 호출 경로만 호환 처리를 유지한다.

### P03. 완전한 OutcomeVector

평가기 출력은 대미지 하나가 아니라 최적화 가능한 모든 최종 지표를 제공해야 한다.

최소 출력:

- 선택 공격의 기본·발동·기대 대미지
- ATK, MATK, 크리티컬, 크리티컬 대미지, 안정률, 관통
- 평타 최종 크리티컬률(선택 스킬의 확정 크리티컬과 분리)
- MAXHP, 버프 전·후 MAXMP
- AMPR 기본 계산값, 듀얼소드 2배 전·후 값, AMPR%
- ASPD, 최종 행동속도
- CSPD, 최종 시전 감소
- 선택한 Utility에서 사용하는 내성·배리어·기타 지표
- 콤보 MP 충족 여부와 취소 위치
- 활성·비활성 조건 및 미지원 효과 진단

완료 기준:

- 목적함수나 제약에서 선택 가능한 모든 지표가 실제 최종값으로 반환된다.
- 미지원 지표를 선택하면 0으로 계산하지 않고 차단 진단을 반환한다.

현재 상태: **1차 D4 축 완료, 확장 축 부분 구현**. 기본·발동·기대 대미지, 공격 지표, 평타 크리티컬률, MAXHP, MAXMP, 기본/듀얼 전후 AMPR, ASPD·행동속도, CSPD·시전 감소와 hard constraint 위반 목록을 반환한다. 콤보 MP 취소 상세와 향후 탱커용 내성·배리어 Outcome은 다음 단계 이후 확장한다.

### P04. ScenarioSnapshot

최적화 중 변하지 않는 입력을 하나의 스냅샷으로 고정한다.

포함 범위:

- 캐릭터 레벨과 기본 스탯
- 스킬 투자와 활성 버프
- 적용 공격 또는 콤보 타격 프로필
- 대상 레벨, DEF/MDEF, 내성, 크리티컬 저항
- 콤보 MP 흐름과 현재 계산 기준
- 사용자가 선택한 Utility·필수 조건

완료 기준:

- 최적화가 시작된 뒤 UI를 다시 읽지 않는다.
- 스냅샷 해시가 같으면 평가 캐시를 재사용할 수 있다.
- 계산 도중 UI 입력이 바뀌면 기존 작업을 취소하고 새 스냅샷으로 시작한다.

현재 상태: **부분 구현**. DOM 읽기는 최적화 시작 전 `getBaseContext`에 한정되고 이후 `BuildSnapshot`·`ScenarioSnapshot`은 동결·해시된다. 기본 Utility 요구치도 Scenario에 포함된다. 캐시 재사용, 입력 변경 취소, Worker 전송은 전역 탐색 실행 단계에 연결한다.

### P05. 장비 구조 조건의 사전 해결

현재 장비·크리스타 조건은 `main`, `sub`, `armor`처럼 장비 구조가 정해지면 결과가 확정된다. 이 조건은 탐색 중 반복 평가하지 않고 후보 생성 단계에서 해결한다.

필수 처리:

- 주무기·보조무기·방어구 구조별 분기
- 각 후보 조건의 참·거짓을 한 번 평가
- 활성 효과를 일반 `statDelta`에 합산
- 비활성 효과는 계산에서 제외하고 설명 메타데이터에 보존
- 고정된 대상 시나리오에서 관통을 ATK%·MATK% 등가축으로 변환
- 조건 자체를 후보 조합 수에 별도 차원으로 추가하지 않음

완료 기준:

- 탐색기에 전달되는 후보가 이미 최종 옵션 벡터를 가진다.
- 콤보·목적함수 반복문 안에서 장비 조건을 재평가하지 않는다.
- 장비 구조가 달라지면 해당 구조용 후보 벡터를 다시 생성한다.
- 실제 데이터에 없는 동적·순환 조건 엔진을 선행 구현하지 않는다.

**현재 상태:** **크리스타 범위 완료**. `d4-problem-compiler.js`가 현재 `main`·`sub`·`armor` 구조를 한 번 판정하고 활성 옵션을 정규 `statDelta`에 합산한다. 비활성 조건은 설명 메타데이터에 보존하며 탐색 반복문에서는 조건을 다시 평가하지 않는다. 장비 구조 자체를 후보로 바꾸는 기능은 Gate C에서 확장한다.

### P06. 통합 CandidatePackage와 제약 모델

현재 크리스타 배열을 다음 공통 후보 모델로 변환할 수 있어야 한다.

```text
CandidatePackage {
  id,
  slot,
  source,
  structureSignature,
  statDelta,
  resolvedConditionMetadata,
  sockets,
  conflicts,
  resourceCost,
  metadata
}
```

필수 제약:

- 부위별 하나 선택
- 슬롯 수
- 크리스타 카테고리 제한은 절대적으로 적용
  - 무기·방어구·추가·특수 크리스타는 해당 장비에만 장착
  - 공용 크리스타는 슬롯이 있는 네 장비 모두에 장착 가능
- 같은 크리스타는 서로 다른 장비에 반복 장착 가능
  - 공용 크리스타는 최대 네 장비에 하나씩 장착 가능
  - 같은 장비의 두 슬롯에 같은 크리스타를 중복 장착할 수 없음
- 강화 전·후 크리스타는 함께 사용할 수 없음
  - 최적화 후보에서는 하위 크리스타를 제거하고 최종 강화 후보만 남길 수 있음
  - 실제 장착에 선행 크리스타가 필요하다는 제작 절차는 후보 점수 계산에서 다루지 않음
- 여러 갈래 강화가 같은 시작 크리스타에서 분기했다면 서로 배타적
- 장비·크리스타 잠금
- 제외 목록
- 주무기·보조무기 호환
- 장비 구조 호환성과 구조 조건의 사전 해결 여부

완료 기준:

- 현재 수동 장착 조합도 같은 후보 모델로 표현된다.
- 잠금·금지·충돌을 UI가 아니라 solver 입력 제약으로 검증한다.
- 고정 장비·커스텀 장비를 나중에 같은 모델로 추가할 수 있다.

현재 상태: **크리스타 범위 완료**. 네 장비의 2슬롯을 `CandidatePackage`로 컴파일하고 부위 제한, 공용 크리스타의 장비 간 반복, 같은 장비 중복 금지, 하위 강화 제외, 같은 시작점 분기 계보 충돌, 잠금·금지·제외를 solver 입력에서 검증한다. 고정 장비와 커스텀 장비 패키지는 Gate C·D에서 같은 계약으로 확장한다.

### P07. 목적함수·Utility 입력 계약

기본 정책은 다음으로 고정한다.

```text
필수 조건을 만족하는 빌드 중 선택 공격의 기대 대미지 최대화
```

사용자가 입력하지 않은 Utility는 순위에 임의로 반영하지 않는다. 단, 입력이 없을 때 다음 기본 hard constraint를 적용한다.

- 근거리 선택 공격: MAXHP 10,000
- 원거리 선택 공격: MAXHP 요구 없음
- 신속의 수도 Lv.10: 버프 전 MAXMP 2,300, 3중첩 적용 후 2,000
- 그 외: MAXMP 2,000
- AMPR: 맥시마이저 Lv.10이면 듀얼소드 2배 적용 전 0, 그 외에는 듀얼소드 2배 적용 전 100
- 평타 최종 크리티컬률: 100. 선택 스킬이 확정 크리티컬이어도 면제하지 않음
- ASPD: 1,000

명시 입력은 위 기본값을 덮어쓴다. 다음 입력 형식이 필요하다.

- 주 목적 지표
- hard minimum / maximum
- Utility 구간별 가치 곡선
- 균형형 모드 가중치
- Pareto 대안 허용 대미지 손실률

완료 기준:

- 같은 입력은 동일한 스칼라 점수 또는 동일한 Pareto 순서를 만든다.
- 단위가 다른 지표를 원시 수치 그대로 더하지 않는다.
- 어떤 Utility도 사용자 설정 없이 숨은 가중치를 갖지 않는다.
- 현재 D1 기준에 따라 기본 공격 또는 선택 스킬 이름이 목적 시나리오에 명시된다.

현재 상태: **기본 epsilon-constraint 정책 구현**. 기본 hard constraint를 만족하는 기대 대미지 최대화와 결정적 동점 순서를 전역 탐색기가 사용한다. Utility 곡선·균형형 가중치·Pareto 대안 입력 UI는 다음 단계다.

### P08. 전수조사 Oracle과 안전한 상한 검증기

분기 한정법을 구현하기 전에 작은 문제를 완전 탐색하는 기준 구현이 있어야 한다.

필수 테스트:

- 작은 후보 집합의 전수조사 최적값
- 장비 구조 조건이 사전 해결된 옵션 사례
- 음수 옵션과 상한 포함 사례
- 잠금·금지·충돌 사례
- Utility hard constraint 사례
- Pareto 해 집합 사례

안전한 상한은 다음 속성을 항상 만족해야 한다.

```text
모든 부분해 P와 모든 완성해 X에 대해 score(X) ≤ upperBound(P)
```

완료 기준:

- 임의 소형 문제에서 solver 결과가 전수조사와 일치한다.
- property test에서 상한 위반이 0건이다.
- Pareto 축약 전후 전역 최적해가 같다.
- 증명할 수 없는 후보 지배 관계는 가지치기에 사용하지 않는다.

현재 상태: **완료**. `exhaustiveSearch` oracle, 안전한 스탯 구간 상한, 계층형 후보 상자 상한, best-bound 전역 탐색과 strict Pareto 축약을 구현했다. 합성 8슬롯 문제에서 전수조사 3,430개와 같은 해를 찾고, 20개 결정적 무작위 문제에서 solver·oracle·동점 순서가 모두 일치한다. 부분해 상한 감사 1,093건과 계층형 후보 상자 property test의 위반은 0건이다. 실제 425개 제한 시간·Worker 성능 회귀도 연결했다.

같은 스탯을 어디에서 얻을 수 있는지와 그 획득처가 다른 선택과 경쟁하는지를 구조화한다.

```text
SourceProfile {
  sourceId,
  sourceType: base | stat | skill | food | consumable | guild | equipment | crysta,
  competesForSlot,
  slotGroup?,
  resolvedContributions,
  structureConditionMetadata,

```

완료 기준:

- 현재 ScenarioSnapshot에서 명시적으로 활성화된 슬롯 비경쟁 획득량만 후보 탐색 전에 합산한다.
- 요리·도핑·길드 버프·스킬을 자동 적용하는 내장 고정 획득처는 두지 않는다.

- Utility 최소 요구량에서 명시적으로 활성화된 비장비 획득량을 뺀 부족분을 계산한다.
- 물리 대미지 계열별 현재 합산량과 후보의 `DeltaLogDamage`를 계산한다.
- 고정된 대상에서 물리·마법 관통을 ATK%·MATK% 등가축으로 계산한다.
- 부위마다 대미지 계열, Utility 획득량, 구조·충돌 서명을 보존한 frontier를 만든다.
- 집중 획득처 지배와 한계효율 구간 지배를 증명할 수 있다.
- 증명할 수 없는 도이·바쿠잔 같은 교차 후보는 실제 평가 대상으로 보존한다.

필수 회귀:

- 과거 환경을 재현한 합성 fixture에서 발도 18%를 세 번 적용한 뒤 네 번째 18%가 약 11.69% 증가를 만드는 사례. 현행 발도 옵션 수치로 등록하지 않는다.
- ASPD 15~20% 분산과 80% 집중 획득처 비교
- 고정 MAXMP로 요구량을 이미 채운 사례
- 낮은 VIT에서 고정 HP + 대미지 후보와 HP% 후보 비교
- BaseATK 4000·DEF 2000에서 공격축 50%p, ATK 90%p와 거리 위력 40% 적용 뒤 두 축 140%p 비교
- 같은 조건에서 물리관통 10%p를 ATK 5%p 등가로 비교한 뒤 실제 평가기로 재검증

현재 상태: **1차 크리스타 범위 구현**. `d4-source-profile.js`가 활성 입력을 포함한 기본 Outcome에서 Utility 부족분, 로그 한계 대미지, ATK·관통 등가축을 계산한다. 부족분이 안전하게 0인 Utility 축은 지배 판정에서 제외하며, ASPD 집중 획득처, 고정 MAXMP 충족, 과거 발도 18% 네 번째 11.69%, BaseATK 4000·DEF 2000 및 관통 10%=ATK 5%p fixture를 통과했다. 전체 획득처 데이터 확장과 설명 UI는 남아 있다.

## 4. Utility 기능 추가 선행조건

### U01. Utility별 검증된 최종 공식

#### MAXHP

Coryn Club Stat Calculator v4.7의 공개 스크립트에서 다음 기준식을 확인했다.

```text
baseHP = floor((VIT + 22.41) × level / 3 + 93)
percentHP = floor(baseHP × (1 + MAXHP% / 100 + HPBoostLevel × 0.02))
finalHP = min(99,999, percentHP + flatMAXHP + skillFlatHP)
```

공개 스크립트의 `skillFlatHP`에는 HP Boost `100 × 레벨`, Bushido `10 × 레벨`, Frontliner II, 방패 패시브 등이 후단 고정값으로 더해진다. 출처는 `https://coryn.club/stat_calculator.php`와 이 페이지가 불러오는 `stat_calculator_v4_7.js`다. 사용자 확인에 따라 Coryn v4.7의 MAXHP 식과 적용 순서를 D4의 확정 공식으로 사용한다.

#### MAXMP

```text
MAXMP = floor(100 + level + totalINT × 0.1 + fixedMAXMP)
```

신속의 수도 Lv.10을 사용하면 3중첩의 MAXMP -300 이후에도 2,000을 유지하기 위해 버프 전 요구치를 2,300으로 둔다. 그 외 기본 요구치는 2,000이다.

#### AMPR

```text
baseAMPR = floor(10 + MAXMP / 100)
equipmentAMPR = floor(baseAMPR × (100 + AMPR%) / 100) + flatAMPR
```

% 단계가 적용될 때마다 정수 버림한다. 이후 적용 순서는 다음과 같다.

1. 패시브 스킬
2. 버프
3. 통상공격 변화 패시브
4. 통상공격 변화 액티브

통상공격 변화 액티브가 여러 개 활성화되면 서로 합산하지 않는다. 각 액티브를 하나씩 단독 적용해 최종 AMPR을 계산하고 가장 높은 결과를 만드는 하나만 채택한다. 동률은 안정적인 스킬 ID 순서로 표시 대상을 정한다. 통상 공격이 다단이어도 AMPR 회복은 한 번만 발생하며, 듀얼소드의 최종 2배는 후보 선택 뒤 적용한다. 축지법은 무기 사거리 밖에서 통상공격을 시도할 때 평타 1회에만 붙는 돌진용 하프 액티브이므로, 원문 규칙은 보존하되 지속 운용 Utility와 D4 AMPR 후보에서는 제외한다.

#### ASPD·행동속도

현재 계산 경로와 최종 행동속도 50% 상한은 존재한다. 사용자 확인에 따라 기본 요구치는 ASPD 1,000으로 확정한다.

현재 상태:

- MAXMP: 공식과 신속의 수도 Lv.10 버프 전 2,300 요구치를 BuildEvaluator에 연결
- 행동속도: ASPD 1,000 기본 요구치와 최종 행동속도 50% 상한 연결
- MAXHP: 확정 공식과 Outcome·회귀 연결
- AMPR: 기본·AMPR%·고정값, 복수 통상공격 변화 액티브의 단독 평가·최댓값 선택·안정적 동률 처리, 듀얼소드 선택 후 2배를 연결했다. 축지법 1회 AMPR은 지속 Utility에서 제외하며 `tools/test-normal-attack-ampr-priority.mjs`로 회귀한다.

### U02. Utility 실행 입력 UI

사용자는 지표마다 다음 중 하나를 선택할 수 있어야 한다.

### U03. Utility 회귀 fixture

- 같은 대미지에서 HP 요구치 만족 여부로 결과가 바뀌는 사례
- MP 경계를 넘으며 콤보 취소가 사라지는 사례
- AMPR 경계에서 회복 행동 횟수가 달라지는 사례
- 행동속도 50% 이후 추가 ASPD 가치가 0이 되는 사례
- 대미지 손실 허용률에 따라 Pareto 추천이 바뀌는 사례
- 신속의 수도 Lv.10에서 버프 전 2,300과 3중첩 후 2,000 경계 사례

- 통상공격 변화 액티브가 둘 이상 활성일 때 각각 단독 평가하고 최종 AMPR 최대 하나만 적용하며, 축지법 1회 AMPR은 후보에서 제외하는 사례
- 선택 스킬이 확정 크리티컬이어도 평타 최종 크리티컬률 100 미만 후보를 제외하는 사례
- 평타 크리티컬률 100 달성 후 선택 스킬도 확정 크리티컬이면 초과 크리티컬률 가치가 0이 되는 사례
- 같은 크리스타의 다른 장비 반복과 같은 장비 중복 금지 사례
- 같은 시작점의 분기 강화 크리스타 배타 사례

## 7. 잠재력 제약 8옵션 자동 설계 선행조건

### F01. 검증된 옵션 상한·잠재력 비용 데이터

다음 수치를 추정 없이 확보해야 한다.

- 옵션별 단계·상한·potential 비용
- 양수·음수 옵션의 비용 변화
- 옵션 수 제한과 배타 조건
- 무기·몸장비·속성 조건
- 출처, 확인일, 적용 레벨과 규칙 버전

사용자가 제공한 Coryn 수동 시뮬레이터와 Dodamu 수동·자동부여의 공개 계산 모델에서 위 구조를 확보할 수 있다. 두 사이트의 코드를 복사하지 않고 독립 데이터로 작성하며 교차 fixture로 검증한다. 현재 저장소에는 이 구조화 레지스트리가 아직 없다.

### F02. 유저 제작 장비 입력 계약

- 장비는 이미 제작 완료
- 기본 크리스타 슬롯 2개
- 최종 옵션은 음수 옵션을 포함해 정확히 8개
- 사용 가능한 잠재력은 사용자 입력
- 단일 성공률과 최종 성공률은 사용자 입력값을 그대로 보존하며 계산·최적화하지 않음
- 크리스타 슬롯 잠금은 전역 크리스타 후보를 고정하는 제약이며 옵션부여 과정과 무관

### F03. 옵션 상한 기준 레벨 계약

인터넷 연결 시 공식 토람 온라인 레벨 상한 개방 공지의 최신 확인값을 우선한다. 확인 결과에는 상한, 공지 URL, 확인일을 저장한다. 인터넷이 없거나 공식 확인에 실패하면 사용자 입력 레벨을 사용하고 결과에 fallback 사실을 표시한다. 2026-08-24 확인 기준 공식 레벨 상한은 Lv.325다.

### F04. 옵션 Pareto DP와 전수조사 fixture

정확히 8개 옵션과 잠재력 hard budget을 만족하는 bounded integer knapsack/Pareto DP를 작성한다. 작은 옵션 집합은 모든 옵션 종류·수치·음수 조합을 전수조사해 결과가 같아야 한다.

필수 회귀:

- 잠긴 크리스타가 고정된 상태에서 8옵션 최적해가 바뀌는 사례
- 잠기지 않은 크리스타 후보와 8옵션을 함께 바꿔야 전역 최적이 되는 사례
- 옵션 1%p의 대미지 증가를 잠재력 1pt당 로그 대미지로 비교하는 사례
- 음수 옵션의 회복 잠재력과 대미지·Utility 손실·옵션 한 칸을 함께 비교하는 사례
- 선택 스킬의 확정 크리티컬에 관계없이 평타 최종 크리티컬률 100을 만족시키고, 100 달성 전·후의 크리티컬률 옵션 가치가 달라지는 사례
- 최신 공식 레벨 상한과 오프라인 사용자 레벨 fallback 사례
- 단일 성공률·최종 성공률이 입력값 그대로 보존되는 사례
## 8. 실행·성능 선행조건

### R01. Worker 실행 계약

- 입력과 출력은 structured clone 가능
- 취소 토큰과 스냅샷 버전 포함
- 최선해·상한·gap을 주기적으로 전달
- UI 스레드에서 전역 탐색 금지
- 첫 구현은 JavaScript Worker로 계산식 단일 기준 유지

현재 상태: **구현 완료**. structured clone 가능한 문제/결과와 스냅샷 버전, Worker 종료 방식 취소, 32ms 진행 스냅샷, UI 스레드 외 탐색을 연결했다.

### R02. 캐시 무효화 계약

다음 값이 바뀌면 관련 캐시를 무효화한다.

- 스탯·스킬·버프·콤보·대상
- 장비 후보와 옵션 상한·잠재력 비용 규칙
- Utility 요구치·가중치
- 데이터 버전과 계산식 버전

현재 상태: **구현 완료**. 전체 Build/Scenario/후보 패키지 서명과 탐색 시간·노드·Pareto 비교 예산을 키로 사용하며 페이지 내 메모리 캐시를 재사용한다.

### R03. 기준 하드웨어와 시간 예산

대상 Windows PC 등급을 정하고 다음 회귀를 측정한다.

- 100ms: 입력 검증·캐시 확인
- 500ms: 첫 유효 추천 목표
- 3초: 일반 입력 정확해 목표
- 5초: 기본 자동 탐색 제한

5초에 정확성 증명이 끝나지 않으면 최선해와 인증된 gap을 반환한다. 임의로 `최적`이라고 표시하지 않는다.

현재 상태: **기본 계약 및 2차 성능 개선 완료**. 실제 425개 fixture 반복 측정에서 컴파일 112.6~119.2ms, 첫 유효 추천 63~65ms, 5초 탐색 5,002ms, 약 41,815~41,843회 평가 후 하한 14,090.0409와 `bounded` 54.726~54.729% gap을 반환했다. 시나리오·부위별 무관 축 제거와 사전식 단방향 지배 비교로 네 부위 Pareto가 비교 예산 100만 안에 모두 완결된다. 성능 회귀 기준은 첫 추천 500ms 이내, 하한 13,500 이상, 5초 gap 75% 이하, 네 부위 Pareto 완결이다. exact 증명률을 더 높이기 위한 남은 핵심은 후보 상자 상한 정밀화다.

### R04. 결정적 결과

병렬 실행 여부와 관계없이 같은 입력은 같은 최고 해와 같은 tie-break 순서를 반환해야 한다.

현재 상태: **구현 완료**. 소형 oracle·20개 결정적 무작위 fixture·Worker 캐시 키 회귀로 동일 입력의 최고 해와 순서를 검증한다.

## 9. 단계별 착수 게이트

### Gate A. 크리스타 전역 최적화 착수

필수: P01~P09 전부 완료

완료 증거:

- 전체 StatRegistry 감사 통과
- 순수 BuildEvaluator의 현행 회귀 일치
- 소형 전수조사와 solver 결과 일치
- 안전 상한 property test 통과
- SourceProfile 고정 획득량·부족분·획득처 frontier 회귀 통과

### Gate B. Utility 최적화 공개

필수: Gate A + U01~U03

MAXHP·AMPR가 아직 미지원이면 해당 Utility만 비활성화하며 0점으로 취급하지 않는다.

### Gate C. 고정 장비 목록 선택 공개

필수: Gate A + E01~E03

구조가 바뀌는 장비는 각 구조별 평가·조건 재컴파일 테스트가 있어야 한다.

### Gate D. 완성 커스텀 장비 최적화 공개

필수: Gate A + C01~C03

자동 옵션 생성 없이 사용자가 입력한 최종 옵션 후보끼리 비교할 수 있는 단계다.

### Gate E. 잠재력 제약 8옵션 자동 생성 공개

필수: Gate A + Gate D + F01~F04

옵션 상한·잠재력 비용 레지스트리와 작은 전수조사 검증이 없는 상태에서는 공개하지 않는다. 장비 제작, 슬롯 생성, 소재, 옵션 부여 행동 순서는 Gate 범위 밖이다.

### Gate F. 실사용 배포

필수: 필요한 기능 Gate + R01~R04

`exact`, `bounded`, `heuristic`, `cancelled`, `invalid` 상태가 UI에서 구분되어야 한다.

현재 상태: **크리스타 전역 최적화 범위 공개 조건 충족**. 다섯 상태를 UI에서 구분하고, bounded 결과에는 인증 gap과 30초 정밀 계산 선택을 제공한다. 자동 장비 옵션 부여 Gate E는 사용자 결정대로 보류다.

## 10. 권장 실행 순서

1. 전체 스탯 키 감사 도구와 StatRegistry 작성
2. BuildSnapshot·ScenarioSnapshot·OutcomeVector 계약 작성
3. 기존 계산식을 순수 BuildEvaluator로 분리하고 회귀 결과 동등성 확보
4. 장비 구조를 확정하고 조건부 옵션을 해결된 스탯 벡터로 사전 물질화

6. 소형 전수조사 oracle 작성
7. SourceProfile을 작성하고 고정 획득량·대미지 계열·Utility 획득처 frontier 생성
8. 안전한 구간 상한과 전역 branch-and-bound 작성
9. 크리스타 8슬롯만으로 정확성·성능 검증
10. Utility 공식과 입력 UI 연결
11. 고정 장비 목록 연결
12. 완성 커스텀 장비 후보 연결
13. 옵션 상한·잠재력 비용 레지스트리와 8옵션 Pareto DP 연결
14. Worker·취소·gap·진행 UI 및 성능 회귀
