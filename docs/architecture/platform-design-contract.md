# 종합 플랫폼 구현 기준

- 확정일: 2026-10-24. 사용자와 정리한 제품·객체·병합·공개 규칙의 구현 기준이다.
- 목표 도메인: `toram.nimp.dev`. 목표 제품 버전대는 `1.x.y`이며 정확한 번호·전환 시점은 추후 결정한다. 이 문서는 버전 변경이나 출시를 수행하지 않는다.
- 현재 기능·배포·검증 상태는 [현재 인계](../handoff/current-development-handoff.md)가 유일한 기준이다. 설계 확정과 구현 완료를 혼동하지 않는다.
- DB/API 상세는 [플랫폼 데이터·API 계약](platform-data-api-contract.md)을 따른다. 아래 후속 결정 외의 합의는 임의로 초기화하거나 다시 추정하지 않는다.

## 1. 제품 범위와 페이지

| 페이지 | 역할·포함 기능 | 연결 |
| --- | --- | --- |
| 홈 | 대표 페이지. 왼쪽 인기 빌드·오른쪽 위 계정·오른쪽 아래 최근 메뉴 | 공통 아이콘 메뉴와 최근 메뉴에서 작업 시작 |
| 도감 | 보스·잡몹·퀘스트·아이템·도핑·스킬·스테이터스·대미지 공식 검색과 정보 조회 | 인벤토리에 담기·시뮬레이터에서 시험·계산기에 적용. 장비 모델·염색 정보도 확장 대상 |

빌드는 여러 구성의 집합체다. 전체 빌드만 공유할 수 있도록 제한하지 않는다. 공략은 퀘스트 등 도감 정보 및 게시판 콘텐츠와 연결하며 별도 최상위 페이지 추가는 확정하지 않았다.

탱커·서포터도 구성·평가 대상이다. 대미지 최대화와 다른 추천 목적함수·조건은 별도 설계하며 임의 수치로 대체하지 않는다. 플랫폼 시뮬레이터 범위가 피격 엔진·콤보 포인트/레벨 등 기존 보류 전체를 자동 승인하지는 않는다. 게임 규칙·추천 정확성 변경은 해당 계약과 출처 검증을 먼저 따른다.

## 2. 공통 화면·탐색 계약

1. 페이지 전체를 길게 스크롤하며 오가는 구성을 기본으로 삼지 않는다. 고정된 작업 공간에서 세부 탭·버튼·필터로 조회와 편집을 끝낸다. 인벤토리의 분류·보관 목록·옵션에는 인위적인 페이지 넘김을 넣지 않는다.
2. 기존 계산기의 세부 탭 전환 구조를 재사용한다. 플랫폼 전역 메뉴와 계산기 내부 스테이터스·장비·스킬·버프·콤보·결과 탭은 다른 계층이다.
3. 같은 공통 기능을 여러 화면에서 호출할 수 있다. 출발 화면의 검색·선택·입력·대상 부위·복귀 위치를 전달하고, 닫기·취소·뒤로가기로 작업을 이어간다.
4. 기능마다 전체 작업을 하는 대표 화면을 두고, 관련 위치에는 요약·바로가기·간단한 조작·선택 패널을 제공한다. 모든 위치에 전체 편집기를 상시 펼치지는 않는다.
5. 같은 원본의 데이터·권한·검증은 공통으로 처리한다. 검색 조건·임시 선택·초안까지 무조건 전역 공유하지 않는다. 현재 범위와 적용 대상을 표시한다.
6. 조회는 입력을 변경하지 않는다. 장비 적용·내 사본 생성·개인 저장·공개 게시를 구분한다. 인증만으로 작업을 확정하거나 로컬 입력을 업로드하지 않는다.
7. 탭·분류·검색·선택 대상은 직접 링크·새로고침·뒤로가기로 복원 가능하게 한다. 주소 변경이 문서 전체 재로딩을 뜻하지는 않는다. 큰 초안·인증 비밀값을 URL에 넣지 않는다.
8. 모바일에서는 동시에 보이는 패널 수를 줄인다. 페이지 높이를 무제한 늘리거나 중첩 여백으로 핵심 수치를 압축하지 않는다. 키보드·화면 확대·포커스 접근을 막지 않는다.
9. `/` 첫 화면은 홈이다. index.html은 공통 틀·홈 HTML을 소유하고, 계산기 마크업·classic 초기화는 pages/calculator/가 소유한다. 홈·도감·게시판·인벤토리 조회는 계산기를 로드하지 않는다. 계산기 사용 시 한 번만 초기화하고 다음 진입에 DOM/입력을 유지한다. 인벤토리 적용·구성 담기와 계정 저장/불러오기도 같은 준비 함수를 기다린다. 직접 링크는 해당 페이지로 열며 초기화 중인 계산기는 노출하지 않는다. 실패 시 새로고침을 안내하고 다른 페이지는 사용할 수 있다.

패널 내부 스크롤을 공통 대안으로 확정하지 않았다. 긴 본문·스킬 트리·3D 공간 탐색의 구체 조작은 후속 화면 설계에서 판단한다.

### 디자인 기준과 기존 UI 재사용

- 인벤토리 종류 선택은 계산기 스킬 탭처럼 한 프레임의 왼쪽에 대분류·소분류 책갈피 두 열을 고정한다. 하위가 없는 대분류도 두 번째 열은 빈 채로 유지한다. 검색·목록·상세·등록은 그 오른쪽 작업 영역 안에 둔다. 세부 종류는 소분류를 눌렀을 때 기존 세 번째 열 위치에 좁은 세로 팝업으로 표시한다. 높이는 항목 수만큼 사용하며 배경 필터를 씌우지 않는다. 선택하면 이동 후 닫고, Esc·바깥 클릭·닫기는 URL과 초안을 유지한다. 현재 경로는 ‘내 인벤토리’ 제목 옆에 상시 표시한다. 개별 트리 표시 이름의 ‘ 스킬’ 접미사는 생략하고 원본 ID·데이터는 유지한다. 대분류는 장비·스킬·도핑·스테이터스·콤보·빌드다. 장비는 다섯 부위와 무기 종류/장비셋, 스킬은 원본의 네 분류·개별 트리/스킬셋, 도핑은 native 버프 계열/도핑셋을 구분한다. URL 조건으로 실제 DB 목록을 필터링한다. “전체”와 각 셋은 하위 책갈피가 없는 최종 조회다. 스킬의 구체 분류(무기·버프·보조·생활)에서만 해당 실제 트리를 표시하며 하위 “전체”를 추가하지 않는다. 도핑은 계열을 소분류에서 바로 고른다. 계산기와 인벤토리는 ui/bookmark-button.mjs의 동일한 버튼 생성 코드를 사용하고 버튼 강조·라벨 규칙을 맞춘다. 모바일은 선택 경로에서 분류 화면을 열고 같은 좌측 세로 열로 선택한 뒤 작업 화면으로 돌아간다.
- 인벤토리는 좌측 ‘내 목록’과 우측 편집 공간으로 나눈다. 목록 폭은 기존 220px의 두 배인 440px이며 좁은 화면에서는 50% 이내로 제한한다. ‘새로 만들기’·‘저장’·새로고침은 목록에 두고 우측의 ‘작업공간’ 제목을 제거한다. 선택 전부터 분류에 맞는 기본 트리/장비 양식을 표시한다. ‘새로 만들기’는 저장된 항목의 편집을 먼저 저장하고 선택을 해제해 기본 초안을 연다. 기본 초안은 ‘저장’을 눌러야 새 객체가 되며, ‘새 스킬트리’, ‘새 무기’처럼 종류별 이름과 (n)을 사용한다. 기존 항목 선택 시에는 같은 ID에 저장하고 변경 없는 수동 저장은 갱신하지 않는다. 기본 초안은 분류별로 메모리에 보관하며 계정 변경 시 폐기한다. 스킬 표시는 기본 90% 크기이며 영역이 좁으면 더 맞춰 전체 트리의 스크롤을 없앤다.
- 기존 스킬·장비 편집은 변경이 있는 2분 주기와 목록/분류/페이지 이탈 시 저장한다. 기본 초안은 이때 메모리에만 보관한다. 작업공간에 이름 입력·별도 저장 하단·상시 사용 안내를 배치하지 않는다. 스킬 작업공간 하단의 계산기 적용/편집·별도 병합·공개·삭제 버튼도 표시하지 않는다. 목록 이름은 선택한 이름 클릭·더블클릭 또는 F2로 수정하며 Enter·포커스 이탈로 적용하고 Esc로 취소한다. 연필·확인 버튼과 수정 번호 표시는 두지 않는다. 저장 실패 시 이동·초기화 없이 입력을 보존하고, 브라우저 새로고침/종료는 미저장 초안이 있으면 이탈 경고를 사용한다.
- 단일 스킬트리 작업공간은 선택한 트리 하나만 편집한다. 스킬셋은 분류·트리 책갈피를 포함해 전체를 편집하거나, 같은 공간에서 개별 구성 합치기로 전환한다. 가져온 개별 트리는 출처가 있는 독립 스냅샷이며 충돌은 기존 전체/트리 선택 규칙을 따른다. 계산기와 ui/skill-tree-simulator.mjs의 렌더링·투자/선행/회수 코드를 공유하지만 상태는 분리한다. 스킬 데이터·포인트 규칙·버프 상태를 새로 추정하지 않는다. 모든 ~셋 편집기는 전체 편집/개별 조립 두 작업 모드를 같은 공간에서 제공하는 기준을 따른다. 이번 구현 대상은 스킬트리·스킬셋이다.
- 새 장비 등록은 인벤토리의 종류·수치·옵션·크리스타 탭에서 직접 입력한다. 계산기를 거치지 않고 소유 객체를 생성하며 공개·조립에 사용할 수 있다. 실패·이탈 취소 시 초안을 보존한다. 상세는 요약·옵션/구성·출처 탭으로 나눈다. 분류·보관 목록·옵션은 모두 같은 작업 영역에 두며 기존 스킬 책갈피처럼 영역 안에서 접근한다. 별도 이전/다음 단계나 공간 확보를 위한 페이지를 만들지 않는다.

- 디자인 참고: 사용자가 많이 관여한 `PKNU_SE_CERT-IS_Scheduler` 프론트의 얇은 경계, 절제된 그림자, 고정 탐색, 여러 정보를 대조하는 분할 화면을 참고한다. 색상은 사용자 지시에 따라 하늘색 계열로 구성한다.
- 팔레트 기준은 ink `#123e5b`, muted `#4a6a80`, surface `#ffffff`, canvas `#eef8ff`, selected `#dff1ff`, 주요 버튼 `#b9e4ff`, 강조/포커스 `#1976a8`다. 밝은 버튼에는 진한 청색 글자를 써 대비를 확보한다. 베이지·갈색은 기본 테마에 사용하지 않는다. 작은 보조 글자·옅은 대비·내부 스크롤은 참고 UI에서 그대로 복제하지 않는다.
- 데스크톱 기본 방향은 접을 수 있는 좌측 공통 메뉴·얇은 상단 바·넓은 본문이다. 장비 부위 카드, 게임 아이콘·연결선의 스킬 트리, 콤보 순서·MP·효과, 현재/추천/증가량 비교는 보존한다.
- 공통 버튼·글자·테두리·여백 규칙을 맞추고 게임 표현과 성공·경고·오류의 의미색을 구분한다. 현재 DOM의 ID·이벤트·Application·저장 경계를 유지하며, 이 설계가 프레임워크 전환이나 계산 엔진 재작성을 요구하지 않는다.

### 홈 구성 기준

| 위치 | 구성 |
| --- | --- |
| 공통 왼쪽 사이드바 | 홈·도감·인벤토리·시뮬레이터·계산기·게시판 대분류 아이콘과 이름 |
| 공통 상단 바 | 서비스 이름·현재 버전·현재 페이지·계정 열기. 세팅 파일 버튼은 계산기 내부에 둔다 |
| 본문 왼쪽 | 비로그인 사용자도 볼 수 있는 현재 핫한 빌드 Top N |
| 본문 오른쪽 위 | 작은 로그인/계정 카드·내 인벤토리 접근 |
| 본문 오른쪽 아래 | 이 브라우저에서 최근 사용한 메뉴. 클릭하면 해당 작업 화면으로 이동 |

Scheduler의 공통 사이드바·탑바와 넓은 목록/작은 보조 패널 구성을 차용한다. 홈에 기능 미리보기 탭이나 전체 편집기를 넣지 않는다. 하늘색 캔버스·흰 패널·일관된 선 아이콘을 사용한다. 좁은 화면에서는 순위→계정→최근 메뉴 순으로 배치하고 일반 모바일 높이에서는 첫 화면 안에 들어오도록 한다. 낮은 화면이나 확대 시에는 내용을 잘라내지 않고 스크롤을 허용한다.

Top N은 공개 빌드 게시글의 즐겨찾기 수를 기준으로 하며 복사 횟수와 구분한다. 순위·이름·무기/역할·작성자·즐겨찾기 수를 제공하고 더 많은 항목은 버튼으로 전환한다. 인기도를 전투 성능 순위로 설명하지 않는다. 공개 게시글/평가 연결 전에는 준비 상태를 명시하며 임의 순위·가상 이용자 수를 표시하지 않는다. N·실제 순위 연결은 공개 게시글 구현 때 정한다.

페이지 소유권은 `web/src/layout/`의 공통 틀·전환, `web/src/pages/{home,inventory,board,catalog}/`의 페이지 화면으로 나눈다. 기존 계산기는 공통 틀 안에 계속 마운트해 입력과 내부 세부 탭을 보존한다. 웹 경로는 `/`·`/inventory?type={}`·`/calculator`·`/board`·`/catalog`, 앱은 `/index.html?view=home|inventory|calculator|board|catalog`다. 최근 메뉴에는 대분류 ID만 최대 4개 저장하고 개인 객체 ID나 계정 토큰을 저장하지 않는다. 아직 없는 대분류는 준비 중으로 비활성 표시한다.

### 도감 조회 계약

- 도감은 `web/src/pages/catalog/`, 조회 상태·표시용 행은 `application/catalog-browser.mjs`가 소유한다. 기존 아이템/보스 서비스와 발행 manifest를 재사용하며 도감을 위한 별도 계정 DB나 원문 복제 API를 만들지 않는다.
- 첫 범위는 발행된 아이템 8분류와 보스다. 전체/무기/몸·추가·특수장비/크리스타/소모품/아바타/기타를 조회하고, 6개 언어의 실제 이름·설명을 표시한다. 없는 번역은 명시하며 임의 번역으로 채우지 않는다. 잡몹·퀘스트·스킬·공식·모델/염색은 해당 데이터와 상세 화면을 별도로 검토한다.
- 웹은 `/catalog?section=items|bosses&kind=분류&locale=언어&q=검색&page=번호&selected=게임ID&tab=info|options|source&detailPage=번호`다. 보스 선택에는 `variant=지역ID:개체ID`, `difficulty`, `level`을 쓴다. 앱은 같은 상태를 `index.html?view=catalog`에 둔다. 새로고침·뒤로 가기·다른 메뉴에서 복귀해도 조회 상태를 복원한다.
- 목록은 일반 PC 6개, 모바일/낮은 화면 4개 단위다. 상세는 정보·옵션/수치 기준·원본 탭과 내용 페이지로 전환한다. 긴 설명도 내용 페이지로 나누며 작은 화면에서 목록/상세를 전환한다. 키보드·확대 시 내용을 잘라 접근을 막지 않는다.
- 보스 개체·난이도·레벨 수치는 기존 `createBossSelection/validateBossSelection/resolveBossTarget`만 사용한다. 새 수식이나 게임 입장 상한을 추정하지 않는다. 미확인 분류·계산 불가 수치는 미확인으로 표시하고 원본을 별도 제공한다. 인벤토리·계산기 입력을 변경하지 않는다.
- 아이템의 고정/조건부 연결 옵션, 원문 후보·미연결 효과, 소모품 duration/그룹, 크리스타 강화 전/후 ID를 보존한다. fullyMapped를 전투 전체 지원으로 설명하지 않으며 미연결 원문을 조회에서 제외하지 않는다.
- 인벤토리 개선은 후속이다. 이 도감에서 저장·적용·공개를 자동 호출하지 않고 로그인 없이 정적 자산만 조회한다.

## 3. 객체·조립·복사

| 단위 | 내용 |
| --- | --- |
| 개별 객체 | 개별 장비, 단일 스킬트리, 개별 도핑, 콤보 등 |
| 중간 객체 | 장비 세팅, 스킬셋, 도핑 세팅, 콤보 목록 등 |
| 빌드 | 스테이터스 및 각 중간 구성을 조립한 객체 |

- 내 인벤토리에 담기는 것은 DB에 저장되는 내 소유의 새 객체다. 다른 사람의 객체를 실시간 참조해서 사용하는 방식이 아니다. 같은 원본의 복사본을 여러 개 가질 수 있다.
- 빌드 필드는 정해진 의미와 허용 객체 종류를 가진다. 단일 객체·중간 객체를 조립 입력으로 받고 해당 필드의 구성으로 해석한다. 임의 JSON이나 실행 코드를 받는 범용 객체 시스템은 만들지 않는다.
- 부모 구성에는 포함한 시점의 스냅샷과 출처를 보존한다. 자식 인벤토리 객체나 원본 게시글이 수정·삭제되어도 저장한 부모 빌드가 자동으로 바뀌거나 깨지지 않는다.
- 원본 게시글·특정 릴리스 등 출처를 기록한다. 최신 원본이 필요하면 출처로 이동해 별도 새 객체로 가져온다. 기존에 수정한 내 버전과 새 버전은 함께 존재한다.
- 객체 조회·복사·내 사본 편집·작성자의 공개본 수정은 구별한다. 원본 데이터 갱신으로 기존 장비/도핑의 고정 스냅샷을 임의 재해석하거나 교체하지 않는다.
- 영구 수명은 자동 만료가 없다는 뜻이다. 명시적 비공개·삭제, 저장 용량·요청 제한은 별개다.

## 4. 두 객체 병합 계약

Git의 충돌 해결과 같은 선택 흐름을 제공하되 두 객체 비교가 전제다. 공통 조상·텍스트 diff·3-way merge는 기본 범위가 아니다.

| 영역 | 큰 단위 | 세부 단위·충돌 처리 | 더 쪼개지 않음 |
| --- | --- | --- | --- |
| 스테이터스 | 전체 중 하나 | 세부 선택 없음 | 개별 STR/DEX 등의 필드 |
| 장비 | 장비 세팅 전체 중 하나 | 주무기·보조·몸·추가·특수별 선택 | 개별 옵션·크리스타·제련 등 |
| 스킬 | 스킬셋 전체 중 하나 | 블레이드·슛·매직 등 스킬트리별 선택 | 트리 안 개별 스킬 |
| 도핑 | 세팅 전체 선택 가능 | 공격속도·최대 HP·명중 등의 카테고리가 겹치고 내용이 다를 때 선택 | 화면의 슬롯 번호별 비교 |
| 콤보 | 목록 합치기 | 별도 객체 리스트로 이어 붙이고 사용자가 나중에 삭제 | 자동 중복 제거·순서 충돌 해결 없음 |
| 외형 | 선택한 장비를 따름 | 별도 외형 복사/가져오기 행동 | 장비 병합의 별도 외형 충돌 없음 |

- 겹치지 않는 단위는 자동으로 합친다. 실제 구성이 같고 이름·출처만 다르면 충돌로 보지 않는다.
- 큰 단위를 선택하면 그 아래 세부 충돌을 해결한다. 전체와 세부의 모순된 선택을 확정 요청에 허용하지 않는다.
- 미지정과 명시적 빈 값은 구별한다. 부분 구성에서 필드가 없으면 그 영역을 제공하지 않은 것이다. 비우기 표현은 해당 타입의 스키마로 정한다. 기존 요구조건의 null/누락 의미를 일괄 변경하지 않는다.
- 도핑은 고정 카테고리 ID로 비교한다. 기존 `buffGroupId`와 화면 카테고리의 대응은 게임 출처로 확인하며, 같은 효과 이름만으로 중복 그룹이라고 추정하지 않는다.
- 콤보 내용이 같아도 두 개를 유지한다. 목록 내 항목 식별자는 충돌하지 않게 한다. 보관할 콤보 목록과 실제 계산할 콤보 선택은 구분한다.
- 병합 결과는 새 인벤토리 객체 생성이 기본이다. 양쪽 원본을 보존하고 최종 결과에 기존 장비·스킬·도핑 검증을 적용한다.

## 5. 외형 계약

- 외형은 장비에 귀속된다. 별도 최상위 외형 인벤토리 객체를 기본으로 만들지 않는다.
- 기본 외형 ID는 해당 게임 장비 ID와 1:1 대응한다. 개인 객체 UUID와 게임 장비 ID를 혼동하지 않는다.
- 외형 변경은 다른 게임 장비의 외형 ID를 지정하는 방식이다. `overrideItemId = null`은 해당 장비의 기본 외형을 뜻한다.
- 장비 병합에서 선택한 장비의 외형·염색도 따라간다. 외형만 쓰려면 명시적인 외형 복사/가져오기를 제공한다. 이 행동은 옵션·제련·크리스타를 바꾸지 않는다.
- 복사 시 원본의 실제 표시 외형 ID를 해석한 뒤 대상에 지정한다. 원본의 null만 복사해 대상 기본 외형으로 바뀌면 안 된다.
- 염색은 장비 외형 하위 데이터다. 실제 염색 필드·호환 부위·모델 자산은 게임 자료 확인 후 결정한다. 미확정 모델·색상 수치를 만들지 않는다.

## 6. 게시글·릴리스·평가·출처

1. 게시글이 공개 버전들을 관리한다. 공개 구성 수정은 기존 릴리스를 바꾸지 않고 새 릴리스를 만든다.
2. 빌드 history page는 GitHub Releases에 가까운 공개 이력이다. 공개 스냅샷·게임 버전·데이터/계산 규칙 버전·업데이트 시기·변경 설명을 묶어 조회·비교·복사한다. 개인 초안 수정이 곧 공개 릴리스 생성은 아니다.
3. 즐겨찾기·별점 등 평가 요소는 특정 릴리스가 아닌 게시글 전체에 붙인다. 새 릴리스에서 초기화하지 않는다. 일반 진입·인기 목록은 최신 공개 릴리스로 이어지고, 출처 링크는 복사 당시 특정 버전을 가리킨다.
4. 누적 평가는 최신 버전만의 평가를 보장하지 않으므로 최신 릴리스 날짜·게임 버전을 함께 표시한다.
5. 비공개·삭제 원본으로의 링크는 남긴다. 접근하면 '원본이 비공개/삭제되어 접근할 수 없습니다'에 해당하는 안내를 제공한다. 내 복사본은 유지한다.
6. 일부 구성 공개에서도 해당 구성만 스냅샷으로 고정한다. 타인의 비공개 객체·초안·인증 정보·불필요한 개인 객체 식별자를 공개 데이터에 섞지 않는다.

## 7. URL·호스팅·버전 전환

- 인벤토리는 `/inventory?type=build`, `/inventory?type=equipment&equipmentType=sword`처럼 같은 작업 공간에서 종류·필터를 전환한다. `/inventory/builds`·`/inventory/equipments`로 작업 공간을 분리하는 방식을 기본으로 삼지 않는다.
- 개별 선택은 `selected` 같은 상태로 전달할 수 있다. 게시판 첫 구현은 `/board?post=ID&release=번호`를 사용하고 최신 버전은 release를 생략한다. 최종 URL 정책과 도감·시뮬레이터의 상세 상태는 추후 검토한다.
- 같은 HTTPS origin에서 프론트와 `/api/`를 제공한다. Google 콜백·앱 로그인·개발/배포 경로와 WASM Worker의 COOP/COEP 계약을 유지한다. 도메인·HTTPS·OAuth의 실제 설정은 별도 배포 작업이다.
- `1.x.y` 전환 시 앱·웹의 저장 형식과 DB 이관을 함께 검증한다. 버전 번호를 먼저 올리거나 기존 파일을 손실 변환하지 않는다. 호환되지 않는 데이터는 명확히 알린다.

## 8. 후속 결정으로 남긴 범위

- 홈의 N·실제 공개 순위 연결, 긴 본문·트리/3D 공간의 조작.
- 게시판 프론트 URL과 개별 인벤토리 상세의 최종 URL 상태 표현.
- 별점 척도와 별도 추천 버튼 추가 여부·인기 정렬의 세부 동점 정책. 게시글 단위 귀속은 확정이다.
- 게임 버전 표기 규격·염색 세부 데이터·장비 모델 자산·도핑 카테고리와 게임 그룹의 정확한 대응.
- 퀘스트 경험치의 원문 데이터·계산 검증, 탱커/서포터 추천 목적함수, 옵션 부여 시뮬레이터의 출처·지원 범위.
- 게시글 관리 정보 수정 범위, 영구 삭제·복구·계정 탈퇴 정책, 저장 한도·요청 키 보존 기간, 이관의 구체 DTO/SQL.
- 정확한 `1.x.y` 번호와 배포 순서. 위 미확정 사항을 추정해 확정 계약으로 추가하지 않는다.

## 9. 구현 수용 기준

- 어느 진입점에서든 대상·범위·권한·동작이 일관되고 초안과 복귀 위치를 보존한다.
- 개별/중간/전체 구성의 저장·복사·부분 공개·조립을 왕복하며 원본과 내 사본이 독립적이다.
- 병합 단위와 콤보 목록·외형 규칙을 위 계약대로 검증한다. 미리보기 후 원본 변경은 덮어쓰지 않는다.
- 공개 이력은 고정되고 최신 링크·특정 버전 출처·게시글 평가·접근 불가 안내가 서로 일치한다.
- 저장·DB 이관·구버전 읽기·JSON 왕복과 실제 웹/앱 로그인·배포를 각각 검증한다. S1 출처·계산 검증·전투 상태 시뮬레이션 완료를 구분한다.
- 새 계산/추천 규칙은 해당 기존 정확성·회귀 Gate를 따른다. 문서만 바꿀 때는 `npm run ai:audit`와 `git diff --check`를 실행한다.
