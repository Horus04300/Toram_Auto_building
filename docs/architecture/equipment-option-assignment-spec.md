# 장비 옵션부여(장비 강화) 데이터·최적화 명세

> 상태: 설계·데이터 수집 기준 문서. 자동 옵션부여 기능은 아직 구현하지 않는다.
>
> 확인일: 2026-08-26

## 1. 목적과 범위

이 문서는 토람 온라인의 **유저 제작 무기·몸장비에 최종 옵션을 부여하는 문제**를 계산기와 D4 전역 빌드 최적화에 연결하기 위한 계약이다.

다루는 것은 다음이다.

- 이미 제작된 장비의 최종 옵션 8개 선택
- 양수 옵션의 잠재력 소비와 음수 옵션의 잠재력 회복
- 옵션별 수치 범위·장비 호환·상호 배타·조건
- 잠긴 크리스타와 잠기지 않은 크리스타를 구분한 전역 평가
- 옵션 1%p의 실제 대미지/Utility 한계효율과 잠재력 기회비용

다루지 않는 것은 다음이다.

- 장비 제작 성공, 기본 ATK/DEF·잠재력 생성, 슬롯 생성, 소재 수급
- 실제 옵션 부여 행동의 순서·되돌리기·실패 시 첫 슬롯 보존
- 재료 소모와 재료 최적화
- 단일 성공률·최종 성공률의 역산 또는 최적화

즉, 게임에서는 옵션 부여의 순서가 성공률과 재료에 영향을 줄 수 있어도, 본 계산기는 사용자가 입력한 최종 성공률을 보존하고 **최종 옵션 집합**만 최적화한다.

## 2. 제품 계약

### 2.1 기본 장비 구조

| 항목 | 계산기 계약 |
| --- | --- |
| 대상 장비 | 유저 제작 주무기 또는 몸장비 |
| 크리스타 슬롯 | 기본 2개. 옵션부여 줄과 독립 |
| 옵션 줄 | 정확히 8개 |
| 음수 옵션 | 허용. 잠재력 회복 효과와 함께 하나의 줄을 차지 |
| 잠긴 크리스타 | 고정 효과로 먼저 합산 |
| 잠기지 않은 크리스타 | D4 전역 후보 탐색에 남김 |
| 성공률 | 단일 성공률·최종 성공률을 사용자 입력값으로 결과 메타데이터에 보존 |
| 잠재력 | 옵션 집합의 hard budget |

크리스타 슬롯 2개와 옵션 8개는 교환하거나 합산하지 않는다. 예를 들어 크리스타 1개를 잠갔다고 옵션 줄이 7개 또는 9개가 되지 않는다.

### 2.2 사용자 입력

자동 옵션 추천을 실행하려면 아래 값이 필요하다.

| 입력 | 필수 | 용도 |
| --- | --- | --- |
| 장비 부위·유형 | 예 | 옵션 호환성·조건 판정 |
| 장비 기준 레벨 | 예 | 옵션 상한 계산 |
| 시작/사용 가능 잠재력 | 예 | hard budget |
| 단일 성공률 | 예 | 결과 표시·저장만 함 |
| 최종 성공률 | 예 | 결과 표시·저장만 함 |
| 잠긴 크리스타와 그 효과 | 선택 | 고정 스탯으로 선합산 |
| 잠기지 않은 크리스타 후보 | 선택 | 전역 탐색 후보 |
| 사용 가능한 옵션/금지 옵션 | 선택 | 플레이어의 재고·선호·금지 반영 |
| 목표 시나리오 | 예 | 스킬, 대상, 버프, Utility 요구치 |

장비 레벨은 최신 공식 레벨 상한 공지를 우선해 결정하고, 온라인 확인이 불가능하면 사용자가 입력한 레벨로 fallback한다. 특정 숫자를 데이터에 영구 상수로 박아 넣지 않는다.

## 3. 게임 정보와 제품 모델의 구분

대장장이의 `장비 강화`는 잠재력을 소비해 옵션을 부여하고, 마이너스 옵션으로 잠재력을 얻을 수 있다. 로컬 원문은 장비 강화의 기본 부여 슬롯과 스킬에 따른 슬롯 증가·부여 상수·성공률 공식을 설명한다. [로컬 Smith 원문](../sources/skills/Smith.txt)

Coryn의 Statting Simulator도 장비 종류, 원본/시작 잠재력, 기준 레벨, 대장장이 숙련도, 다수의 옵션 줄, 성공률, 재료와 부여 단계를 별도 입력으로 둔다. [Coryn Statting Simulator](https://www.coryn.club/statting_simulator.php)

그러나 이 프로젝트는 게임 UI의 절차를 그대로 복제하지 않는다. 다음처럼 의도적으로 분리한다.

| 게임 절차 | 계산기·D4 모델 |
| --- | --- |
| 옵션을 여러 단계로 부여 | 최종 옵션 벡터만 보관 |
| 단계별 잠재력 변화와 성공률 | 사용자가 준 단일/최종 성공률을 보존 |
| 단계별 재료 소모 | 범위 밖 |
| 실제 슬롯 증가 스킬 | 제품 계약의 정확히 8옵션으로 정규화 |
| 음수 옵션을 먼저 넣는 순서 | 음수/양수의 순잠재력 비용만 반영 |

따라서 자동 추천이 "이 옵션 조합이 최적"이라고 말할 수는 있어도, "이 순서로 실제 부여하면 그 성공률이 나온다"고 말해서는 안 된다.

## 4. 옵션 카탈로그 데이터 계약

자동 기능을 열기 전에 모든 선택 가능한 옵션을 아래 레코드로 등록한다. 수치·상한·비용은 출처 확인 전 추정으로 채우지 않는다.

| 필드 | 설명 |
| --- | --- |
| `id` | 불변 식별자 |
| `label` | 화면 표시명 |
| `statDelta` | 계산기에 전달할 스탯 키와 단위당 변화량 |
| `equipmentTypes` | 허용되는 장비 유형(무기/몸장비 및 세부 제한) |
| `min`, `max`, `step` | 수치 도메인 |
| `sign` | `positive`, `negative`, 또는 양방향 |
| `potentialCost(level, value)` | 해당 최종 수치의 순잠재력 비용. 음수 옵션은 음수 비용 가능 |
| `lineCost` | 기본 1줄. 예외가 있으면 명시 |
| `exclusiveWith` | 함께 선택할 수 없는 옵션 ID |
| `requires` | 속성·장비 유형·다른 옵션 등 활성 조건 |
| `source` | URL/원문 위치, 확인일, 규칙 버전 |
| `verificationStatus` | `unverified`/`verified`/`deprecated` |

`statDelta`는 표시명으로 계산하지 않는다. 현재 `StatRegistry`에 등록된 키로 변환하고, 등록되지 않은 키는 조용히 버리지 말고 카탈로그 검증 오류로 처리한다.

### 4.1 상한과 비용 데이터의 확인 규칙

1. 공식 공지: 장비 레벨 상한의 기준.
2. Coryn과 Dodamu 공개 계산기: 옵션 범위·잠재력 비용·호환성의 교차 확인 후보.
3. 서로 다르거나 한쪽만 확인되면 `unverified`로 남기며 자동 생성에 사용하지 않는다.
4. 확인된 값은 출처 URL, 확인일, 적용 장비 유형, 레벨 규칙을 함께 기록한다.

Dodamu의 수동/자동 옵션부여 페이지는 교차 확인 대상으로 유지한다.

- [Dodamu 수동 계산기](https://dodamu.org/stat/manual)
- [Dodamu 자동 계산기](https://dodamu.org/stat/auto)

문서 작성 시점의 자동 수집 환경에서는 Dodamu 본문을 안정적으로 읽을 수 없었다. 따라서 해당 사이트에서만 확인되는 수치·공식은 아직 데이터 레지스트리에 넣지 않는다.

## 5. 최종 옵션 유효성

최종 옵션 후보 `S`는 아래를 모두 만족해야 한다.

```text
lineCount(S) = 8
sum(potentialCost(option, value) for option in S) <= availablePotential
각 옵션 값은 해당 min/max/step을 만족
각 옵션은 장비 유형·조건을 만족
exclusiveWith 충돌이 없음
모든 statDelta 키가 등록됨
```

음수 옵션은 잠재력을 회복하더라도 옵션 한 줄을 소모한다. 따라서 단순히 "가장 큰 잠재력 회복량"을 선택하지 않는다.

성공률은 다음의 입력 검증만 한다.

- 숫자이며 0~100 범위
- 단일 성공률과 최종 성공률을 각각 독립 저장
- 계산기가 값의 진위를 역산하거나 수정하지 않음

## 6. D4 전역 최적화 연결

### 6.1 평가 순서

```text
장비 구조·버프·스킬·대상 확정
        ↓
잠긴 크리스타와 수동 고정 옵션 선합산
        ↓
8옵션 후보 생성 또는 사용자가 입력한 완성 옵션 검증
        ↓
각 후보를 CandidatePackage로 변환
        ↓
잠기지 않은 크리스타·고정 장비 후보와 전역 D4 탐색
        ↓
BuildEvaluator로 완성 빌드 재평가
```

장비 조건이 붙은 옵션은 먼저 확정된 `main`·`sub`·`armor` 구조에서 활성화 여부를 판정한다. 예를 들어 경갑옷일 때만 유효한 관통 옵션은 활성 상태의 최종 스탯으로 변환한 뒤 다른 옵션과 같이 평가한다. 조건 자체를 별도 탐색 차원으로 추가하지 않는다.

### 6.2 기회비용

옵션 `o`를 1단위 늘릴 때의 우선순위 참고값은 다음과 같다.

```text
DeltaLogDamage / DeltaPotential
= log(Damage_after / Damage_before) / (Potential_after - Potential_before)
```

이는 후보 정렬과 안전 상한 보조값일 뿐, 최종 순위는 아니다. 같은 계열 합연산, ATK·관통 등가축, 크리티컬 임계, 반올림, Utility 요구치 때문에 반드시 전체 `BuildEvaluator` 결과로 다시 비교한다.

특히 다음을 지킨다.

- 평타 최종 크리티컬률 기본 hard constraint는 100이다. 선택 스킬의 확정 크리티컬은 이를 면제하지 않는다.
- 이미 100을 넘은 크리티컬률은 선택 스킬 기대 대미지에 기여할 때만 한계가치가 있다.
- MAXMP·MAXHP·AMPR·ASPD는 다른 고정 획득처와 현재 세팅을 합산한 뒤 부족분만 Utility 제약으로 평가한다.
- 음수 옵션은 회복 잠재력뿐 아니라 대미지·Utility 손실과 1줄 기회비용을 함께 비교한다.

## 7. 구현 알고리즘(향후)

옵션 자동 생성은 "크리스타 전수조사"가 아니라 부위별 후보 생성 단계다.

1. 카탈로그에서 현재 장비·레벨에 가능한 옵션의 유한 도메인을 만든다.
2. 정확히 8줄과 잠재력 예산을 상태로 하는 bounded integer knapsack/Pareto DP를 수행한다.
3. 상태에는 최소한 `lineCount`, `remainingPotential`, 관련 스탯 벡터, 조건 서명을 둔다.
4. 같은 줄 수에서 잠재력이 더 많이 남고 모든 관련 스탯·Utility가 열등하지 않은 상태만 안전하게 우선 제거한다.
5. 남은 Pareto 상태를 커스텀 장비 `CandidatePackage`로 변환한다.
6. 이 후보를 잠기지 않은 크리스타·고정 장비와 함께 D4 전역 탐색에 넣는다.

작은 옵션 도메인에서는 DP 결과를 원시 전수조사와 비교해 정확성을 검증한다. 옵션 상한·비용 데이터가 `verified`가 아니면 해당 옵션을 자동 생성 대상에서 제외하고, UI에 이유를 표시한다.

## 8. 구현 전 필수 테스트

- 양수·음수 옵션을 합쳐 정확히 8줄인 후보만 통과
- 잠재력 예산을 1pt 초과한 후보 거부
- 장비 부적합 옵션·상호 배타 옵션 거부
- 잠긴 크리스타의 고정 효과가 옵션 최적해를 바꾸는 사례
- 잠기지 않은 크리스타와 옵션을 함께 바꿔야 전역 최적이 되는 사례
- 평타 크리티컬 100 미달 후보 거부
- 선택 스킬 확정 크리티컬이어도 평타 제약을 유지하는 사례
- 음수 옵션의 잠재력 회복만으로 더 좋은 후보라고 오판하지 않는 사례
- 1%p 변화의 `DeltaLogDamage / DeltaPotential`이 현재 빌드에 따라 달라지는 사례
- 사용자 입력 단일/최종 성공률을 변형 없이 저장·불러오기 하는 사례
- 소형 카탈로그 DP 결과와 원시 전수조사 일치

## 9. 현재 착수 조건

자동 옵션부여를 구현하려면 다음이 먼저 충족돼야 한다.

- 옵션별 상한·잠재력 비용·호환성의 검증된 카탈로그
- 옵션 단위와 `StatRegistry` 키의 1:1 매핑 감사
- 최소 전수조사 fixture와 데이터별 출처/확인일
- 고정 장비·수동 완성 커스텀 장비 입력 계약

그 전까지는 사용자가 입력한 완성 옵션을 일반 장비 스탯으로 계산하는 범위만 유지한다.
