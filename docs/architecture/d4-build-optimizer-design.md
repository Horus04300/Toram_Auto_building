# D4 빌드 최적화 알고리즘 설계

- 상태: 설계 완료, 2단계 크리스타 전역 탐색 엔진 구현 완료(실사용 UI 연결 전)
- 기준일: 2026-08-24
- 범위: 크리스타 전역 조합, 고정 장비 후보, 유저 제작 장비 8옵션 자동 설계, 대미지 외 Utility
- 선택 알고리즘: **전역 제약 기반 Anytime Pareto Branch-and-Bound**
- 구현 선행조건: `docs/architecture/d4-build-optimizer-prerequisites.md`

## 1. 결론

D4는 각 부위를 따로 평가한 뒤 합치는 방식으로 구현하면 안 된다. 완성 빌드 전체를 하나의 해로 취급하고, 실제 계산기가 완성 빌드를 평가한 값을 목적함수로 사용해야 한다.

권장 구조는 다음 네 층이다.

1. 게임 수식을 DOM과 분리한 순수 `BuildEvaluator`
2. 고정 장비·크리스타·커스텀 옵션 범위·잠재력 제약을 동일한 문제로 변환하는 `ProblemCompiler`
3. 부위별 후보를 안전하게 축약하는 Pareto 동적 계획법
4. 빠른 초기해와 안전한 상한을 함께 사용하는 anytime 전역 분기 한정법

이 구조는 빠르게 좋은 해를 먼저 보여주고, 시간이 허용되는 동안 최적임을 증명한다. 제한 시간까지 증명이 끝나지 않으면 현재 최선해와 최적성 오차를 함께 표시한다.

임의로 복잡한 빌드 최적화는 배낭 문제와 집합 포장 문제를 포함하므로 NP-hard다. 따라서 모든 크기의 입력에 대해 짧은 고정 시간 안에 정확한 최적해를 항상 보장하는 알고리즘은 기대할 수 없다. D4의 정확한 제품 계약은 **빠른 초기해 + 안전한 상한 + 검증 가능한 최적성 오차**여야 한다.

## 2. 현행 코드에서 먼저 해결할 구조적 전제

현재 크리스타 데이터에는 425개 후보와 87종의 스탯 키가 있다. 조건 키는 현재 `main`, `sub`, `armor` 세 종류다. 그러나 현재 `applyStat`은 대미지 계산에 필요한 일부 키만 소비하며 `MaxHP`, `MaxHPP`, `AMPR`, `AMPRP` 등 여러 Utility 스탯은 완성 결과에 보존하지 않는다.

따라서 최적화기만 교체해서는 최대 HP·공격 MP 회복 등을 최적화할 수 없다. 다음 계약이 선행되어야 한다.

- 모든 옵션은 정규화된 `StatVector`에 보존한다.
- 등록된 스탯 키가 평가기에 없으면 조용히 무시하지 않고 진단 오류를 낸다.
- 계산기는 DOM을 읽지 않는 순수 함수 `evaluate(build, scenario)`를 제공한다.
- 같은 입력은 항상 같은 결과를 반환한다.
- 합산, 반올림, 상한 적용 순서를 스탯별 레지스트리에 기록한다.
- 대미지뿐 아니라 MAXHP, MAXMP, AMPR, ASPD, 행동속도, CSPD, 시전 감소, 내성 등 최적화 가능한 최종 지표를 함께 반환한다.

구조는 다음처럼 분리한다.

```text
BuildInput + Scenario
        ↓
ProblemCompiler ── 구조 분기·후보·옵션·잠재력 제약
        ↓
GlobalOptimizer ── 해 후보 BuildAssignment
        ↓
BuildEvaluator  ── 실제 게임 수식의 단일 기준
        ↓
OutcomeVector   ── 대미지·HP·MP·AMPR·속도·조건 충족 여부
```

## 3. 수학적 문제 정의

### 3.1 결정 변수

장비 부위 집합을 `S`, 부위 `s`에서 선택 가능한 장비를 `I_s`, 크리스타 슬롯을 `K_s`, 가능한 크리스타를 `C_s`, 제작 옵션을 `O_s`라고 둔다.

- `x[s,i] ∈ {0,1}`: 부위 `s`에서 장비 `i`를 선택
- `z[s,k,c] ∈ {0,1}`: 부위 `s`의 슬롯 `k`에 크리스타 `c`를 장착
- `q[s,o] ∈ Z`: 유저 제작 장비 옵션 `o`의 선택 단계 또는 수치
- `u[s,o] ∈ {0,1}`: 유저 제작 장비의 8개 옵션 칸 중 옵션 `o`의 사용 여부

기본 선택 제약은 다음과 같다.

```text
Σ(i ∈ I_s) x[s,i] = 1
Σ(c ∈ C_s) z[s,k,c] ≤ 1
z[s,k,c] ≤ 해당 장비의 슬롯 사용 가능 여부
```

여기에 잠금, 제외 목록, 같은 장비의 동일 크리스타 중복 금지, 장비 부위 제한, 강화 전후·동일 시작점 분기 계보 충돌, 무기·보조무기 호환, 스킬 사용 가능 조건, 유저 제작 장비의 정확히 8개 옵션과 잠재력 예산 제약을 추가한다. 같은 크리스타는 서로 다른 장비라면 반복 장착할 수 있다. 기본 2개 크리스타 슬롯은 옵션 8개와 별개이며 옵션부여 탐색 차원에 넣지 않는다.

### 3.2 완성 스탯

장비 구조 분기 `b`를 먼저 확정하고 그 구조에서 조건을 해결한 뒤, 스탯 `j`의 원시 합계를 다음처럼 정의한다.

```text
resolvedDelta[e,j,b] = resolveStructureCondition(e, b)
A_j(X | b) = A_j^base + Σ(e ∈ 선택 효과) resolvedDelta[e,j,b](q_e)
```

`X`는 해당 구조 분기 안의 장비·크리스타·최종 옵션 전체 선택이다. 장비 제작 자체와 옵션을 부여하는 행동 순서는 범위 밖이다. 장비 조건은 solver의 추가 결정 변수가 아니며, 분기 `b`가 정해질 때 활성 효과는 일반 스탯 벡터에 합산되고 비활성 효과는 제외된다.

최종 결과는 현재 게임 계산식 전체를 담은 함수로 계산한다.

```text
Y = F(A(X), structure(X), scenario)
```

`structure`에는 주무기, 보조무기, 방어구 개조, 속성, 슬롯 수처럼 계산식 자체를 바꾸는 선택이 들어간다. `scenario`에는 대상, 선택 공격/콤보, 버프, 스킬 투자 상태가 들어간다. `F`는 바닥 함수, 상한, 저항, 크리티컬 기대값 등 실제 계산 순서를 그대로 사용한다.

### 3.3 목적함수는 하나로 고정할 수 없다

대미지, 최대 HP, 최대 MP, AMPR, 행동속도는 단위가 다르므로 사용자 의도 없이 하나의 절대 순위를 만드는 것은 수학적으로 정의되지 않는다. 다음 세 가지 입력을 분리한다.

1. **필수 조건**: 반드시 만족해야 하는 최솟값·최댓값
2. **주 목적**: 조건을 만족하는 해 중 최대화할 값
3. **선호 Utility**: 필수는 아니지만 가치가 있는 값과 가치 곡선

기본 모드는 다음 epsilon-constraint 방식으로 한다.

```text
maximize D(X)
subject to HP(X) ≥ HP_min
           MP(X) ≥ MP_min
           AMPR(X) ≥ AMPR_min
           NormalAttackCrit(X) ≥ 100
           Motion(X) ≥ Motion_min
           X ∈ feasible builds
```

즉 기본적으로는 사용자가 정한 생존·자원·속도 요구를 만족하면서 선택 공격의 기대 대미지를 최대화한다. 이 방식은 서로 다른 단위에 임의의 가중치를 붙이지 않는다.

사용자 입력이 없을 때의 기본 hard constraint는 다음과 같다. 사용자가 값을 입력하면 해당 값이 기본값을 덮어쓴다.

- 선택 공격이 근거리이면 `MAXHP ≥ 10,000`, 원거리이면 MAXHP 기본 요구치 없음
- 신속의 수도 Lv.10이면 버프 전 `MAXMP ≥ 2,300`; 3중첩의 MAXMP -300 이후 2,000을 유지한다.
- 그 외에는 `MAXMP ≥ 2,000`
- `AMPR ≥ 100`; 듀얼소드는 2배 적용 전 100을 검사하고 최종 표시는 200
- 평타 최종 크리티컬률 `≥ 100`; 선택 스킬의 확정 크리티컬 여부와 무관하게 검사
- 기본 속도 요구치는 `ASPD ≥ 1,000`으로 확정한다.

균형형 모드가 필요할 때만 다음 정규화 점수를 사용한다.

```text
Phi(X) = w_D · log(max(epsilon,D(X)) / D_ref)
       + Σ(j ∈ Utility) w_j · u_j(Y_j(X))
```

`u_j`는 사용자가 정한 구간별 선형 Utility 곡선이며 0~1로 정규화한다. 예를 들어 HP는 목표치 이후 가치가 포화될 수 있고, 행동속도는 게임 상한 이후 추가 가치가 0이다. 가중치를 지정하지 않은 Utility를 계산기가 자의적으로 점수에 넣지 않는다.

마지막으로 Pareto 모드는 어느 한 지표에서도 다른 해보다 나쁘지 않은 비지배 해 집합을 반환한다. 이를 통해 다음 선택지를 함께 보여줄 수 있다.

- 최고 대미지
- 대미지 손실 1% 이내 최대 HP
- 대미지 손실 1% 이내 최대 MP/AMPR
- 사용자가 지정한 균형형 점수 최고값

### 3.4 Utility 조건의 표현

각 Utility는 다음 계약을 가진다.

```text
UtilityMetric {
  id,
  sourceOutcome,
  hardMin?,
  hardMax?,
  curve: [(value, utility), ...],
  weight,
  aggregation
}
```

구간별 선형 곡선은 임계점, 체감효율, 상한을 모두 표현할 수 있다. 불연속적인 가치도 계단 구간으로 표현한다.

- 최대 MP: 현재 콤보를 끝까지 쓸 수 있는 소비량 경계에 큰 가치가 생길 수 있다.
- 최대 HP: 생존 목표까지는 가치가 크고 이후에는 완만하게 만들 수 있다.
- AMPR: 단순 수치뿐 아니라 콤보 이후 필요한 통상 공격 횟수 변화에 계단형 가치가 생길 수 있다.
- 행동속도: 실제 최종 행동속도 또는 검증된 행동시간 결과를 사용하고 상한 이후 포화시킨다.

MP·AMPR의 회전율 Utility를 사용할 경우 `BuildEvaluator`가 검증된 MP 소비·회복 규칙으로 회전 결과를 먼저 산출해야 한다. 확인되지 않은 전투 시간을 임의 공식으로 만들지 않는다.

## 4. 동일 옵션 합연산과 기회비용

각 아이템의 점수를 미리 더해서는 안 된다. 모든 옵션을 합산한 뒤 `F`를 다시 평가해야 한다.

예를 들어 최종 배율의 한 계열이 `1 + p/100`이고 같은 계열 옵션 `delta`를 추가하면 상대 증가율은 다음과 같다.

```text
((1 + (p+delta)/100) / (1 + p/100)) - 1 = delta / (100+p)
```

따라서 이미 `p`가 클수록 같은 `delta`의 상대 효율은 감소한다. 크리티컬, 안정률, 행동속도처럼 상한이 있는 값은 상한을 넘는 순간 한계효율이 0이 된다. 완성 빌드를 실제 식으로 재평가하면 이 효과가 자동으로 반영된다.

### 4.1 기회비용의 정의: 획득처 집중도와 슬롯 대체비용

```text
ExplicitNonSlot_j = 현재 ScenarioSnapshot에서 명시적으로 활성화된 비장비 획득량
Residual_j = max(0, Required_j - ExplicitNonSlot_j)
```

요리·도핑·길드 버프·스킬은 주요 획득처일 뿐 자동으로 적용되는 고정 획득처가 아니다. 현재 세팅에서 실제로 습득·활성화·입력된 값만 `ExplicitNonSlot_j`에 포함한다. 초기 구현은 내장된 고정 획득처 목록을 요구하지 않으며, 이후 데이터가 추가되면 같은 SourceProfile 계약으로 확장한다.

이 설계에서 기회비용은 특정 후보를 강제로 포함했을 때의 사후 점수 차이가 아니다. **한 스탯을 어느 획득처에서 얼마나 집중적으로 챙길 수 있으며, 그 선택으로 다른 슬롯을 대미지 옵션에 사용할 수 있게 되는가**를 뜻한다.

획득처 `s`의 후보 `c`가 주는 대미지 계열 변화와 Utility 변화의 현재 가치를 다음처럼 둔다.

```text
SourceValue(s,c | X,lambda)
  = DeltaLogDamage(s,c | X)
  + Σ(j) lambda_j · DeltaUtility_j(s,c | X)
```

`lambda_j`는 아직 부족한 Utility 한 단위의 대미지 환산 그림자가격이다. 현재 세팅에서 명시적으로 활성화된 비장비 획득량만으로 요구량을 채웠다면 `Residual_j=0`이고 `lambda_j=0`이므로, 해당 Utility만 제공하는 크리스타는 우선순위에서 사라진다. 반대로 특정 슬롯만 Utility를 매우 크게 제공한다면 그 슬롯의 집중 획득 가치가 커지고 다른 슬롯을 대미지에 사용할 수 있다.

`lambda`와 `SourceValue`는 좋은 초기해와 탐색 순서를 만드는 데 사용한다. 이 값만으로 후보를 제거하지는 않는다. 후보 제거는 뒤의 명확한 우선순위 증명 조건을 만족할 때만 수행한다.

### 4.2 잠재력 pt의 기회비용과 크리티컬 임계

완성된 유저 제작 장비에 사용할 수 있는 잠재력을 `P_user`, 옵션 `o`를 수치 `q_o`까지 부여하는 순잠재력 비용을 `C_o(q_o)`라고 둔다. 음수 옵션은 `C_o(q_o) < 0`이 될 수 있다.

```text
Σ(o) C_o(q_o) ≤ P_user
Σ(o) u_o = 8
MarginalPotentialValue(o, q → q+1 | X)
  = [log D(X + Δ_o(q)) - log D(X)] / [C_o(q+1) - C_o(q)]
```

1%p가 실제 대미지에 주는 영향은 고정 점수가 아니라 현재 완성 빌드 `X`에서 `BuildEvaluator`를 전후 두 번 평가해 구한다. 잠재력 그림자가격 `lambda_P`는 좋은 초기해와 탐색 순서를 만들 때 사용한다.

```text
L(X, lambda_P) = log D(X) - lambda_P · max(0, Σ C_o(q_o) - P_user)
```

음수 옵션은 회복하는 잠재력만큼 이득이지만 대미지·Utility 손실과 옵션 한 칸을 동시에 소비한다. 따라서 회복 잠재력만으로 순위를 정하지 않고 `대미지 손실 / 회복 잠재력`과 8칸의 슬롯 대체비용을 함께 비교한다. 이 그림자가격은 가지 순서와 안전한 상한에 사용하고 최종 순위는 원래 잠재력 제약 아래 실제 완성 빌드를 재평가한다.

크리티컬률은 선택 공격의 대미지 축과 평타 AMPR 안정성 제약을 분리해 평가한다. 선택 스킬이 확정 크리티컬이어도 평타를 통한 MP 회복이 필요하므로 기본 운용 제약 `NormalAttackCrit(X) ≥ 100`을 면제하지 않는다. 평타 최종 크리티컬률은 대상 크리티컬 저항, 스탯·버프·고정 장비·잠긴 크리스타를 반영한 최종값으로 검사한다.

따라서 크리티컬률 옵션을 강제로 한 줄 포함하지는 않지만, 평타 100을 만족하지 못한 후보는 기본 탐색에서 infeasible로 제외한다. 이미 평타 100이 보장되면 초과 크리티컬률은 선택 스킬의 기대 대미지에 기여하는 경우에만 1%p의 `DeltaLogDamage / DeltaPotential`을 갖고, 선택 스킬도 확정 크리티컬이면 초과분의 한계효율은 0이 된다. 사용자가 평타 크리티컬 기본 요구치를 명시적으로 덮어쓰는 UI는 추가할 수 있지만, 기본값은 100이다.

### 4.3 물리 대미지 계열의 균형점

선택한 물리 공격이 ATK, 크리티컬 대미지, 근거리 위력, 발도공격 네 계열만 사용한다고 단순화하면 대미지의 관련 부분은 다음 곱 구조로 볼 수 있다.

```text
D proportional to Attack(A) · Critical(C) · Range(R) · Unsheathe(U)
```

같은 계열 안에서는 합산되고 다른 계열과는 곱해지므로 비교에는 로그 한계효율을 사용한다.

```text
DeltaLog_k(delta | p_k) = log((100 + p_k + delta) / (100 + p_k))
```

크리티컬 대미지는 실제 크리티컬 확률·상한·300 이후 반감 규칙을 포함한 `BuildEvaluator`의 전후 결과로 `DeltaLog`를 구한다.

다음 18% 수치는 사용자가 설명한 과거 환경의 사례이며 현재 발도공격 옵션 수치나 상한을 뜻하지 않는다. 그 과거 사례에서 발도공격 18%를 세 개 사용해 `U=54`인 상태라면 네 번째 18%의 실제 상대 증가율은 다음과 같다.

```text
(1.72 / 1.54) - 1 = 0.116883... = 약 11.69%
```

당시 같은 슬롯에서 ATK 또는 근거리 위력을 최대 8%만 얻을 수 있었다면, 기존 ATK·근거리 합산량이 0이어도 상대 증가율은 최대 8%였으므로 네 번째 발도 18%도 더 우선할 수 있었다. 알고리즘은 계열을 억지로 균등 배분하지 않고 **현재 데이터의 검증된 옵션 수치, 현재 합산량, 획득처별 최대 제공량**으로 다음 한 단위의 로그 대미지 증가를 비교한다.

### 4.4 고정 시나리오의 공격력 등가축

대상 DEF/MDEF와 기준 ATK/MATK가 고정되면 공격력·관통을 같은 `%p` 비교축으로 환산할 수 있다. 물리 공격의 선형 구간을 예로 들면 다음과 같다.

```text
E_phys = ATK - DEF × (1 - PhysicalPierce / 100)
AttackAxisP = 100 × E_phys / BaseATK

PierceEquivalentAtkP(ΔP)
  = 100 × (E_phys(P + ΔP) - E_phys(P)) / BaseATK
  = DEF / BaseATK × ΔP
```

마법 공격은 `ATK`, `DEF`, 물리관통을 각각 `MATK`, `MDEF`, 마법관통으로 바꿔 같은 방식으로 계산한다.

예를 들어 `BaseATK=4000`, `DEF=2000`, 관통 0이면 `E_phys=2000`이므로 공격력 계열의 시작점은 `50%p`다. 거리 위력 계열은 기본 `100%p`에서 시작한다. 이때 공격력 옵션 `90%p`와 거리 위력 `40%`를 얻으면 두 축이 각각 `140%p`가 되어, 해당 두 계열만 놓고 본 균형점이 된다.

같은 예에서 물리관통 `10%p`는 `DEF/BaseATK × 10 = 5%p`의 ATK 등가값이다. 이 환산은 고정된 공격·대상과 같은 수식 구간 안에서 후보 정렬, 획득처 frontier, 안전 상한을 강화하는 용도로 쓴다. 실제 최종 순위는 바닥 함수·상한·스킬 고유 방어 무시·음수 구간을 포함한 `BuildEvaluator`의 원래 수식으로 다시 검증한다.

공격력 등가축은 실제 스탯 키를 ATK로 바꾸어 저장한다는 뜻이 아니다. 서로 다른 옵션을 비교하기 위한 시나리오 로컬 좌표이며, 대상이나 선택 스킬이 바뀌면 다시 계산한다.

### 4.5 Utility 획득처의 우선 처리

Utility는 모든 크리스타를 함께 돌리기 전에 다음 순서로 처리한다.

1. 현재 세팅에서 명시적으로 활성화된 슬롯 비경쟁 획득량을 먼저 계산한다.
2. 최소 요구량에서 고정 획득량을 뺀 `Residual`을 계산한다.
3. 각 장비·크리스타 부위가 제공할 수 있는 `Utility 증가량 / 대미지 슬롯 대체비용`의 Pareto frontier를 만든다.
4. 한 부위에서 대량으로 챙기는 경우와 여러 부위에서 분산해 챙기는 경우를 비교한다.
5. 요구량을 채운 뒤 남는 부위는 대미지 계열 균형 계산으로 돌린다.

적용 예시는 다음과 같다.

- ASPD: 사용자가 제시한 고르도 사례처럼 다른 크리스타에서 15~20%씩 분산하는 대신 특정 추가 장비 크리스타에서 80%를 확보하면, 남은 부위를 모두 대미지 옵션에 쓸 수 있다. AGI가 낮아 ASPD% 효율이 낮다면 에투왈 사례처럼 특수 장비 크리스타의 큰 고정 ASPD·행동속도 조합이 더 좋은 획득처가 될 수 있다. 비교는 원시 ASPD가 아니라 최종 행동속도와 요구치 충족 여부로 한다.
- MAXMP: 기본·레벨·INT와 현재 세팅에서 실제로 활성화한 스킬·요리·도핑·길드 버프만 먼저 합산한다. 이들은 자동 고정값이 아니라 입력 가능한 주요 획득처다. 활성 입력만으로 MP 요구치를 만족하면 MAXMP 전용 크리스타의 그림자가격은 0이 된다.
- MAXHP: VIT이 낮으면 HP%의 절대 증가량이 작다. 호뢰파섬 사례처럼 대미지 옵션과 고정 HP +7000을 함께 제공하는 후보는 HP% 전용 후보보다 높은 frontier에 남을 수 있다. 현재 세팅에서 실제로 활성화한 HP업·전선 유지 II·길드 버프 등이 있으면 이를 반영한 뒤 부족분만 장비에서 찾는다.

### 4.6 명확한 우선순위와 실제 계산 필요 영역

다음 경우에는 실제 전역 조합을 늘리지 않고 우선순위를 확정하거나 후보를 제거할 수 있다.

1. **무관 후보 제거**: 목적 대미지, Utility, 해결된 스탯 벡터 어디에도 영향을 주지 않는다.
2. **요구량 충족 제거**: 고정 획득처로 Utility 요구량을 이미 충족했고 후보가 그 Utility 외의 가치를 제공하지 않는다.
3. **동일 서명 엄격 지배**: 같은 부위·구조·충돌 서명에서 한 후보가 모든 관련 대미지 계열과 Utility에서 다른 후보보다 나쁘지 않다.
4. **집중 획득처 지배**: 한 개의 고효율 획득처와 나머지 부위의 최고 대미지 조합이, 그 획득처 없이 Utility를 분산 충족하는 모든 조합보다 나쁘지 않음이 상한으로 증명된다.
5. **한계효율 구간 지배**: 남을 수 있는 합산량 전 구간에서 후보 A의 최소 `DeltaLogDamage`가 후보 B의 최대값보다 크다.

다음은 실제 `BuildEvaluator`와 전역 탐색으로 넘긴다.

- DEX·STR처럼 여러 대미지 계열을 동시에 바꾸는 후보
- 도이와 바쿠잔처럼 직업 스탯·무기 공식에 따라 순위가 달라지는 후보
- 대미지 상한·반감·임계점을 탐색 도중 넘나드는 후보
- 서로 다른 계열에서 장단점이 갈리는 Pareto 후보
- Utility 요구량 충족 방법이 둘 이상이고 어느 쪽도 집중 획득처 지배를 증명하지 못한 경우

기존의 강제 포함·제외에 따른 점수 차이는 다음 이름의 결과 설명 지표로만 남긴다.

```text
ForcedChoiceRegret(e) = Phi(X*) - max Phi(X), subject to e in X
ExclusionRegret(e)    = Phi(X*) - max Phi(X), subject to e not in X
```

이는 사용자가 정의한 획득처 기회비용과 구분한다.

## 5. 조건부 옵션의 구조 확정 후 사전 물질화

현재 장비·크리스타의 조건은 `main`, `sub`, `armor`처럼 장비 구조만 확인하면 확정된다. 따라서 조건 자체를 전역 탐색의 동적 변수로 유지할 필요가 없다.

```text
StructuralState = (mainWeapon, subWeapon, armorType, element, ...)
ResolvedCandidate = resolveConditions(candidate, StructuralState)
```

조건은 다음 단계로 처리한다.

1. 주무기·보조무기·방어구 등 장비 구조를 먼저 확정한다.
2. 해당 구조에서 각 조건을 한 번 평가한다.
3. 활성화된 효과를 후보의 일반 스탯 벡터에 합산한다.
4. 비활성 효과는 수치 벡터에서 제외하되 결과 설명용 메타데이터에는 남긴다.
5. 탐색기는 조건이 이미 해결된 후보 벡터만 비교한다.

예를 들어 `경갑옷일 때 물리관통 +10%`는 경갑옷 구조 분기에서 활성화한다. 고정된 대상과 공격력 조건이 주어지면 그 관통을 ATK% 등가축으로 변환하여 다른 공격 옵션과 함께 평가한다.

장비 종류 자체도 최적화 대상이면 가능한 장비 구조를 먼저 소수의 분기로 나눈 뒤, 각 분기 안에서 후보 조건을 다시 물질화한다. 이때 보존할 정보는 구조 서명, 해결된 옵션 값, 충돌 서명, 결과 설명용 조건 메타데이터다.

향후 실제 데이터에 파생 스탯·다른 후보·전투 중 사건에 의존하는 조건이 추가될 때만 동적 조건 엔진을 별도로 설계한다. 현재 존재하지 않는 순환 조건이나 범용 Boolean AST는 D4의 선행조건으로 두지 않는다.

## 6. 유저 제작 장비 8옵션 자동 설계

### 6.1 범위와 입력 계약

장비는 이미 제작됐다고 가정하며 장비 제작, 슬롯 생성, 옵션 부여 행동 순서, 소재 비용은 계산하지 않는다. 기본 장비 구조는 크리스타 2슬롯과 옵션 8개다. 옵션 8개에는 음수 옵션이 포함될 수 있으며 최종 옵션 조합을 자동으로 고른다.

사용자는 다음 값을 입력한다.

- 사용 가능한 잠재력
- 단일 성공률
- 최종 성공률
- 인터넷을 사용할 수 없을 때 적용할 옵션 상한 기준 레벨

단일 성공률과 최종 성공률은 계산기가 역산하거나 최적화하지 않고 입력값을 결과 메타데이터로 보존한다. 잠재력은 옵션 조합의 hard budget으로 사용한다. 옵션 상한 기준 레벨은 최신 공식 레벨 상한 공지를 먼저 사용하고, 공식 확인이 불가능한 오프라인 상태에서는 사용자 입력값을 사용한다. 2026-08-24 확인 기준 공식 상한은 Lv.325다(`https://toram.jp/information/detail/?information_id=11036`).

크리스타 슬롯은 옵션부여 과정과 무관하다. 잠긴 크리스타는 고정 효과로 먼저 합산하고, 잠기지 않은 크리스타 슬롯만 전역 크리스타 후보로 남긴다. 옵션 8개와 크리스타 2슬롯 사이에 슬롯 수를 공유시키지 않는다.

### 6.2 최종 옵션 후보 표현

사용자가 이미 완성된 유저 제작 장비 옵션을 입력한 경우와 자동 생성한 8옵션 후보 모두 일반 장비와 동일한 `CandidatePackage`로 변환한다.

```text
CandidatePackage {
  slot,
  structureSignature,
  statDelta,
  resolvedConditionMetadata,
  sockets,
  conflicts,
  potentialCost,
  optionLineCount: 8,
  source: fixed | custom-final | custom-generated
}
```

옵션 수치가 1%p 달라질 때마다 합산 후 실제 평가 함수에서 한계효율이 다시 계산되므로 커스텀 옵션에 의한 효율 변동이 반영된다.

### 6.3 잠재력 제약 후보 생성

각 옵션의 허용 범위, 수치 단위, 양수·음수 순잠재력 비용, 무기·몸장비 제한, 동시 선택 불가 조건을 정규화한다. 최종 옵션의 순서가 아니라 최종 8개 옵션과 잠재력 합계만 상태로 유지한다.

```text
OptionState = (
  nextOptionIndex,
  remainingPotential,
  selectedOptionValues,
  optionCount,
  statVector,
  conflictSignature
)
```

옵션 상한과 잠재력 비용은 Coryn·Dodamu의 공개 계산 모델을 교차 참고해 독립된 데이터로 작성하고, 레벨 상한은 공식 공지를 우선한다. 코드 자체를 복사하지 않으며 출처·확인일·규칙 버전을 기록한다.

옵션 8개와 잠재력 예산은 bounded integer knapsack과 Pareto 동적 계획법으로 후보를 만든다. 옵션별 `DeltaLogDamage / DeltaPotential`은 초기 정렬과 상한에 사용하되, 크리티컬 임계·동일 계열 합연산·스탯 반올림처럼 상호작용하는 후보는 제거하지 않고 완성 빌드 평가까지 유지한다.

같은 옵션 인덱스와 충돌 서명에서 다음 조건을 만족하는 상태만 제거한다.

- 남은 잠재력이 더 많거나 같음
- 사용한 옵션 칸이 더 적거나 같음
- 모든 대미지·Utility 관련 결과의 안전 상한이 더 나쁘지 않음
- 구조·옵션 충돌 서명이 같음

하나라도 비교할 수 없으면 둘 다 유지한다. 옵션 DP의 정확히 8줄인 최종 Pareto 상태가 해당 부위의 커스텀 장비 후보가 되며, 잠긴 크리스타와 합산하고 잠기지 않은 크리스타 후보·고정 장비와 함께 전역 탐색한다. 결과에는 최종 8개 옵션, 사용 잠재력, 각 1%p의 실제 한계효율, 사용자가 입력한 단일·최종 성공률을 반환한다.
## 7. 고정 장비 목록 통합

추가 장비, 특수 장비, 보조무기 등의 고정 목록은 각 부위의 후보 집합 `I_s`로 넣는다. 유저 제작 장비도 같은 후보 집합에 들어가므로 별도 후처리가 필요 없다.

주무기·보조무기처럼 공격 공식과 스킬 사용 가능 여부를 바꾸는 장비는 가장 먼저 분기한다. 해당 구조 분기가 정해진 다음에만 그 구조에서 유효한 조건과 후보를 컴파일한다.

장비 하나와 그 장비에 들어갈 크리스타 조합을 부위 패키지로 묶는다.

```text
SlotPackage = equipment + customOptions + crystaSlots
```

각 부위에서 가능한 패키지를 생성한 뒤 안전한 Pareto 전처리를 수행하고, 남은 부위 패키지들을 전역 탐색한다. 이 방식은 장비 목록 선택과 크리스타 선택의 상호작용을 동시에 계산한다.

## 8. 전역 탐색 알고리즘

### 8.1 1단계: 문제 컴파일

- 문자열 스탯 키를 정수 ID의 조밀한 벡터로 변환
- 구조 상태별 조건을 한 번 평가해 해결된 스탯 벡터로 물질화
- 잠금·금지·계보·호환성 제약을 비트셋으로 변환
- 목적함수에 영향을 주지 않는 스탯도 Utility 또는 최종 계산식에서 쓰이면 보존
- 선택 공격·대상·버프가 같은 동안 재사용 가능한 시나리오 캐시 생성

스탯 합산에는 가능한 한 고정소수점 정수를 사용한다. 게임 수식에서 소수가 필요한 스탯은 키별 배율을 선언하고, 마지막 평가 단계에서만 변환한다. 이는 부동소수점 순서 차이로 순위가 바뀌는 문제를 줄인다.

각 부위 후보를 만들기 전에 고정 획득량과 Utility 부족분을 계산하고, 부위별 `대미지 계열 + Utility 획득량 + 슬롯 대체비용` frontier를 만든다. 같은 대미지 계열의 큰 수치를 한 번에 얻는 후보와 Utility를 집중 획득하는 후보를 보존한다.

획득처 집중 지배와 한계효율 구간 지배가 수학적으로 증명된 후보만 제거한다. `SourceValue`가 낮다는 이유만으로 제거하지 않는다.

### 8.2 2단계: 부위별 후보 생성과 안전한 Pareto 축약

각 부위에서 고정 장비, 수동 커스텀 완성 옵션, 잠재력 제약으로 자동 생성한 8옵션 frontier, 크리스타 조합을 패키지화한다.

후보 `A`가 `B`를 제거할 수 있는 충분조건은 다음과 같다.

1. 구조·충돌·옵션·계산식 서명이 같음
2. 자원 비용이 더 나쁘지 않음
3. 현재 남은 탐색 범위에서 모든 목적·제약 결과가 더 나쁘지 않음이 증명됨

단순히 ATK가 높다는 이유로 HP·MP·AMPR 후보를 제거하지 않는다. Utility 축이나 계산식 분기가 다르면 지배 관계를 선언하지 않는다. 증명할 수 없으면 후보를 유지한다.

### 8.3 3단계: 빠른 초기해

정확 탐색 전에 다음 순서로 유효한 초기해를 만든다.

1. 필수 조건을 우선 만족하는 greedy 구성
2. 고정 획득량을 제외한 Utility 부족분을 가장 집중도 높은 획득처로 채우는 구성
3. 각 대미지 계열의 현재 `DeltaLogDamage`가 큰 후보를 순서대로 선택하는 구성
4. 그림자가격 `lambda`를 갱신하는 Lagrangian 반복
5. 현재 빌드를 시작점으로 한 부위 교환 coordinate descent
6. 상위 후보를 사용한 작은 beam search

이 초기해는 결과를 빨리 보여주는 동시에 분기 한정의 하한 `L`을 높여 많은 분기를 제거한다. 초기해는 최적이라고 표시하지 않는다.

현재 크리스타 구현은 Pareto 준비 전에 원본 후보를 선형 스캔해 Utility 우선·대미지 우선 초기해를 즉시 평가한다. 이후 각 부위의 상위 대미지/Utility 후보를 실제 `BuildEvaluator`로 다시 비교하는 제한된 coordinate descent를 수행한다. 전체 정렬을 첫 결과의 선행조건으로 두지 않아 실제 425개 fixture에서 첫 유효 추천을 61~63ms에 확보한다.

### 8.4 4단계: 안전한 상한

부분 선택 `P`에서 아직 고르지 않은 후보들이 만들 수 있는 각 스탯 범위를 계산한다.

```text
A_j ∈ [lower_j(P), upper_j(P)]
```

남은 각 부위의 조건이 이미 해결된 후보 벡터에서 스탯별 최솟값·최댓값을 구해 구간을 만든다. 서로 다른 장비 구조의 후보는 같은 상한 계산에 섞지 않고 구조 분기별로 계산한다.

게임 계산식 `F`의 사칙연산, min/max, floor, clamp, 조건 분기를 구간 연산으로 실행한다. 이렇게 얻은 `U(P)`는 부분 선택을 어떤 방식으로 완성해도 넘을 수 없는 안전한 목적함수 상한이어야 한다.

```text
∀ completion X of P: Phi(X) ≤ U(P)
```

구간 상한이 느슨해도 정확성은 깨지지 않고 탐색량만 늘어난다. 다음 방법으로 상한을 강화한다.

- 부위별 최대 기여를 단순 합이 아니라 배타 선택 제약과 함께 계산
- 선형 구간에서는 LP relaxation 사용
- 상한·바닥 함수의 break point로 구간 분할
- 구조 분기별 별도 상한
- 상한·바닥의 수식 구간이 확정될 때 즉시 재계산

현재 최선 점수 `L`에 대해 `U(P) ≤ L`이면 그 분기를 제거한다. 필수 Utility의 가능한 최댓값조차 요구치를 충족하지 못하면 점수와 무관하게 제거한다.

현재 크리스타 구현은 각 부위 후보를 안전한 스탯 상한 envelope를 가진 이진 트리로 만든다. 탐색 노드는 네 부위의 후보 부분집합 상자 `(C_weapon, C_armor, C_additional, C_special)`이며, 상한은 각 상자의 envelope를 합산해 기존 `BuildEvaluator`로 평가한다. 한 부위를 끝까지 확정한 뒤 다음 부위로 넘어가지 않고, envelope의 과대평가 감소량이 큰 두 부위를 동시에 이분해 최대 네 자식 상자를 만든다. 모든 실제 조합은 정확히 하나의 자식 상자에 포함되므로 상한의 안전성을 유지하면서 부위 간 배타 선택 상관을 더 빨리 반영한다. 남은 완성 조합 수가 64개 이하인 상자는 추가 상한 노드 없이 직접 전수조사한다. 소형 무작위·음수 옵션 문제의 모든 계층형 상자 상한과 최종해를 전수 대조하는 property test를 둔다.

### 8.5 5단계: anytime 분기 한정

초기에는 점수가 유망한 가지를 깊이 탐색해 좋은 완성해를 빠르게 찾고, 이후 best-bound 우선순위 큐로 가장 큰 상한을 가진 가지부터 증명한다.

현재 완성해 중 최고 점수를 `L`, 남은 노드의 최대 상한을 `U`라고 하면 최적성 오차는 다음과 같다.

```text
gap = max(0, U-L) / max(abs(L), epsilon)
```

- 탐색 큐가 비거나 `gap = 0`: 전역 최적 증명
- 제한 시간에 도달하고 `gap > 0`: 현재 최선해와 인증된 오차 반환
- 사용자가 취소: 마지막 유효한 최선해와 당시 오차 반환

Pareto 모드에서는 한 점의 `L` 대신 현재 비지배 해 집합을 유지한다. 부분 노드의 목적 상한 벡터가 현재 Pareto 집합에 완전히 지배되면 제거한다.

### 8.6 Big O와 원시조합 최악 시간

구조 분기별 부위 패키지 수를 `m_s`, 완성 빌드 1회의 평가 비용을 `T_F`라 두면 원시 전수조사는 다음과 같다.

```text
N = Π(s) m_s
Time = O(N × T_F)
Space = O(depth)          // 한 조합씩 순회
Space = O(N)              // 모든 조합·best-bound 노드를 보존하는 최악 경우
```

각 선택 단계가 평균 `m`개이고 단계가 `k`개라면 `N=m^k`이므로 `O(m^k × T_F)`다. Pareto frontier와 branch-and-bound는 일반 입력에서 `N`을 크게 줄이지만, 모든 후보가 비지배이고 상한이 느슨한 최악 경우에는 여전히 `O(N × T_F)`다. best-bound 우선순위 큐의 메모리도 최악에는 `O(N)`이며, 메모리 제한형 깊이 우선 탐색을 쓰면 메모리를 줄이는 대신 좋은 상한 노드의 처리 순서를 일부 포기한다.

현재 기록된 잠금 없는 원시조합 `N=39,381,065,483,300,352`개를 단순 평가한다고 가정한 시간은 다음과 같다. 아래는 평가기 호출만 센 이론값이며 UI·메모리·후보 생성 비용을 제외한 실측값이 아니다.

| 평가 속도 | 예상 시간 |
| ---: | ---: |

## 9. 속도 계약

제안하는 기본 UX 시간 예산은 다음과 같다. 실제 수치는 구현 후 대상 PC 벤치마크로 조정한다.

- 100ms 안: 입력 검증과 이전 캐시 확인
- 500ms 안: 첫 유효 추천 표시 목표
- 3초 안: 일반 입력의 정확해 완료 목표
- 5초: 기본 자동 탐색 시간 제한
- 5초 초과: 현재 최선해와 최적성 gap을 표시하고 사용자가 정밀 계산을 계속할 수 있게 함

복잡한 입력에서도 UI 스레드를 막지 않는다. 첫 구현은 기존 계산식을 그대로 공유할 수 있는 JavaScript Worker를 사용한다. Rust 작업 스레드로 옮길 때는 계산식을 별도로 재작성하지 않고 공통 계산 IR에서 JS/Rust 평가기를 생성하거나 두 평가기의 전수 일치 검증을 통과시켜야 한다. 어느 실행 계층이든 16~32ms 단위로 진행 상태와 최선해를 전달한다.

현재 구현은 JavaScript Worker에서 기존 `ToramCalculationKernel`을 직접 재사용한다. 5초 기본 탐색이 `bounded`이면 인증 gap과 함께 결과를 표시하고, 사용자가 선택하면 같은 스냅샷을 30초 예산으로 다시 탐색한다. 시간 예산이 다른 실행은 캐시를 공유하지 않는다.

2026-08-24 실제 425개 fixture의 개선 기준은 컴파일 약 113~117ms, 첫 유효 추천 62~65ms, 5초 약 9.2만회 평가, 하한 14,090.0409, 상한 약 20,385, gap 약 44.7%다. 30초 정밀 모드는 약 69.6만회 평가 후 상한 17,556.75, gap 24.604%였다. 반복 BuildSnapshot·해시·동결 생성을 생략한 집계 평가 경로와 상한용 경량 결과를 사용하고, envelope 감소량이 큰 두 부위를 동시에 분할하며 64조합 이하 상자를 직접 전수조사한다. 물리/마법·거리·발도/일진강풍 변환에 따라 실제로 영향을 주는 축만 남기고, 각 부위 안에서 값이 변하지 않는 축은 지배 비교에서 제외한다. 사전식 ID 순서에서는 뒤 후보가 앞 후보를 제거할 수 없다는 동점 계약을 이용해 중복 역비교를 제거했으며, 부위당 비교 예산 100만 안에서 네 부위 Pareto가 모두 완결된다. 실수식 좌표 개선은 부위당 192개 후보를 사용한다. 자동 회귀 합격선은 첫 추천 500ms 이내, 하한 13,500 이상, 5초 gap 75% 이하, 네 부위 Pareto 완결이다. 이는 품질 회귀 방지선이지 exact 완료 기준이 아니며, gap이 남으면 계속 `bounded`로 표시한다.

진행률은 검사한 조합 수를 전체 조합 수로 나누지 않는다. 가지치기로 전체 수가 계속 바뀌기 때문이다. 다음 정보를 표시한다.

- 경과 시간 / 시간 예산
- 현재 최선 점수
- 최적성 gap
- 처리 노드 수
- `정확한 최적해`, `gap 이내 추천`, `초기 추천` 상태

성능을 위해 다음을 적용한다.

- DOM 접근 없는 순수 평가기
- 조밀한 TypedArray 스탯 벡터
- 충돌·호환성 비트셋
- 부분합 증분 갱신과 되돌리기
- `(구조 서명, 관련 스탯 벡터, 시나리오)` 평가 캐시
- 8옵션 DP와 부위 패키지 Pareto 캐시
- 구조 분기 단위 병렬 실행
- 동일 점수의 결정적 tie-breaker

## 10. 결과 계약

최적화 결과는 최소한 다음 정보를 포함한다.

```text
OptimizationResult {
  status: exact | bounded | heuristic | cancelled | invalid,
  bestBuild,
  score,
  outcomes,
  hardConstraintStatus,
  lowerBound,
  upperBound,
  optimalityGap,
  elapsedMs,
  alternatives,
  activeConditions,
  inactiveConditions,
  sourceOpportunityCosts,
  forcedChoiceRegrets,
  craftPlan?,
  diagnostics
}
```

`exact`가 아닌 결과를 최적이라고 표시하지 않는다. 조건부 옵션은 문제 컴파일 단계에서 해결하되 어떤 장비 구조 때문에 활성·비활성됐는지 함께 보여준다. 등록되지 않은 스탯이나 평가되지 않는 옵션 상한·잠재력 비용 규칙이 선택 목적에 영향을 줄 수 있으면 `invalid` 또는 비인증 결과로 처리하고 누락 키를 표시한다.

## 11. 정확성 검증

구현 시 다음 테스트가 필수다.

1. 작은 임의 문제를 전수조사해 전역 탐색 결과와 일치하는지 비교
2. 모든 부분 노드에서 `upperBound ≥ 모든 실제 완성 점수` 속성 검사
3. Pareto 전처리가 전수조사 최적해를 제거하지 않는지 검사
4. 동일 옵션 합연산, 크리티컬·안정률·행동속도 상한의 한계효율 회귀
5. 주무기·보조무기·방어구 조건이 바뀔 때 조건부 옵션 가치가 바뀌는 사례
6. 크리스타 계보·동일 장착·잠금·제외 목록 충돌 사례
7. 고정 장비와 커스텀 장비가 같은 후보 집합에서 경쟁하는 사례
8. 작은 옵션·잠재력 문제의 8옵션 DP 결과를 전수조사와 비교
9. 시간 제한·취소 시 반환한 `L`, `U`, gap의 유효성 검사
10. 같은 입력의 결과와 tie-break 순서가 실행마다 같은지 검사
11. 등록된 모든 스탯 키가 평가·Utility·진단 중 하나에 연결되는지 감사
12. 일반·최악 입력에 대한 500ms/3초/5초 성능 회귀
13. 과거 환경을 재현한 합성 fixture에서 발도공격 18%를 세 번 적용한 뒤 네 번째 18%의 상대 증가율이 약 11.69%가 되는 계열 균형 사례. 현행 발도 옵션 데이터로 사용하지 않는다.
14. 고정·외부 MAXMP로 요구량을 만족하면 MP 전용 크리스타가 제거되는 사례
15. 고정 ASPD·ASPD%·낮은 AGI에 따라 집중 획득처가 달라지는 사례
16. 낮은 VIT에서 고정 HP와 대미지 옵션을 함께 가진 후보가 HP% 전용 후보보다 우선하는 사례
17. BaseATK 4000·DEF 2000에서 공격력 등가축이 50%p이고, ATK 90%p·거리 위력 40% 적용 뒤 두 축이 140%p가 되는 사례
18. 같은 시나리오의 물리관통 10%p가 ATK 5%p 등가이며 최종 BuildEvaluator 순위와 모순되지 않는 사례
19. 장비 구조 조건이 후보 생성 때 한 번만 해결되고 탐색 노드 수에 별도 조건 차원을 추가하지 않는 사례
20. 근거리/원거리 기본 MAXHP 요구치, 신속의 수도 전후 MAXMP, 듀얼소드 전후 AMPR, ASPD 1000 기본 요구치 사례
21. 복수 통상공격 변화 액티브를 각각 단독 평가해 최종 AMPR이 가장 높은 하나만 적용하고, 축지법의 1회성 하프 액티브 AMPR은 지속 Utility에서 제외하는 사례
22. 같은 크리스타의 다른 장비 반복 허용, 같은 장비 중복 금지, 강화 분기 계보 충돌 사례
23. 잠긴 크리스타 조합은 고정하고 잠기지 않은 크리스타와 유저 제작 8옵션을 함께 최적화하는 사례
24. 같은 대미지 옵션의 1%p가 현재 합산량과 잠재력 비용에 따라 다른 `DeltaLogDamage / DeltaPotential`을 만드는 사례
25. 선택 스킬이 확정 크리티컬이어도 평타 최종 크리티컬률 100을 만족하는 후보만 유지하고, 평타 100 달성 후에는 선택 스킬의 크리티컬 판정에 따라 초과 크리티컬률의 한계효율이 0이 되는 사례
26. 음수 옵션이 회복 잠재력 대비 대미지·Utility 손실과 옵션 한 칸의 비용으로 비교되는 사례
27. 공식 레벨 상한 온라인 확인 성공과 오프라인 사용자 입력 fallback 사례
28. 단일 성공률·최종 성공률 입력값을 계산하지 않고 결과에 그대로 보존하는 사례

## 12. 구현 순서

D4 구현은 다음 순서로 나눈다.

1. `BuildEvaluator` 순수 함수화와 전체 `StatRegistry`
2. 현행 크리스타 8슬롯만 대상으로 전역 탐색·상한·전수조사 대조
3. Utility 요구치, Utility 곡선, Pareto 대안 추가
4. 추가 장비·특수 장비·보조무기 등 고정 후보 목록 연결
5. 완성된 유저 제작 장비 옵션 후보 연결
6. 8옵션·잠재력 비용 데이터 계약과 옵션 Pareto DP 연결
7. Worker/Rust 병렬화, 제한 시간, 중단·재개, 진행 UI
8. 획득처·잠재력 기회비용, 강제 선택 후회값, 대안 설명 UI

1~2단계에서 안전한 상한과 전역 최적 증명을 확보하기 전에는 기존 결과를 `전역 최적`이라고 바꾸지 않는다.

## 13. 요구사항과 후속 결정 대응

| 요구사항 | 설계 대응 |
| --- | --- |
| HP·MP·AMPR·행동속도 Utility | hard constraint + 구간별 Utility + Pareto 결과 |
| 유저 제작 장비의 커스텀 효율 | 최종 옵션을 일반 후보와 동일하게 전체 빌드에서 재평가 |
| 유저 제작 장비 8옵션 자동 설계 | 잠재력 hard budget + 8줄 bounded knapsack/Pareto DP + 전역 BuildEvaluator 재평가 |
| 빠른 계산 | 빠른 초기해, Pareto 축약, 안전한 상한, 캐시, 병렬 anytime 탐색 |
| 고정 장비 목록 중 최선 선택 | 모든 장비를 부위 후보 집합으로 통합 |
| 동일 계열 합연산 체감효율 | 옵션별 점수 합산 금지, 완성 빌드 `F` 재평가 |
| 조건부 옵션 가치 변화 | 장비 구조를 먼저 확정한 뒤 조건 효과를 일반 옵션 벡터로 사전 물질화 |
| 획득처 기회비용 | 고정·외부 공급 후 Residual 계산, 슬롯별 집중 획득 frontier와 슬롯 대체비용 비교 |
| 잠재력 pt 기회비용 | 옵션 1%p의 `DeltaLogDamage / DeltaPotential`, 음수 옵션 손실, 옵션 8칸 대체비용을 함께 평가 |
| 크리티컬률 자동 선택 | 평타 최종 크리티컬률 100을 기본 hard constraint로 보장하고, 초과분만 선택 스킬의 한계효율로 평가 |
| 명확한 우선순위와 실제 계산 구분 | 지배를 수학적으로 증명한 후보만 제거하고 교차 후보는 BuildEvaluator 전역 평가 유지 |
| ATK·MATK·관통 비교 | 고정 시나리오의 공격력 등가축으로 후보를 정렬하고 최종 순위는 원래 수식으로 재검증 |
| 과거 발도공격 18% 사례 | 현행 데이터가 아닌 한계효율 합성 회귀로만 보존 |
| 원시조합 복잡도 | 최악 `O(Π m_s × T_F)`, 약 3.94경 조합은 규칙 기반 축약 없이는 실행 불가 |
