# 부여 실행 전 성공률 경고 계산

2026-10-21. 저장된 PE의 `SmithGrant.OnGrantBeforeStartButton`을 선택 분석했다. 기존 `ShowCheckWindow`는 창 표시만 하며, 이 함수에서 비용·잠재력과 스킬 보너스를 읽어 실행 전 경고에 쓰는 정수를 만든다. 게임 실행·서버 난수 판정은 관측하지 않았다. 입력 해시·토큰·주소·상수 원시 바이트는 index.json에 보존했다. 직접 Ghidra 분석이며 REA retained Evidence ID는 없다.

```text
D = max(원본 ItemDBData.Potential, 현재 WeaponPotential)
A = 100 + getSuccessSkillRate()
rate = trunc(f32(A - f32(f32(f32(100 / D) × (소모비용 - 현재잠재력)) × 2.3f)))
warningRate = max(0, rate)
```

식의 모든 나눗셈·곱셈·뺄셈은 각각 float32다. 2.3f의 원시 바이트는 `33331340`이고 정확한 실수 2.3과 다르다. 세 강화 스킬이 Lv10이면 A=160이다. warningRate가 100 이상이면 낮은 확률 경고 분기를 건너뛴다. 0이면 경고 화면에서 실행 버튼을 끄는 분기가 있다. 이 경고 계산을 서버의 전체 성공 판정과 같다고 주장하지 않는다.

분모는 단순한 현재 잠재력이 아니다. `MasterItemDataManager.GetMasterItemData`가 돌려준 마스터의 +0x4c 16비트 값과 현재 잠재력을 비교해 큰 값을 쓴다. ItemDBData.get_Potential의 코드 `0f b7 41 4c c3`와 같은 필드다. 제작 스탯으로 늘어난 최초 잠재력이나 이전 단계의 최댓값을 분모 하한으로 저장하는 코드가 아니다.

따라서 사용자 정리의 `160+230×(부여후/부여전)`은 현재 잠재력이 원본 기초 잠재력 이상일 때 대수적으로 대응한다. 현재 잠재력이 원본보다 작으면 분모 하한이 달라지고, 대응하는 식도 float32 연산 순서를 보존해야 한다. 실험기는 이 네이티브 순서를 사용한다.

기본 부여 경로처럼 마이너스 옵션으로 잠재력을 늘린 뒤 마무리할 때는 현재 잠재력이 원본 기초 잠재력을 넘으므로 분모 보정의 영향이 없다. 이 예외는 계산 재현의 경계로 보존하며 일반적인 경로 최적화의 큰 차이로 설명하지 않는다.

원본 기초 잠재력과 제작 후 시작 잠재력을 별도 값으로 유지해야 한다. 마지막 단계의 잠재력이 음수라는 이유만으로 실패로 처리하지 않으며, 다음 부여를 시작할 수 있는 조건은 별도로 확인한다. 각 옵션의 독립 성공/실패·첫 슬롯 보호·반전 결과와 실제 완성 확률은 이번 함수의 증명 범위가 아니다.
